Covers all five packages (`hcl_core`, `hcl_radiance`, `hcl_daysim`, `hcl_mcp`, `hcl_platform`). The spectral and circadian methods implement published models directly from primary literature (see `docs/literature-bibliography.md`).

**Date:** 2026-08-11 (as-built revision).
**Method:** Every module was re-read in full against the current source for this revision; each cited `file.py:NN` reference, constant, default, and tool/prompt/resource count was verified against the code as it stands today. ## 0. What this project is

`hcl-mcp` is a portable, dependency-light Python toolkit for spectral and human-centric lighting analysis, exposed as a local **MCP (stdio) server**. Its spectral, circadian, and photometric methods implement published scientific literature directly (see §11 citations and `docs/literature-bibliography.md`). It computes spectral / human-centric-lighting metrics per **CIE S 026:2018** and the CIE S 026 α-opic suite, generates Radiance inputs, runs the per-channel Radiance pipeline when Radiance is present (else emits the exact command sequence), and adds an electric-lighting layer (IES photometry per **IESNA LM-63**, EnergyPlus daylight-controls energy model per **EnergyPlus Engineering Reference §7.3.5**, and EN 12464-1) and a circadian-alerting layer (nvRD model per **Amundadottir 2016** and an automatic annual→nvRD bridge driven by Daysim).

### Architecture — five modules in four layers, strict discipline

Listed bottom-up; imports point downward only.

```
hcl_platform/ Stdlib-only compat base beneath everything: forward-slash path normalization
              (paths.py), UTF-8/LF text I/O (textio.py), Windows-aware executable resolution
              (exe.py: resolve_exe appends platform executable extensions and is the single
              resolver behind both adapters' resolve_bin). No domain logic.
hcl_core/     Pure Python, zero deps for the verified math (≤401-pt arrays, plain loops →
              bit-for-bit reproducible on the 9-channel path). The valuable, verifiable
              asset. The extras layer (presets, spectral_metrics) alone adds colour-science (numpy).
hcl_radiance/ Radiance adapter. Detect binaries → build command lines → run-or-emit. Parse
              outputs. Runs engine subprocesses and writes simulation output.
hcl_daysim/   Peer adapter for Daysim (ds_shortterm/epw2wea), build-from-source, never bundled.
              Also runs engine subprocesses. The one edge between the two adapters is the
              annual nvRD pass borrowing the sub-hourly .wea generator.
hcl_mcp/      Thin FastMCP server. 47 tools (+4 verb_object aliases = 51 registered names),
              14 resources, 13 prompts. Maps tools → core/radiance/daysim; holds no business logic.
```

The layer separation is honoured, and asserted rather than assumed: `hcl_core` imports nothing from the layers above it (only the stdlib-only `hcl_platform` base below it), and `tests/test_module_layering.py` walks `src/` and fails the suite on any import above a module's layer. All subprocess/filesystem access for simulation lives in `hcl_radiance`/`hcl_daysim`; the MCP layer holds no business logic. A large physical-sky feature (spectral-sky-from-EPW, §7bis) and a native-Radiance `gensdaymtx` driver were added to this architecture without breaking it: an offline EPW→atmosphere/geometry→SPECTRL2/SMARTS→SEDES1→1nm-record→artifacts pipeline in `hcl_core`, plus native engines in `hcl_radiance`. The canonical as-built record for that feature is `docs/spectral-sky-as-built.md`; the physics/math derivation is `docs/spectral-sky-methodology.md`.

### Code size

**99 source files** + **149 test files** (`find src -name '*.py'` = 99, `find tests -name '*.py'` = 149; **≈17,186 source lines**). The tree includes the spectral-sky-from-EPW pipeline, OBJ/CAD import, the geometry-derived sensor tools, the geometry health check, the SEDES1 local-recalibration path, the opt-in SEDES2 tabulated cloud modifier, and the LM-83 three-phase engine (`lm83.py`, `klems.py`, `threephase*.py`, `aperture.py`, `lm83_run.py`, `lm83_sun.py`, `source_cal.py`). *(Re-counted 2026-08-12; the previous `91 / 138 / ≈15,226` was the 2026-08-06 count, before the LM-83/three-phase modules landed.)*

### Headline verdict

The **pure-Python spectral math is a literature-grounded implementation** with two deliberate corrections (§9.3a/§9.3b below). Every constant independently recomputed reproduces the published model (or, for the §9.3b fix, the corrected value). The **electric-lighting math** (IES photometry per IESNA LM-63, EnergyPlus controls per §7.3.5) reproduces all golden values exactly. The **two things to know** before trusting a *live* run:

1. **The enhanced colored-sun reconstruction is time-resolved on a live Daysim run** (§7.5) — `generate_subhourly_wea` surfaces per-timestep `timestamps`/`solar_zeniths` and `annual_nvrd` feeds them into the reconstruction, so the air-mass reddening varies by time of day. A constant 30° zenith is used only in degraded mode (no Daysim / empty `.wea`), and that case is labelled in `enhanced_solar_note`. (Accuracy is still bounded by the simplified `weather.solar_zenith` model.)
2. **The live paths are executed, not just emit-tested.** Daysim is **built and live** (`HCL_DAYSIM_BIN=/usr/local/daysim/bin`); `run_annual` (2-phase DDS), the `annual_nvrd` Daysim bridge, SMARTS, and the native `gensdaymtx` driver are all live-validated (2026-06/07, Radiance 6.1a at `/usr/local/radiance`). The **electric-lighting / luminaire→Radiance transport** (`ies2rad`→colorize→`!xform`→combined octree) is live too, since 2026-07-18 and re-exercised 2026-08-12 — ⚠️ but only on an `A1`-honouring engine: check `radiance_status().source_cal` before quoting any electric number (§10.3).

## 1. The spectral foundation — `hcl_core/{data,_spectra,spd,materials,metrics,alpha_opic}.py`

> **Source:** Inanici, Brennan & Clark 2015 (9-/3-channel bin layout, H-2/H-4). CIE S 026/E:2018 (α-opic suite, H-5…H-12).

This is the heart: SPD → channel binning → circadian metrics and the CIE S 026 α-opic suite.

### 1.1 Reference data (`data.py`, `_spectra.py`)

> **Source:** Inanici, Brennan & Clark 2015, §2–3 (9-channel bin layout and photopic/melanopic weight vectors, H-2/H-4). Jung, Cheng, Brennan & Inanici 2023 (OPN5 neuropic scheme, H-4).
> **Source:** CIE S 026/E:2018 (action spectra `ACTION_S/M/L/RHOD/MEL`, `V_LAMBDA`, K^D65 reference ELR; H-5…H-12).

**9-channel bins** (`data.py:13-14`), ascending, labelled b1,b2,b3 (blue) / g1,g2,g3 (green) / r1,r2,r3 (red):

```
[380,419][419,459][459,499][499,529][529,558][558,587][587,608][608,630][630,780]
```

**3-channel bins** (`data.py:15`), DESCENDING, paired r,g,b: `[587,780][499,587][380,499]`. The descending order is preserved from the `CIE Toolbox:98` reference, *including* its latent ordering bug — corrected only downstream in `alpha_opic.py` (§1.5). The ascending-reordered counterpart `BINS_3_ASC = [[380,499],[499,587],[587,780]]` (`data.py:18`) is the single source consumed by the §9.3b fix in both `alpha_opic` and spectral reconstruction.

**Bins share boundaries** (419, 459, …) and the binning is **inclusive on both ends** (`spd.py:145`, `lo <= k <= hi`), so boundary wavelengths are **double-counted** in two adjacent bins. This is faithful to the source's `avg_count` and is by design — the bins are not a strict partition.

**Weight vectors** (`data.py:21-26`), verified digit-for-digit against `9-channel:276-278` (grid path) and `3-channel:177-178`:

- `W_PHOTOPIC_9` sums to **1.000023917 → 1.000024** — the *only* non-unity column, by design. (The validation tolerance must be ±5e-5, not ±1e-6, to admit it.) `179 × Σ = 179.004281`.
- `W_MELANOPIC_9`, `W_NEUROPIC_9`, `W_PHOTOPIC_3`, `W_MELANOPIC_3` all sum to 1.000000.
- **§9.2 within-source inconsistency:** `W_NEUROPIC_9[2] = 0.000069431` (the grid-path value). The alternative image/pcomb path rounds it to `0.00007`. This implementation standardizes on the grid value for both paths.

**Action spectra** (`_spectra.py`): 401-value (380–780 nm @1 nm) curves `ACTION_S/M/L/RHOD/MEL` (CIE S 026:2018 α-opic action spectra), `V_LAMBDA` (CIE photopic V(λ)), `D65_ELR` (D65 efficacy-of-luminous-radiation, for EDI normalization), and `IPRGC_SENS_WEIGHTING` (311-value ipRGC curve for nvRD). Spot-verified against the CIE S 026 reference values. Cones (S/M/L) carry 10 leading zeros (no sensitivity <390 nm). The file is machine-generated (`scripts/extract_spectra.py` header) and re-exported through `data.py:7-10`.

**Other constants:** `LUMINOUS_EFFICACY = 179.0` (Radiance lm/W, H-3); `EML_PER_MEDI = 1.103` (EML ≈ mel-EDI × 1.103, H-12, from the Five-Step HCL method Eq. 3 — *Human-Centric Lighting: Foundational Considerations and a Five-Step Design Process*; not used in the core metrics path); the `NVRD` dict (`data.py:36-37`: EI50=106.0, slope=3.55, filters (0.3,1.7,2.3) h, `zeff = 310/683/118.5/1.42·0.91`, timestep_h=0.1 — Amundadottir 2016). Also present: `ALPHA_ARRAYS`/`ALPHA_NAMES` (α selector 1..5 → action array / name), `FOV_WEIGHTS` (ipRGC field-of-view quadrant weights, `data.py:34`).

### 1.2 SPD parsing & binning (`spd.py`)

> **Source:** Inanici, Brennan & Clark 2015, §2 (bin-average definition, H-2).

`parse_spd` (`:41-115`) — implements the standard SPD-to-channel-bin pipeline (linear interpolation + bin averaging); together with `bin_average` below it backs the MCP tool `spd_to_channels`. It accepts a `.spd` **file path**, SPD text, or `(λ, value)` pairs — a bare no-newline string that names a readable file is read from disk via `_read_if_path` (`:8-19`), mirroring the IES reader:

1. Tokenize on comma→tab→whitespace, drop non-numeric rows (`_rows_from_text`, `:21-39`).
2. Keep wavelengths 380≤λ≤780 (`:45`).
3. **Linear end-extrapolation** to 380/780 using the first/last gradient (NOT "repeat last value" — the source *docstring* is wrong, its *code* extrapolates; this implementation follows the code), with a `max(0.0, …)` **clamp** (`:64,68`) so a negative extrapolation cannot inject unphysical negative irradiance into the positive-weighted α-opic/melanopic integrals. A lone in-range sample (which can't define a slope) is extended **flat** to both anchors instead of crashing (`:50-57`).
4. Linear-interpolate to a 1-nm grid, then collapse onto integer nodes (last-write-wins for colliding sub-integer rows). Because `int(round())` is round-half-to-even, half-integer-aligned inputs can leave odd keys unemitted; a **backfill pass** (`:101-114`) linearly fills any missing integer key so the output is **exactly 401 keys** (380..780). For integer-spaced inputs nothing is backfilled and the result is bit-identical to the pre-backfill behaviour.

`bin_average` (the inclusive `lo <= k <= hi` predicate is the load-bearing part): average within each inclusive bin → 3 or 9 values, at **full precision — no rounding**. The original Lark port rounded each band mean to 3 decimals, an *absolute* 5e-4 quantum and therefore scale-dependent: harmless on preset SPDs (native scale ~75–113) but corrupting on the absolute W/m²/nm spectral irradiance `spectral_emit.to_channels` feeds in (worst band error ~13 % near 0.01, 100 % at 0.002). Removing it is inert for every existing consumer — the ramp goldens are exactly representable and reproduce to the digit. Note the §9.3a reconstruction is calibrated to the closed-band **MEAN convention**, not to any rounding precision (it is a flat linear scalar, so it cannot be). A `channel_type` guard rejects anything but 0/1.

### 1.3 Materials (`materials.py`)

> **Source:** Ward / LBNL Radiance transmissivity polynomial (standard Radiance glass material definition).

`glass_transmissivity` (`:5-15`) — transmittance Tn → Radiance transmissivity, the standard Radiance polynomial; accepts a float or a list, and short-circuits `Tn == 0` to `0.0`:

```
trans = (sqrt(0.8402528435 + 0.0072522239·Tn²) − 0.9166530661) / (0.003626119·Tn)   (round 3)
```

`write_material` (`:28-54`): emits Radiance primitives (via `_primitive`, `:21-25`) — glass `void glass NAME … 3 v0 v1 v2`, plastic `void plastic NAME … 5 r g b spec rough` (the classic spec/rough swap is absent; argument order is r,g,b,specularity,roughness). 9-channel → three files `_a`(b1b2b3)/`_b`(g1g2g3)/`_c`(r1r2r3); 3-channel → one file. Glass values are transmittance→transmissivity converted first. Returns `{files, channel_output}`. (only `material_type` 0/1; anything else raises — sky/electric-light materials live elsewhere, e.g. `sky.py`.)

### 1.4 Circadian metrics (`metrics.py`)

> **Source:** Inanici, Brennan & Clark 2015, §2–3 (channel-weighted metric formula). Jung, Cheng, Brennan & Inanici 2023, §2–3 (neuropic/OPN5 weighting).

The core formula (`_dot`, `:6-7`): **`metric = 179 · Σ(weightᵢ · channelᵢ)`** (H-4, per Inanici et al. 2015 §2). `circadian_metrics` (`:120`) accepts one point (list of 3/9) or many (list of lists) and returns a dict or list of dicts, dispatching through `_one` (`:29`). 9-channel returns photopic/melanopic/neuropic lux; 3-channel returns photopic/melanopic only (neuropic intentionally undefined for 3-channel). Length is enforced (9 or 3). Verified golden: a point → photopic 51.5333, melanopic 41.0736, neuropic 18.2406 (`tests/test_metrics.py`). A `channel_type` guard (in `_one`, `:30-31`) rejects anything but 0/1 (closes a silent-misroute path).

**Every return additionally carries mel-DER and mel-EDI** (`_with_mel_edi`, `:62-118`) — the ADR-0006 output contract, not an optional extra:

- `mel_edi` — CIE S 026 mel-EDI, obtained from `melanopic_lux` via the **per-channel-type D65 ratio** `_d65_ratio` (`:17-27`, memoized in `_D65_MEL_PHOT_RATIO`, `:14`), *not* a fixed 1.169 or 1.103 constant. This is the quantity every circadian standard is written in; `melanopic_lux` is larger (≈1.0997× on the 9-bin route) and substituting it silently relaxes any threshold.
- `mel_der` — **always the spectrum AT THE POINT, never at the lamp**, plus `mel_der_source` recording which of three routes produced it:
  - `spd_transported` — a source `spd` was supplied, so `spectral_metrics.mel_der_transported` (§2.1) keeps the source's within-bin detail and recovers the per-bin transport from the channels. Comes with `source_mel_der` (the luminaire's own figure, i.e. what a datasheet quotes) and `transport_ratio` between them. **A datasheet mel-DER will not match `mel_der`, and that is correct** — the room is entitled to disagree with the lamp.
  - `binned_channels` — no `spd`; inferred from channel averages alone, carrying `_BINNED_NOTE` (`:46-52`): exact for D65, ~1.5% for smooth spectra, up to ~8% high on narrow-band sources.
  - `spd_source_untransported` — a dark point, where transport cannot be recovered; the source value is returned, labelled, via `_UNTRANSPORTED_NOTE` (`:54-59`).

The `spd=` parameter is the *source* spectrum feeding these channels, not the answer. See §2.1 for the transport math and ADR-0006 for the rationale.

### 1.5 The α-opic suite (`alpha_opic.py`) — the most scrutinized module

> **Source:** CIE S 026/E:2018 (α-opic irradiance E_α, photopic illuminance E_v, ELR, K^D65, EDI; H-5…H-9, H-11).

**Two entry points.** The channel path (bin reconstruction) and the gold-standard exact-from-SPD path.

**The §9.3a float-division fix (CONFIRMED, `:53`):**

```
intensity = (179.0/683.0) · (1.0/107.0) · channel   = 0.0024493370 · channel
```

The float literals matter: the bare `(179/683)*(1/107)` under integer division evaluates to `0·0 = 0`, **zeroing every α-opic output** — the float form preserves the intended CIE S 026 computation. The reconstruction (`_reconstruct_irradiance`, `:37-59`) spreads each channel **flat across its bin** (`irrad += [intensity[i]]*(hi-lo)`, then append the 780-nm point → 401 values). The same reconstruction is re-exposed publicly as `irradiance_per_nm` (`:61-69`) for the annual→nvRD bridge's `faithful` reconstruction, delegating to the private function so the two never diverge.

> **Grounding gap:** The `(179/683)·(1/107)` scalar (H-10) has no published derivation; appears only in `melanopic_calcs.bas:40`; treat as implementation lineage. It cancels exactly in **ELR** (the ratio E_α/E_v, where both sides carry it) and in ratios of two **same-path** EDIs, but it does **NOT** cancel in absolute E_α, in **absolute EDI/mel-EDI**, or in the nonlinear nvRD sigmoid — so absolute channel-path E_α, mel-EDI and R_D are unvalidated. Use the SPD path (H-5) for absolute irradiance.
>
> ⚠️ **Why EDI does not cancel** (the module docstring states this at `alpha_opic.py:11-15`; earlier revisions of this line said "cancels in ELR and EDI" and were wrong). `EDI = E_α·1000 / K_α^D65`, and `K_α^D65` is recomputed **only from the fixed D65 spectrum** (`:79`) — it is source-independent and therefore carries no `1/107`. The constant survives in the numerator alone, so EDI is directly proportional to it. Verified by execution: scaling the channel vector ×10 leaves ELR at 1.2013 (ratio exactly 1.0) while EDI moves 161.96 → 1619.64 (ratio 10.0). The same factor is the observable footprint in the §2.4 validation check: exact-vs-channel mel-EDI is 7.22e6 vs 1.75e4 (≈412×, i.e. 99.757 % divergence) while the constant-independent ELR ratio agrees to **0.625 %**.

**The §9.3b bin-ordering fix (CONFIRMED, `:52`):** for 3-channel, input `[r,g,b]` is reordered to `[b,g,r]` and paired with **ascending** `_BINS_3_ASC` (= `BINS_3_ASC` from `data.py`, `= [[380,499],[499,587],[587,780]]`). A descending-bin vector indexed against ascending action arrays would integrate the *red* channel against the *blue* end of each action spectrum; this implementation aligns each channel to its true wavelength range. **Consequence:** 3-channel α-opic output *intentionally differs* from the naive descending-order result (this implementation is the correct side; the 9-channel path is unaffected). 3-channel is supported but flagged approximate; **9-channel recommended.**

**The CIE S 026 integrals** (`_from_irradiance_pure`, `:71-81`, DL=1 nm), per CIE S 026/E:2018:

```
E_alpha = Σ irrad·action·DL                         α-opic irradiance
E_v     = 683 · Σ irrad·V_LAMBDA·DL                 photopic illuminance (lx)
ELR     = (E_alpha / E_v) · 1000        (mW/lm)     α-opic efficacy of luminous radiation
K_D65   = (Σ D65·action / (683·Σ D65·V)) · 1000     the D65 reference α-opic ELR (one per action)
EDI     = (E_alpha · 1000) / K_D65      (lx)        α-opic Equivalent Daylight (D65) Illuminance
```

Each result is rounded (`E_alpha` 6 dp, `ELR`/`EDI` 4 dp). `_from_irradiance` (`:84-102`) is a thin dispatcher: it uses a **numpy fast-path** (`np.dot`) when numpy is importable and falls back to the pure-Python `_from_irradiance_pure` reference otherwise; both apply the same rounding, which absorbs sub-ULP `np.dot`-vs-`sum` differences, so results are parity-identical. numpy is a hard transitive dependency (via colour-science) so the fast-path is normally taken; the pure-Python version remains the source of truth.

`alpha_opic_from_channels` (`:104-114`) drives the reconstruction path (α=None → all five selectors keyed by name). `alpha_opic_from_spd` (`:116-125`) skips reconstruction entirely (real per-nm SPD → integrals), so there is **no 1/107 and absolute E_alpha is meaningful**. This is the validation reference and a genuine capability extending the channel-path approach.

## 2. Spectral extras — `hcl_core/{spectral_metrics,presets,luminaire,validation}.py`

### 2.1 `spectral_metrics.py` (uses `colour-science`)

> **Source:** Ohno 2013, *Practical Use and Calculation of CCT and Duv*, LEUKOS **10**:47 (CCT/Duv inversion) — realized via `colour-science` library (Mansencal et al.).
> **Source:** CIE S 026/E:2018 (mel-DER = melanopic ELR / D65 melanopic ELR, H-11).
> **Source:** *Human-Centric Lighting: Foundational Considerations and a Five-Step Design Process*, Eq. 3 (EML = 1.103 · mel-EDI, H-12).

- **`cct_duv(spd)`** (`spectral_metrics.py:13-20`): SPD → CIE 1931 XYZ (2° CMFs via colour-science) → CIE 1960 UCS (u,v) → **CCT + Duv per Ohno 2013**. Realized via `colour-science`. Verified live: D65 → 6502.7 K (Duv +0.0032, correctly above the Planckian locus), A → 2855.7 K (Duv ≈ 0). CMFs come from the library, not embedded.
- **`mel_der(spd)`** (`spectral_metrics.py:27-33`): melanopic ELR ÷ D65 melanopic ELR = **1.0 for D65 by definition** (validation anchor, CIE S 026:2018 H-11). Scale-invariant. Rounded to 4 dp. Warm→cool ordering verified live (A 0.4958 < D50 0.8474; LED_3000K 0.5699 < LED_5000K 0.8181).
- **`mel_der_transported(spd, channels, channel_type)`** (`spectral_metrics.py:54-101`) — **the ADR-0006 core**, and the reason `mel_der` is a point quantity rather than a lamp quantity. mel-DER is a property of the spectrum where the observer is; `mel_der(spd)` reports the *luminaire* and is right only while the room is spectrally neutral, while the binned channels lose the source's within-bin structure (up to ~8% high on a narrow-band fluorescent). Neither is what a sensor at that point would read. The engine models transport at bin resolution — it bins the source, bins each material, multiplies per channel — so the transport it actually applied is recoverable exactly:

  ```
  T_i = channels_i / bin_average(spd)_i        (T_i = 0 where the source does not emit)
  mel-DER_point = [ Σ S(λ)·T_bin(λ)·s_mel(λ) / (683·Σ S(λ)·T_bin(λ)·V(λ)) × 1000 ] / K^D65_mel
  ```

  keeping the source's full 1-nm structure while applying the simulation's own per-bin transport. `_bin_of` (`:42-51`, memoized in `_BIN_OF`, `:39`) is the λ→bin index map. **Scale-invariant in both arguments** (the channels'/SPD's arbitrary unit ratio cancels in the mel÷photopic ratio) and **reduces exactly to `mel_der(spd)` when every `T_i` is equal** — so supplying a source SPD purely for source characterisation is unaffected. Returns **`None`** (never a fabricated number) when no band carries usable light: a dark point, or an all-negative channel row, drives the denominator to zero, and the caller falls back to a labelled value. Raises `ValueError` when `len(channels)` disagrees with the bin count for `channel_type`.
- **`mel_photopic_ratio(spd)`** (`spectral_metrics.py:104-111`): raw spectral-shape indicator `Σ(SPD·mel)/Σ(SPD·V)` on peak-normalized action curves (D65 ≈ 0.9058, verified). The docstring explicitly warns this is **NOT** mel-EDI/lux and **NOT** mel-DER (a name that invites a "D65 is 9% melanopic-deficient" misread).
- **`eml_medi_convert(value, direction)`** (`spectral_metrics.py:113-119`): `EML = mel_EDI × EML_PER_MEDI` (= 1.103) and inverse, selected by `direction ∈ {"medi_to_eml","eml_to_medi"}` (raises `ValueError` otherwise); H-12, Five-Step HCL Eq. 3.

> **Exact-from-SPD path** (`spectral_metrics.py:168-`): `alpha_opic_from_spd(spd)` is a thin reshaping wrapper over the verified `hcl_core.alpha_opic.alpha_opic_from_spd` exact path (renamed via the `EDI_NAME` map at `:131` to a flat `{s_edi,m_edi,l_edi,rhod_edi,mel_edi}` dict) — it is the "ground truth" the validation §5.10 divergence check compares the 9-channel reconstruction against, using the same CIE S 026 K^D65 normalization so any divergence is attributable to channel reconstruction, not differing constants.

> **⚠️ The scale heuristic is a HINT, not a determination** (`_RELATIVE_PEAK_MAX` = 1.5 at `:136`, `_SCALE_WARNING` at `:147-153`, `spd_looks_relative`/`scale_warning_for` at `:156-166`). A per-nm peak **cannot** separate absolute from normalised: real daylight at 1 nm spreads its energy over ~400 bands, so genuinely **absolute** readings sit near 0.1–0.4 W/m²/nm — *below* this threshold. Absolute exterior daylight readings peak around 0.004–0.41 and would all be flagged: a 100% false-positive rate on genuinely absolute data. Integrated irradiance does not separate them either (that set integrates to 1–139 W/m², overlapping a normalised spectrum). The emitted warning therefore reports that the scale is **INDETERMINATE from the values alone** — consistent with both a normalised and a genuinely absolute spectrum — and states that if the input *is* absolute the `*_edi` values are correct lux-scale EDIs. It must never assert the input is relative or that the EDIs are unusable: on correct absolute data that tells the user to discard a correct answer. The scale-invariant metrics (mel-DER, CCT, α-opic ratios) are unaffected either way.

### 2.2 `presets.py` — illuminant SPDs

### 2.3 `luminaire.py`

### 4.1a A1 candela-scale integrity — `hcl_radiance/source_cal.py`

> **Source:** Radiance `source.cal` / `ies2rad` `brightdata`. Root-caused on a local Radiance 6.1a build, 2026-07-18.

`ies2rad` writes an IES file's candela scale into the scene as the `brightdata` argument **`A1`**, and `source.cal`'s `corr`/`flatcorr` apply it. Some builds resolve those to a compiled built-in `source_corr` that **ignores `A1`**, so every IES luminaire emits at unit scale. The failure is silent and severe: a 4×L09 `office_room` grid read **34 lx where it should read 494 lx**, and `glare_ugr` returned **UGR 0** — not a low number but a *clean* one, because the sources fell below `evalglare`'s detection threshold. ⚠️ **The factor is the luminaire's own candela scale, so it differs per fixture — 14.4× for the Glamox L09, 2.068× for the Ludwig Leuchten 2722-001. Affected results must be RE-RUN, never rescaled.** Sky paths (`gensky`/`gendaymtx`) never reference `A1` and are unaffected. **This is not an hcl-mcp defect** — the electric pipeline is correct given a Radiance that honours `A1`; do **not** fold `A1` into `color_luminaire`, which would double-scale on a stock build.

**Two detection layers, because either alone is insufficient.** `inspect_source_cal(path)` is a pure text read (no Radiance, always runs): it strips Radiance `{ }` comments — *load-bearing*, since the unpatched file carries the correct `A1*v` formulas **inside a comment block**, so a naive `grep A1` classifies the broken file as healthy — accumulates each `corr`/`flatcorr` definition to its terminating `;` (multi-line definitions would otherwise be misread as defective, failing in the one direction that raises a false alarm on a good install), and takes the **last** definition, which is how Radiance resolves and how the shim works. `probe_a1_honored(work_dir, raypath=)` measures instead of reading: it renders one luminaire twice with `A1` differing 10×. Honoured → ratio 10; dropped → ratio 1; nothing lands between, hence the `> 5.0` threshold. The probe is the only layer that can catch this defect, since it lives in the *compiled* `source_corr` rather than in the text. `check_a1()` runs both and the probe wins on disagreement. **All three report `a1_honored=None` — never `False` — when no verdict is reachable**, so an unreadable install is "unknown", never "broken" and never a pass.

**The correction is a RAYPATH shim, not a patched install.** `write_shim(dir)` copies the installation's `source.cal` and appends the explicit `corr`/`flatcorr`/`boxcorr`/`lboxcorr`/`cylcorr` formulas (byte-equivalent to `scripts/live_validation_phase2/source_cal_A1_fix.append`); the directory goes first on `RAYPATH`, which Radiance resolves ahead of the system copy. Nothing in the Radiance installation is written, so **no `sudo` is needed** and reverting means deleting a directory. ⚠️ **`write_shim` RAISES rather than writing an overrides-only file** when the base cannot be found or lacks `src_theta`: `RAYPATH` takes the *first* `source.cal`, not the union, so a partial file would shadow the real one and remove every other definition — `rtrace: src_theta: undefined variable`, i.e. no scene renders at all, which is strictly worse than the wrong-but-plausible numbers the defect produces. The system lib also stays *on* `RAYPATH` behind the shim, since `rayinit.cal` still loads from the installation.

**Opt-in, off by default** (`shim_raypath`): `HCL_RADIANCE_SHIM=1` enables it for every run, wired through `runner.run_sequence` → `proc.run_sequence(env_extra=)` so it reaches the actual subprocess environment (execution only — emitted commands stay portable, and `env_extra=None` is a verified no-op on the shared Daysim path). A silent always-on override is deliberately avoided: it would make two machines disagree about what the same scene means. `grid.engine_provenance(work_dir)` stamps `engine.source_cal` onto results from **both** luminaire-rendering paths — `run_grid` (grid.py) and `run_image`/`glare_ugr` (image.py) — which is what the advisory keys off. **Live-verified end-to-end:** defective build ratio 1.0 → shim applied ratio 10.0, system `source.cal` untouched.


`run_sequence` (the real executor lives in `hcl_core/proc.py:87`; `runner.py:11` is a thin re-export wrapper) is the **only subprocess executor**. On `available=False` it returns `{ran:False, commands:[exact ordered shell lines], reason, outputs}` — the hybrid run/emit contract. `render` (`hcl_core/proc.py:22`) `shlex.quote`s tokens except a literal `|` pipe and appends `< stdin` / `> stdout` (or `>>` when `append`) redirects (the RGB-from-HDR pcomb `-e` expression carries `;()*`, which produces `bash: syntax error` unless quoted). A step runs as one shell line when it sets `shell=True` or carries a `|` token; an optional per-step `timeout` (seconds) returns `returncode 124` on `TimeoutExpired`, an **`OSError` (the command could not be STARTED at all — missing binary, not executable, bad interpreter) is caught and returned as `returncode 127`** rather than escaping as a raw traceback through the MCP layer (reachable on a partial Radiance install, since `available` gates only on oconv+rtrace and then rpict/pcomb/gendaymtx are absent), and `path_prepend` prepends dirs to `PATH` **for execution only** (emitted commands stay bare-name/portable — used so `HCL_DAYSIM_BIN` binaries off `PATH` resolve at run time). `parse_rtrace_res` (`runner.py:18`) takes the first three numeric columns per non-empty line, skipping any header/non-numeric lines.

**Pure command builders** (`commands.py`, no execution): `build_oconv` (`oconv -f <files…>`, materials/sky ordered before geometry), `build_rtrace` (per-point irradiance, flags below), and `pts_to_text` (points → Radiance text). `DEFAULT_RTRACE_PARAMS = "-ab 2 -ad 512 -as 256 -aa 0.1 -ar 64 -lw 0.001"` (`commands.py:8`) are **the toolkit's chosen irradiance defaults, not inherited from any upstream reference** — and ==caller==s override via `rad_params`.

### 4.2 Colored Perez sky/sun (`sky.py`)

> **Source:** Perez et al. 1990/1993, all-weather sky luminance/radiance model (embedded in Radiance `gendaylit`) — model lives inside Radiance.

Built around `gendaylit` (Radiance Perez all-weather sky). Geographic/time conventions (`build_gendaylit:45`, meridian `:64`, `lon_w` `:65`): `meridian = int(UTC·−15)`; `lon` is **standard signed / east-positive** (Seattle = `−122.3`, Athens = `23.73`, matching raw EPW and typical geographic coordinates), negated internally (`lon·−1`) to gendaylit's west-positive `-o`; latitude +north. `-W` = direct-normal + diffuse-horizontal; `-E` = global horizontal.

> **Irradiance-argument guards (both `build_gendaylit` and `build_gendaylit_luminance`).** `irrad_mode="W"` raises `ValueError` unless **both** `direct` and `diffuse` are supplied, and `"E"` raises unless `globl` is — checked **before** `str()` can turn a `None` into the literal string `"None"`. gendaylit *accepts* `"None"` as an irradiance, computes a zero-energy sky and emits no solar primitive at all, so the slip would otherwise surface much later as `find_solar_line`'s "no solar RGB line" — a message pointing at the parser and saying nothing about the missing argument. Found live 2026-08-06; `direct`/`diffuse` are **separate parameters from `direct_channels`/`diffuse_channels`** (which carry spectral shape only — gendaylit needs the broadband magnitudes to place the sun), which is what makes omitting them an easy mistake. *(Note: `import_weather`'s explicit `longitude` override uses the opposite, west-positive, sign — it feeds the Daysim `.wea` path directly, which is west-positive; the auto path derives it from the EPW so callers rarely pass it there.)*

**Solar position — two forms (`_solar_position_args`, `sky.py:25-43`).** By default the command is the date/time form and **gendaylit's own ephemeris** derives the sun from `month day hour` + `-a/-o/-m`, reading `hour` as a **wall-clock instant**. Supplying `sun_zenith_deg` **and** `sun_azimuth_deg` (both or neither — either alone raises) instead emits `gendaylit -ang <altitude> <azimuth>`, which bypasses that ephemeris. `-a/-o/-m` are then dropped: gendaylit ignores them under `-ang` (verified byte-identical output), so emitting them would imply a dependency that is not there. Conventions are taken **verbatim from a `SpectralSkyRecord`'s `geometry` block** so the caller does no arithmetic — `zenith_deg` → altitude `90 − z`; `azimuth_deg` (clockwise from **North**) → gendaylit azimuth `az − 180` (gendaylit measures from **South**, positive toward **West**; verified live — `gendaylit -ang 50.9511 -13.135` reproduces the date-form sun vector to within 0.002 in direction cosines). `-ang` composes with both `-C` and `-E`, and leaves the output structurally identical (19 lines), so `find_solar_line`/`assemble_sky_def` are unaffected — they anchor on the `light solar` primitive, not a line position.

> **Why this exists.** `build_gendaylit` never applies an EPW hour-ending → mid-interval (`hour − 0.5`) conversion; that is the orchestrator's job (`spectral_pipeline.py:43`, §5), and this function's `hour` may legitimately be a wall-clock time. But `spectral_sky_from_epw`'s `hour` is an **EPW hour-ENDING label** whose geometry is evaluated at the mid-interval instant. Passing the same integer to both therefore left the record's spectrum and the traced sky **half an hour apart — 7.5° of diurnal arc** — with nothing raised: the spectral shape was computed for one sun position while the beam was traced from another. Threading `sun_zenith_deg`/`sun_azimuth_deg` closes it *by construction* rather than by the two ephemerides happening to agree (they agree to 0.05° in altitude, 0.135° in azimuth, but that is a coincidence of implementation, not a guarantee). Default behaviour is unchanged.

**Sky-glow per-channel normalization** (`sky_glow:129-137`): `sky_mat_i = C_i / Σ_j(v_j·C_j)` — each diffuse channel divided by the photopic-weighted diffuse sum, emitted as `skyfunc glow sky_mat … 4 <vals> 0`. Recomputed golden: `[0.8,0.9,0.85]→0.92 1.03 0.98` (green >1.0 is correct, photopic sum <1).

**Solar coloring — the mean-RGB coefficient** (`scale_solar:115-127`):

- **3-channel:** `coef = mean(solar RGB) / Σ(direct·W_PHOTOPIC_3)` (`:119`), emitted as one solar line.
- **9-channel:** the **same** `coef = mean(solar RGB) / Σ(direct·W_PHOTOPIC_9)` (`:122`) — identical mean-of-RGB numerator to the 3-channel path; the only difference is that 9-channel emits three solar lines (a/b/c). The coefficient is **NOT** channel-count-dependent. *(the code now uses the mean of RGB in both paths, so 3ch and 9ch scale the sun identically.)*

`_SKY_TAIL` (spectra mode, `sky.py:11-15`) uses a grey ground glow `1 1 1`. A `luminance` mode (`-C`, 3-channel only; `colored_sky_luminance`) defers coloring to Radiance's built-in chromaticity and is **pure-emit** — it embeds `!gendaylit … -C …` inline and returns `{ran:False, files, sky_defs}` with no Radiance run. Its separate tail `_SKY_TAIL_LUMINANCE` (`sky.py:59`) retains the warm `1 0.8 0.5` ground glow.

### 4.3 Grid pipeline & recombination (`grid.py`)

> **Source:** Inanici, Brennan & Clark 2015, §3 (per-channel Radiance pipeline + 9-channel concatenation).

Per channel-set: oconv → rtrace (`-I+ -h- -ov`, irradiance at point; the `-h+`→`-h-` and `-oV`→`-ov` remove spurious warnings — see `build_rtrace` in `commands.py:157`). `_recombine` (`:422`) concatenates set-major/RGB-minor: 9-channel → `[s0R,s0G,s0B, s1…, s2…] = [b1,b2,b3, g1,g2,g3, r1,r2,r3]`; pinned by an asymmetric CI test. **Live-verified:** both 3ch and 9ch reproduce `562.345 lux = 179 × π`. Before recombining, `run_grid` **asserts every channel set returned the same number of sensor rows** and raises a `ValueError` naming the offending `.res` files when they disagree: `parse_rtrace_res` drops any line whose first three tokens are not numeric — right for a stray `rtrace: warning` on stdout, but it lets one set come back short, after which point *p* silently took a **later** point's value (a wrong melanopic number, reported with full confidence) until the ragged tail raised a bare `IndexError` naming neither the file nor the mismatch.

`_recombine` forwards a `spd=` to `circadian_metrics` for the **electric block only** — `_sole_electric_spd` (`:134`) returns the one spectrum every driven luminaire shares, or `None` when they differ. That SPD is the **source** spectrum, not the answer: `circadian_metrics` recovers the room's per-bin transport from the channels and reports mel-DER at the point (`spd_transported`, plus `source_mel_der`/`transport_ratio` — ADR-0006, §"Output contract" in the methodology). The `daylight` and `combined` blocks pass no SPD and stay on the binned route, correctly: a daylit sensor's spectrum is the sky record (not held here) and a combined block is a two-source mixture whose ratio varies per point, so neither has a single source spectrum to hand. `_sole_electric_spd` compares the luminaires' spectra **pairwise, not through a `set`** — an inline SPD arrives as `[[nm, value], …]`, the only shape JSON carries, and a list is unhashable, so building a set took the whole run down with `TypeError`.

**Electric-lights integration** (reported exactly as built):

1. `ies2rad -m <multiplier·maintenance_factor> [-c R G B] [-t lamp] -dm[/divisor] -o <name> <ies>` → writes `<name>.rad`+`.dat` directly (no stdout redirect). **Critical:** `-m` carries USER scaling only (`multiplier·maintenance_factor`); the IES `candela_multiplier/ballast_factor/pfactor` are applied by ies2rad internally (`mult = -m · mult · bfactor · pfactor`) — folding them into `-m` would square them. `units=2`→`-dm` (meters), `units=1`→`-df` (feet).
2. **Colorize** reads the ies2rad `.rad`, swaps the `3 1 1 1` light line for the spectral triplet (`color_luminaire`), writes `_colored.rad`, then `place_luminaires` wraps it in **`!xform`** lines (the leading `!` makes it an inline Radiance command; a bare `xform` is invalid scene input → `undefined modifier "xform"`). SPD/preset channel vectors are luminance-normalized (`_normalize_luminance:115`, `dot(W_PHOTOPIC, channels)==dot(W_PHOTOPIC, [1]*n)`) so ies2rad's baked photometric output is preserved and only the spectral shape is imposed (a relative peak-1 SPD would otherwise collapse the electric contribution ~100×).
3. Builds **electric-only** (sky dropped) and **combined** octrees. Sky exclusion goes through `_select_non_sky`: a non-empty explicit `sky_files` argument (exact path membership) is **authoritative** and used alone — the escape hatch in both directions, naming a sky nothing would detect *or* keeping a sky-looking file (exterior context) inside the electric octree. It is exposed on the MCP `run_grid` signature. When `sky_files` is `None`/empty, `_is_sky_file` decides by **content first**: `_has_sky_primitives` reads up to 64 kB and matches gensky/gendaylit as words (covering `!gendaylit …`, a bare command, and the `# gensky …` comment header gensky itself writes), `skyfunc` (whether *defined* by gensky as `void brightfunc skyfunc` or used as a modifier), `source sky`/`source ground`, `light solar`, and `skybright`/`perezlum.cal`. The basename is OR'd in as a fallback hint for files that cannot be read (the emit path), as a **plain substring** — `sky.rad`, `clear_sky.rad`, `skydome.rad`, `clearsky.rad`; still not `whiskey.rad`; directory names ignored.

   > **This is a detector, not a guarantee.** Its predecessor was a basename word-boundary regex, `r"(^\|[^a-z])sky([^a-z]\|$)"` compiled `IGNORECASE` — which makes `[^a-z]` exclude letters of *both* cases, so every name with a letter beside `sky` slipped through (`skydome.rad`, `clearsky.rad`), while the docstring claimed sky "can never leak". One leak reported **17705 lx where the true electric-only value was 1662 lx**, silently. Any boundary rule merely relocates that edge, which is why detection is content-first and the basename fallback has no boundary at all. A hand-rolled sky using none of these primitives, under a name with no "sky" in it, will still reach the electric octree — that is what `sky_files` is for. See ADR-0007.
   >
   > The `electric` block therefore also carries **`lumen_bound`** (`_lumen_bound`): `Σ(luminaire total_flux · multiplier · maintenance_factor · instance_count) / (sensor-grid bounding box)`, with `exceeded`. `total_flux` (integrated zonal flux — what enters the room) is used over `rated_lumens` where the photometric type supports it. The area understates the floor, so the ceiling is generous and the check errs toward silence; it bounds the **mean**, never a single point. `ELECTRIC_EXCEEDS_LUMEN_BOUND` (severity `error`) reports it. Returns `None` — no key — when no lumens resolve or the grid is degenerate, so a bound nobody could compute is never reported as one that passed.

`_run_with_colorize` (`:507`) is an order-preserving executor: a colorize reads the `.rad` its preceding ies2rad writes, so on the run path it flushes buffered commands at each colorize boundary (forcing ies2rad to produce its `.rad`), then colorizes, then continues. On the emit path a flat-white stub `.rad` is written so the placed-`.rad` inputs exist and the emitted command list stays honest. `_luminaire_wattage` reads an explicit `wattage`, else the IES input-watts field, else `0.0`; `total_wattage = Σ(wattage · count)` where `count` defaults to the placement instance count.

### 4.4 Image / FOV (`image.py`, `image_commands.py`, `masks.py`)

> **Source:** Khademagha et al. **2018/2016** (Meas. Sci. Technol. **29**(8):085902 + 2016 *Build. Environ.* review) — ipRGC FOV weighting regions {upper_inner:2.06, upper_outer:1.37, lower_inner:0.34, lower_outer:0.23}. (A prior "2021" attribution was a year slip; corrected repo-wide.)

`build_rpict` default `-vta -vh 180 -vv 180` (angular fisheye), 800×800 (`image_commands.py:11`; `run_image` default `rad_params="-ab 2 -ad 512 -aa 0.1 -ar 64"`). The pcomb action-curve maps (`_pcomb_map`) are a **numerically-equivalent single-pass refactor** of a multi-pass pcomb chain — coefficients stored as **exact decimal strings** so the neuropic `0.000069431` (`image_commands.py:31`) renders verbatim (a float would emit `6.9431e-05`). **FOV weighting** (Khademagha et al. 2018/2016) uses regional weights `_FOV = {upper_inner:2.06, upper_outer:1.37, lower_inner:0.34, lower_outer:0.23}` (`image_commands.py:38`) via a masked threshold-multiply (`fov_pcomb_steps`). Masks are resized with `pfilt -1 -x -y` (`masks.py:15-29`; shipped Khademagha masks are 512px, renders default 800px, and pcomb errors on mismatch). A synthesize-from-angular-position fallback (`synthesize_fov_masks_steps`, upper/lower split at the meridian, inner/outer at `inner_deg=30°`) exists but is flagged "**not publication-grade** — replace with the validated Khademagha masks." **RGB-from-HDR** (`rgb_from_hdr_steps`) is the cosine-weighted eye-irradiance pipeline (`vwright -vf` → pcomb `dot=Dx·Vdx+Dy·Vdy+Dz·Vdz` → `pvalue -h -H -df | total -if3`).

**Critical 9-channel semantics** (`image.py` docstring `:44-49`): for 9ch, the eye source is the **melanopic** luminance map (`pcomb_melanopic_map`), so `rgb.txt` is *already* melanopic-weighted eye irradiance → ×179 for mel-EDI, sent to compliance directly; do NOT re-run `circadian_metrics` (would double-count). For 3ch, `rgb.txt` is raw cosine-weighted RGB → feeds `circadian_metrics(channel_type=0)`. Glare (`evalglare`) runs on the combined HDR; for 9ch it uses `combined0.hdr` (the 'a'/blue-bin scene) as the luminance source and is noted as approximate.

> **Status / how to read FOV output.** `run_image` defaults `fov_weighting=False`, whose `rgb_from_hdr_steps` output is **cosine-weighted corneal-vertical eye irradiance — the standards-aligned quantity** (WELL/CIE S 026/iNSOM define the 250 lx target on *this*, not on the retinally-weighted value). FOV weighting is therefore a **non-thresholded opt-in companion**: read it comparatively (gaze-vs-gaze, source-vs-source), never against 250 lx (category error). The **faithful** path (four shipped Khademagha masks) is **live-run** — a companion study drove all four observers through this exact `fov_pcomb` pipeline (masks confirmed by `runs3_gaze/verify_khademagha.py`) and frames it as **Rung 3** of a cosine-vertical-default / multi-view-sweep / FOV-companion metric ladder (methodology §12bis.2). The *synthesized* fallback masks remain not-publication-grade.

### 4.5 OBJ/CAD geometry import (`geometry_import.py`)

> **Source:** Wavefront `.obj` geometry format; Radiance `obj2rad`/`xform` (Ward / LBNL) — conversion lives inside Radiance.

`import_geometry` (`geometry_import.py:782`) ingests a Wavefront `.obj` + a per-group `material_map` and returns a per-channel Radiance scene that composes directly into `run_grid`/`run_annual` (`scene_sets = [[*mats, sky, geom] for mats, geom in zip(material_sets, geometry_set)]`). It follows the same **run-or-emit** discipline as the rest of `hcl_radiance`: material `.rad` and the `obj2rad` mapfiles are authored in pure Python on every path, only `obj2rad`/`xform` *execution* is gated (`_available()` probes both; `discover._REQUIRED` (`discover.py:20-22`) carries `obj2rad`+`xform`). The pure parsing/geometry logic (vertices, faces, normals, mesh quality, `.mtl` hints, markers) lives in a sibling `geometry_obj.py`; `geometry_import.py` is argv-builders + binding + orchestration + the extended features. `geometry_obj.py`'s `parse_obj` retains per-object (`o`) names alongside `g`-group names on each face, and exposes `object_centroid` for each named object — the anchor that the standalone sensor tools use for workstation seat/screen pairing.

- **Discovery** (`parse_obj_groups`): material names are the `usemtl` tokens in order, else the `g` group names (deduped, order-preserving). `validate_material_map` **hard-fails** with an `UnmappedGroupsError(ValueError)` naming every unmapped group; its `.payload` is the **same structured discovery report** `dry_run=True` returns (`groups`, `bbox_m`, `missing_normals`, `mesh_quality`, `.mtl` `suggestions`, `unmapped`), so the failure doubles as the discovery path — the honesty boundary (no silent generic material; the OBJ carries no spectral data). (A missing `units` does not mask the more actionable unmapped-groups error — a provisional `scale=1.0` feeds the discovery/error payload, and `units` is hard-required via `scale_factor(units)` only *after* the map checks pass.)
- **Per-channel binding** (`group_channels`/`build_material_sets`): scalar `refl`/`tvis` → flat `[v]*N` (N=3 for `channel_type=0`, 9 for `channel_type=1`); `spd` → `bin_average(parse_spd(…))`; glass → `write_material(material_type=0)`, plastic → `1`. `group_channels` **raises** if a non-SPD spec is missing its required scalar key (`tvis` for glass, else `refl`). The group-major `write_material` output is transposed into set-major `material_sets` (1 list for 3ch, 3 for 9ch), index-aligned with `geometry_set`.
- **Per-channel assembly** (`build_material_mapfile` + the `_SUFFIXES` loop, `_SUFFIXES = {0:[""], 1:["_a","_b","_c"]}`): one `obj2rad -m <mapfile>` run per channel-set, the mapfile assigning each group its suffixed modifier (`<group>_a/_b/_c`) so emitted modifiers match `write_material`'s. `xform` then applies `-s <factor>` (units→m) and `-rx 90` (`up_axis="Y"`→Z-up).
- **The `obj2rad` qualifier subtlety (live-confirmed).** `obj2rad`'s `-m` matches the `Material` qualifier **only** to `usemtl` names; a `g`-group name matches the `Group` qualifier. So `build_material_mapfile` emits `(Group "x")` for group-only OBJs and `(Material "x")` when `usemtl` is present (`obj_group_qualifier`); a **mixed** OBJ with faces obj2rad would drop (`obj_unmaterialized_faces > 0`) **hard-fails** rather than render partial geometry. A capability-gated test runs real `obj2rad` (Radiance 6.1a) and asserts a group-only OBJ emits polygons — the guard against the silent-empty-geometry class.
- **Extended import features.** Beyond the core OBJ→scene conversion, `import_geometry` supports the following (each output key appears only when its feature is mapped or requested); all bind through the existing channel machinery — **no new physics / no new equation**:
  - *Material ergonomics.* String `material_map` values resolve through `resolve_spec` (`geometry_import.py:541`) → `hcl_core/surface_library.py`, e.g. `{"walls":"painted_gypsum"}`; a `*.matmap.json` **sidecar** (`load_sidecar`, accepts both a wrapped `{"material_map":…}` and a bare top-level group map) supplies defaults (explicit kwargs always win); the wrapped/bare split plus metadata stripping lives in **`split_map_metadata`**, applied to the **inline `material_map=` argument too** (DEF-INLINE-MAP, 2026-07-23) — `_`-prefixed comment keys are dropped and `units`/`up_axis`/`north_angle_deg`/`channel_type` are absorbed only where the caller left them unset, so a caller can pass a sidecar's parsed contents straight in. Before that the strip lived inside the file loader alone, and an inline paste reached `resolve_spec` with `_README` as a spec, raising `KeyError: unknown surface "Pinned material map for …"` — the file's own comment quoted back as a material name. Anything left after the split is still a group spec, so a typo'd material still raises; the adjacent `.mtl` pre-fills `suggested_refl`/`map_kd` **hints only** (`parse_mtl`/`mtl_suggestions`, `suggested_refl = round(mean(Kd), 4)`, never a material value); `dry_run=True` returns the discovery payload (groups + `bbox_m` + `mesh_quality` + suggestions) as a success.
  - *Mesh preflight* (`mesh_quality` in `geometry_obj.py`): degenerate-face (<3 unique verts) / missing-normal / non-manifold-edge (edge used by >2 faces) counts + worst-offender group — **quantify, never repair**.
  - *Geometry-derived sensors* (`derive_sensors=True` → `derive_sensor_outputs`): a work-plane grid (floor → `floor_z + workplane_h`, default 0.8 m, footprint-clipped, up-facing `[x,y,z,0,0,1]`) — `floor_z` is the floor's **top** face (the walkable surface), the same datum `floor_top_z` and hence `workplane_grid`/`observer_points` use, so a modelled slab of non-zero thickness does not shift the derived heights and eye-level **observer** points gazing toward the mean glazing normal (`mean_aperture_normal`) — returns these as `observer_sets`, one per `eye_heights` entry (**default seated 1.2 m + standing 1.6 m**), each with its own `points` + DGP `glare_views`; flat `observer_points`/`glare_views` (all heights concatenated) remain for back-compat. `eye_heights`/`workplane_h`/`spacing` (defaults `(1.2, 1.6)`/`0.8`/`0.6`) are tunable (exposed on the MCP wrapper, `server.py:453-454`). All points share the geometry's final world frame.
    **Footprint clipping (`clip_to_footprint=True`, `footprint_border=0.0`).** `_world_footprint` returns the floor's full axis-aligned *extent*, so on a concave (L/T/U) plan the lattice covers the bounding box. Grid points **and** observers are therefore run through `footprint.clip_points` against `floor_polygons` in the pre-north frame, exactly as the standalone `workplane_grid`/`observer_points`/`photosensors` tools already do — this path was previously the only sensor producer that did **not** clip, and the points it left in an L-notch were not merely useless: the notch is open exterior (no floor, ceiling or walls), so they read **high** and inflated every unweighted spatial aggregate (sDA, DA_avg, UDI, ASE, and `df_min`, which sets DF uniformity from a single point). On `l_room.obj` at spacing 1.0 that was 9 of 36 grid points and 2 of 8 observers. Each dropped observer takes its paired DGP view with it, so `observer_points`/`glare_views` stay index-aligned; the counts surface as a `clipped{grid_kept,grid_dropped,observers_kept,observers_dropped,…}` block **and** as an import warning. Rectangular rooms are unaffected — `office_room.obj` at the default 0.6 spacing keeps all 84 points with 0 dropped (regression-guarded), so no published count moved. `footprint_border` insets uniformly from every real edge (use it when a floor slab runs under the walls).
  - *Georeferencing* (`north_angle_deg`): the final `xform` term `-rz (−north_angle_deg)` (post-remap frame, spec §3.1), threaded through **every** channel run; a single `_to_world`/`_rotate_north` is the one source of truth so sensors, apertures and luminaire markers all share the scene frame. A per-aperture **orientation report** (`aperture_report`) emits each glass group's area + **true-north** azimuth/tilt (azimuth `= atan2(nx, ny) mod 360`, 0=N/90=E), using the **area-weighted** mean normal over the group's faces (not just the first face).
  - *Ground ↔ sky bridge.* A `type:"ground"` group yields `ground_albedo` — a 1-nm (401-value) spectral albedo (`derive_ground_albedo`, area-weighted across ground groups, clamped to [0,1]; `ground_albedo_kind="spd"` from a real SPD via `parse_spd→to_grid_list`, else a flat scalar broadcast) — that drives the spectral ground-glow term via the `spectral_sky_from_epw(spectral_albedo=…)` override (`server.py:1642`; gray default unchanged when `None`, `len==401` validated at `server.py:1665`). So one reflectance colours both the scene polygon and the sky's ground reflection.
  - *Context.* A `type:"context"` group (`context_groups` in the result) is **exterior shading**: it still binds + enters the `obj2rad`/`oconv` octree (casts shadows), but `_context_groups` excludes it from the auto-sensor footprint (`_world_footprint` fallback) and the implausible-room bbox sanity check (`_noncontext_model_bbox`, fed as `sanity_bbox` into `_bbox_warnings`).
  - *Luminaires* (`type:"luminaire"`): OBJ `p`-primitive markers (or a group-face centroid fallback via `marker_positions`) → world-frame placement via `_to_world`. Assembles a **drop-in `electric_lights`** payload (`luminaire_electric_lights` → `{ies, placement:{positions}, spd/preset, multiplier, maintenance_factor, units…}`) that `run_grid`/`run_image` consume directly — they run `ies2rad`+colorize+`_luminaire_channels` downstream, so the importer adds no photometry. (The informational `result["luminaires"]` block via `luminaire_block` is retained.) Missing marker/`ies` → a warning, never a silent drop. Luminaire groups are excluded from `build_material_sets` (no geometry faces, no `refl`/`tvis`).
  - *Provenance & export.* `build_manifest` stamps source-SHA-256 + import params + bbox-in-meters + timestamp; writes it to a `manifest.json` **sidecar** (`manifest_path`) **and** embeds it as a `#`-comment provenance header in each geometry `.rad` (`_embed_manifest_header`, idempotent via a header marker, emit-safe via `os.path.exists`). `annotate=True` adds a material **summary** table (`material_summary`) and the colored-by-material `oconv→rpict→falsecolor` command plan (`annotate_steps`).
  - *Measured-SPD plumbing.* `surface_meta` reports `measured=True` **only** when a library entry carries a `source` citation **and** a readable `spd` file (`os.path.exists`); `resolve_spec` loads that SPD text so binding uses a real spectrum. The **shipped catalog stays illustrative scalars** (no fabricated measured data); the path is fixture-proven (`tests/fixtures/measured_demo.spd`).
  - *Surface catalog* (`hcl_core/surface_library.py`): the shipped `_CATALOG` is **8 named entries** — `painted_gypsum`/`white_ceiling`/`oak_floor`/`concrete` (`type:"plastic"`, `refl` 0.70/0.80/0.25/0.30), `clear_float_6mm`/`low_e_double` (`type:"glass"`, `tvis` 0.78/0.62), `grass_ground`/`asphalt_ground` (`type:"ground"`, `refl` 0.20/0.10) — each with a `family` (wall/ceiling/floor/glazing/ground) and `illustrative:True`. `surface_lookup(name)` returns a copy (KeyError on unknown), `surface_meta(name)` returns `{family, illustrative, measured, notes, source}`, and `list_surfaces()` enumerates names. Every shipped entry is a **scalar reflectance/transmittance starting value, not measured data** — `measured` is always `False` because no entry carries a `source`+`spd`; `resolve_spec` therefore flags each string-resolved group `illustrative` and `import_geometry` appends the "illustrative library reflectances (not measured)" warning.
  - **Live-validated:** **four** Radiance-6.1a tests pass — `obj2rad→xform→oconv→rtrace`, a north round-trip, an **IES-luminaire octree build** (the bug-prone live path; the placement references the `ies2rad -o <g>.rad` output, and `xform` takes an absolute intermediate path — Radiance searches RAYPATH by name, not cwd), and the **annotate** `oconv→rpict→falsecolor` recolor render (produces a valid `#?RADIANCE` `.hdr`).

### 4.5a Geometry health check (`geometry_health.py`)

> **Source:** no external source — pure Python over the same parsed-OBJ structures `geometry_import.py`/`geometry_obj.py` already build; needs no Radiance binaries and builds no scene.

`check_geometry_health` (`geometry_health.py:662`) audits a parsed OBJ + resolved `material_map` and returns a **report**, not a pass/fail gate: `{ok, counts, findings, checked, skipped, confidence}`, `ok = (error count == 0)`. Both tools that surface it may additionally carry an `advisories` entry (`GEOMETRY_HEALTH_UNCLEAN`, severity `error` when `ok` is false else `warn`) so an unread report still announces itself — note `skipped` is *never* empty by construction, so the rule keys on `ok`/`counts` and only names the skipped categories in its message. See §"Advisories" and `src/hcl_mcp/advisories.py`. It exists because a defective scene — coincident surfaces, a window with no opening cut in the wall — completes a full Radiance run and returns a plausible-looking number with nothing in the return value revealing the geometry was unsimulable. The MCP tool `check_geometry(obj_path, material_map, sidecar, units, up_axis, sensors, photosensors, electric_lights)` (`server.py:504`) exposes it standalone — `units` (from the argument or the sidecar) resolves to the `scale` the tolerances need, so it is load-bearing, not cosmetic; `import_geometry` calls the same function internally and embeds the report as `result["health"]`, plus a `strict: bool = False` kwarg (also on the MCP tool, `server.py:454`) that raises `GeometryHealthError` — a `ValueError` subclass whose `.payload` is the same report, mirroring `UnmappedGroupsError` — when the report holds any `error`-severity finding, rather than returning results built on defective geometry. **`check_geometry_health` never raises on any parseable OBJ** — a NaN or infinite coordinate used to reach a bare `ValueError: cannot convert float NaN to integer` out of the plane-key computation (surfacing through the `check_geometry` MCP tool as a hard failure instead of a report); non-finite coordinates are now a reported finding, and every geometric check skips faces that reference a non-finite vertex (`_face_is_finite`, `:27`) instead of crashing on them.

- **Severity contract** (module docstring, `geometry_health.py:6`): `error` — physically wrong or unsimulable, changes traced physics; `warning` — probably wrong, but legitimately valid in some models, never blocks; `info` — a fact worth seeing that no rule can decide. **Severity discipline:** an *inferential* check (one that guesses modeller intent from geometry, e.g. "this glazing face probably needed an opening") may never emit `error` — its ceiling is `warning`. `finding()` (`:52`) enforces the corollary in code: constructing an `error` or `warning` finding without a `fix` string raises `ValueError` — a finding the user cannot act on is not worth emitting. `NON_FINITE_COORDINATES` is `error` under this contract because a NaN/infinite vertex is not an inference — it is a fact about the model that Radiance genuinely cannot trace, so it changes traced physics outright; `NO_FLOOR_GROUP` stays `warning` because "no floor" is an inference about modeller intent, and the contract forbids an inferential check from emitting `error`.

> **Units (`scale=`, load-bearing).** Every tolerance in this module is an absolute physical quantity — 1 mm
> coincidence, 5 mm planarity, and a 2 m² ceiling on the end-cap containment exclusion. `check_geometry_health`
> therefore takes a `scale` (model units → metres, the same factor `import_geometry`'s `units` resolves) and
> converts vertices **once at entry** before any check runs; both call sites pass it, and `scale=1.0` is
> byte-identical to omitting it. Without it the constants silently changed meaning with the unit system, and it
> broke **both** ways: a real 0.5 mm z-fight in a millimetre model read as a 0.5-*unit* separation and was
> missed, while a legitimate 1 × 1 m end-cap read as 1e6 units² and blew past the 2 m² gate — producing a
> spurious `COINCIDENT_SURFACES` **error**, so `strict=True` refused to import a valid building. Related:
> `_plane_key` quantises the plane offset by `tol`, so a pair separated by almost exactly `tol` can straddle two
> buckets; faces register in both adjacent buckets (pairs de-duplicated) so unit-conversion round-off cannot
> decide whether a defect is caught. `face_area` still returns raw units² — it is used only for ratio and
> degeneracy tests, which are scale-invariant.

- **Tier-1 checks implemented** (`check_geometry_health`, `:662`, runs all eight unconditionally):
  - `NON_FINITE_COORDINATES` (**error**, `check_finite_coordinates`, `:592`) — one or more vertices have a NaN or infinite coordinate. Reachable from a plain-text OBJ, not just a contrived one: `v nan 0 0` parses directly, and `v 1e400 0 0` parses to `+inf` in both Python and the OBJ float grammar — a plausible exporter-overflow defect. `detail.vertices` reports the affected count. A non-finite vertex poisons every downstream float computation (Newell's-method normals, centroids, `round()` in `_plane_key`), which is why every other geometric check now skips a face that references one (`_face_is_finite`, `:27`) rather than tracing it.
  - `COINCIDENT_SURFACES` (**error**, `check_coincident_surfaces`, `:225`) — faces coplanar within `tol` (default 1 mm **of real-world length** — `check_geometry_health(scale=…)` converts vertices to metres first, so the tolerance means the same thing in an mm/cm/ft model; see the units note below) **and** with genuine positive-area overlap in the plane, not mere contact. The overlap/containment predicate (`_xy_extent_overlaps`, `:124`) deliberately excludes faces that only share an edge or corner, or whose footprint rests entirely inside another's (a wall's end-cap flush against a floor, an adjoining wall's full-depth face) — real building geometry tiles edge-to-edge constantly, and abutting/touching coplanar faces are **not** reported because faces that do not overlap cannot z-fight. What remains is a genuine stacked/crossing overlap, told apart from a rest/corner junction by an equal-vs-subset-but-not-equal test on each in-plane axis. Radiance resolves a ray hitting two coplanar surfaces non-deterministically, so the run completes with speckled output and illuminance that drifts between runs — that non-determinism is why this is `error`, not `warning`.
  - `WINDOW_WITHOUT_OPENING` (**error**, `check_window_without_opening`, `:470`) — a glazing face whose **centroid** sits inside an unbroken opaque (non-glass, non-context) face sharing its plane. Radiance traces the opaque surface, so the room renders dark (or nearly dark) while the run still completes and reports a plausible low daylight-autonomy number. This is a **centroid probe**, not full polygon clipping: a window that only *partially* overlaps an opaque face (centroid clear, but part of the glazing still covered) is missed. That miss direction is deliberate and safe for an `error`-severity check — a missed defect is recoverable by re-running the check after a fix; a false error on correct geometry is not — and the check targets the common, unambiguous defect (an exporter forgot to cut the opening at all), not partial-clip geometry.
  - `DUPLICATE_FACES` (**warning**, `check_duplicate_faces`, `:334`) — identical vertex sets (winding-invariant via `frozenset`). A doubled surface doubles its group's area, silently biasing aperture areas, ground-albedo weighting and facade selection.
  - `NON_PLANAR_FACE` (**warning**, `check_non_planar_faces`, `:366`) — polygon vertices deviating from their own best-fit (Newell-normal, centroid-anchored) plane by more than `tol` (default 5 mm of real-world length; `detail.worst_deviation_m` is in metres); Radiance `polygon` requires planarity and Newell's method silently area-averages a warped quad without complaint.
  - `NOT_ENCLOSED` (**warning**, `check_enclosure`, `:553`) — boundary edges (used by exactly one face, on non-`context` groups) — an open room that leaks light. `warning`, not `error`, because top-lit test cases, single-facade models and ground planes legitimately have open edges.
  - `DEGENERATE_FACES`, `NON_MANIFOLD_EDGES`, `NO_VERTEX_NORMALS` (all **warning**, `check_mesh_quality`, `:524`) — re-coded findings over the pre-existing `mesh_quality()` metrics (`geometry_obj.py`), now surfaced with a `fix` instead of raw counts only.
  - `NO_FLOOR_GROUP` (**warning**, `check_no_floor_group`, `:616`) — no group resolves to `type:"floor"`. Advisory, not a defect: floor-top height, the interior reference used to orient "inward" from the glazing, and sensor/observer heights all key off the floor group when one is typed, and fall back to an estimate (lowest horizontal face, or the centroid of non-context geometry) when none is. The estimate is usually right but is a guess about modeller intent, not a measurement, which is why the check is capped at `warning`.
- **`skipped` and `confidence` are always populated, never omitted.** Categories with no Tier-1 checks — `materials`, `apertures`, `conventions` (winding/north), and `sensors`/`luminaires` when their inputs aren't supplied — appear in `report["skipped"]` with a stated reason, so an absent category reads as "not checked yet," never as "checked, nothing wrong." `confidence["interior_reference"]` is explicitly `None` with a note that the interior-reference confidence used to downgrade findings on non-convex room plans is not computed in this tier.
- **Why no normals/winding check.** Radiance `polygon` primitives are **two-sided**, and this pipeline emits only `plastic` and `glass` materials — never a one-sided primitive — so surface-normal *direction* does not change traced results. A winding-consistency finding would therefore be a **convention** finding, not a physics one, and is out of scope for this tier (deferred to Tier 3 alongside `WINDING_INCONSISTENT`/`NORTH_ANGLE_UNSET`); `NO_VERTEX_NORMALS` above is the mesh-quality metric, not a winding check.
- **Deferred (Tiers 2–3, not implemented):** materials/spectral-integrity/luminaires (`REFL_OUT_OF_RANGE`, `GLAZING_TVIS_SUSPECT`, `SPD_*`, `IES_PHOTOMETRY_SUSPECT`, `LUMINAIRE_LOAD_IMPLAUSIBLE`, …); apertures/shading/conventions/sensors (`SHADING_*`, `WINDING_INCONSISTENT`, `NORTH_ANGLE_UNSET`, `GRID_SPACING_*`, `PHOTOSENSOR_*`, `SENSOR_INSIDE_SOLID`, …); `ROOM_HEIGHT_IMPLAUSIBLE`/`UNITS_SCALE_IMPLAUSIBLE`/`IMPLAUSIBLE_BBOX` re-coding (Tier 2, alongside the other plausibility checks).

### 4.6 Methodology-grade sensor placement — `hcl_radiance/sensor_methodology.py`

A pure-stdlib module (no Radiance call, always runs) that separates the sensor-placement math from the bundled `derive_sensors=True` shortcut in `import_geometry`. It is the back-end for the `workplane_grid` and `observer_points` tools (§10). **Six public helpers** — `floor_top_z`, `detect_interior`, `en12464_grid`, `detect_workstations`, `glazing_centroid`, `build_observers`. (`circadian_metrics` is **not** in this module; it lives in `hcl_core/metrics.py:120` — see §1.4.)


| Function                                              | Role                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `floor_top_z`                                         | Returns the highest world-Z of any face classified as floor — i.e. the top of the structural slab (the walkable surface) rather than a bbox extreme.`0.0` if no floor faces.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `detect_interior`                                     | Per-axis innermost-wall-face detection. For an axis-aligned wall every vertex shares that coordinate so `min == max` (a no-op); for a **leaning** wall it keeps the interior inside the wall's inner surface instead of extending out to its outer edge. Methodology carries `d_source`/`p_source`/`calc_area`/`n_cells`/`spacing`/`x_positions`/`y_positions`/`count`. Takes an optional `footprint`/`footprint_border` (geometry-sensor-placement feature): when a footprint (a list of XY polygon rings from `footprint.floor_polygons`) is supplied, cells are clipped via `footprint.clip_points` and the result carries a `clipped{kept,dropped,footprint_source,footprint_border}` block; `footprint=None` (the default when called directly) skips clipping entirely — fully backward-compatible. |

**Why per-axis innermost-wall-face, not vertex bbox or face-normal sign.** Two traps make the naive approaches unreliable. First, taking the bbox over the whole inward-facing *set* returns the *outer* shell — wrong by the wall thickness — because that set includes both faces of every wall. Second, face-normal sign follows OBJ winding order, which is model-dependent and unreliable for classifying inside vs. outside without additional context. The per-axis innermost-face design sidesteps both: it selects **one face per side** by centroid proximity to the room centre (winding-independent), then reads the room-facing extremum of *that face's* vertices — one number per side. Wall groups are those containing at least one vertical face whose height is ≥50% of the room height (`min_span = room_h * 0.5`); when room height is undetectable, every non-floor/non-glass/non-context group is treated as a wall. Room height comes from `_ceiling_z` (`:36`), which accepts a face as ceiling only at `nz > 0.8` and returns `None` when none qualifies — so a strongly sloped ceiling degrades the ≥50%-span wall rule to that fallback.

North rotation: all math is computed pre-north and the ==caller== (`server.py`) applies `_rotate_north` once — rotating both position and gaze — so sensors share the scene frame with the geometry.

A sibling pure-stdlib helper module, **`hcl_radiance/sensor_layout.py`**, supplies the lower-level geometry primitives used by the bundled `derive_sensors=True` path in `import_geometry` (`geometry_import.py`): `work_plane_grid` (up-facing `[x,y,z,0,0,1]` rows centred within a footprint bbox at the ==caller==-supplied `workplane_h`; default spacing 0.5 m), `eye_observer_points` (eye-level rows with a horizontal gaze direction; defaults `eye_h=1.2`, `toward=(0.0,-1.0)`, `spacing=2.0`), and `dgp_views` (the Radiance fisheye view-string builder: one `-vp .. -vd .. -vta -vh 180 -vv 180` view per observer) — no Radiance call, always runs.

**Concave (L/T/U) room support (geometry-sensor-placement feature, `workplane_grid` in `server.py`).** `detect_interior`'s per-axis innermost-wall-face rule is exact for rectangular and convex rooms, but on a concave room it can collapse to an inner sub-rectangle (or degenerate to zero/negative extent) because the "innermost face per side" model assumes one wall per side. `workplane_grid` now guards this: it computes the footprint bounding-box area (from `footprint.floor_polygons`) and trusts `detect_interior`'s result only when it has positive width **and** height **and** its area is ≥ `_INTERIOR_TRUST_RATIO` (0.6, `server.py:563`) of the footprint-bbox area. When the check fails, it falls back to the floor bounding box (inset by `wall_thickness` if given), sets `interior_extent_source="footprint_bbox"`, flags a warning, and still runs the grid through the footprint polygon clip in `en12464_grid` — so the lattice is laid over the full bbox and then trimmed to the true (possibly concave) floor outline. This is what makes an L/T/U room usable end-to-end: the rectangular office case is untouched (trust ratio passes, `interior_extent_source="inner_surface"`, byte-identical 45 points), while a concave room now gets a grid spanning every arm instead of collapsing to whichever sub-rectangle the wall-face heuristic happened to find. **Known limitation:** the EN border (`border_offset`) is still enforced only along the interior/footprint-bbox rectangle, not along concave (notch) walls — a grid can therefore sit closer than `border_offset` to a re-entrant corner; raising `footprint_border` insets uniformly from every real edge as a workaround. Live-verified: a rectangular office scene reproduces 45 points; an L-shaped room produces 48 kept / 16 dropped cells with both arms of the L covered.

### 4.6a Room footprint geometry — `hcl_radiance/footprint.py`

Pure-stdlib (no Radiance, no numpy), shared by `workplane_grid`, `observer_points`, `photosensors`, and `preview_scene`. Five functions:

- **`floor_polygons(parsed, material_map, scale, up_axis, north_angle_deg=None)`** — one XY ring per horizontal floor-group face (faces with `|nz| >= 0.5` after the up-axis remap; vertical floor-tagged trim faces are skipped). **Frame duality is the key design point:** called with `north_angle_deg=None` (the default) it returns rings in the **pre-north** frame — used by `workplane_grid`/`observer_points`/`photosensors`, whose internal math runs pre-north and applies `_rotate_north` once at the end. Called with an explicit `north_angle_deg` it projects each vertex into the **post-north final** frame directly — used by `scene_preview.build_scene` so the rendered floor outline lines up with already-rotated `.pts` files without a second rotation step.
- **`point_in_polygon(x, y, ring)`** — ray-cast point-in-polygon, but with an explicit boundary pass first: every edge is tested for exact collinearity (cross-product == 0) plus segment-bounds containment, so a point sitting exactly on a wall edge counts as **inside** (inclusive boundary) rather than being at the mercy of ray-cast's boundary ambiguity. Falls through to the standard ray-cast interior test for non-boundary points.
- **`point_in_footprint(x, y, polygons)`** — trivial multi-ring wrapper: `True` iff `(x,y)` is inside **any** ring (`any(point_in_polygon(...))`).
- **`min_edge_distance(x, y, polygons)`** — minimum point-to-segment distance from `(x,y)` to any edge of any ring (`_point_seg_dist`, a clamped-projection formula), used to enforce a `footprint_border` inset.
- **`clip_points(points, polygons, border=0.0)`** — splits a point list into `(kept, dropped)`: a point is kept iff it is inside the footprint (`point_in_footprint`) **and** at least `border` from every edge (`min_edge_distance`). Empty `polygons` is a pass-through (`kept=all, dropped=[]`) — this is what makes `footprint=None`/no-floor calls fully backward-compatible.

The module docstring is explicit that the footprint is the **floor SLAB** (the floor group's own faces), which sits wall-thickness **outside** the interior wall surface — reliable for "is this point over the floor" shape-clipping, but not a substitute for `detect_interior`'s wall-surface reading when an exact interior boundary (not just the slab outline) is needed.

### 4.6b Daylight-dimming photosensor placement — `hcl_radiance/sensor_daylight.py`

Pure-stdlib, pre-north frame (methodology.md §3 in the outer validation-kit repo). Backs the `photosensors` MCP tool. Three public functions:

- **`glazing_wall(parsed, material_map, scale, up_axis)`** — finds the **dominant glazed facade**: sums face area per glass group and picks the group with the largest total glass area, then computes that group's vertex-mean XY centroid and its Z extent (`H_win`=max, `sill_z`=min). **The inward direction is deliberately derived from the room centroid, not the glass face normal:** `inward = normalize(floor_centroid − glazing_centroid)`. This mirrors the same winding-unreliability rationale as `detect_interior` (§4.6) — OBJ face-normal sign depends on vertex winding order, which this codebase cannot trust across arbitrary source models, whereas "which way is the room" from two centroids is winding-independent. Returns a dict `{point, inward, transverse, H_win, sill_z, group}`. Raises `ValueError` if the material map has no glass group at all (photosensors placement is meaningless without a facade to reference).
- **`daylight_zones(H_win, sill_z, *, zone_rule="head_height", depth_factors=(1,2), sensor_fraction=2/3, task_height=0.0)`** — builds sidelighting zones measured in depth from the facade. `zone_rule="head_height"` (default) produces zones at `depth_factors × H_win` (default two zones: primary to 1×H_win, secondary to 2×H_win, named `primary`/`secondary`/`tertiary`), each zone's sensor sitting at `near + sensor_fraction × (far − near)` into the zone. `zone_rule="ies_2.5"` instead produces a single zone of depth `2.5 × (H_win − task_height)` (the IES/LM-83-style single-zone rule of thumb). (`place_photosensors` passes the window head **above the floor**, `H_win − floor_top_z`, as this function's `H_win`.)
- **`place_photosensors(parsed, material_map, scale, up_axis, *, zone_rule="head_height", depth_factors=(1,2), sensor_fraction=2/3, task_height=0.0, mount="workplane", workplane_h=0.8)`** — orchestrates `glazing_wall` + `daylight_zones` into world points: for each zone, projects a point `sensor_depth` inward from the facade centroid along the `inward` vector, centred on the facade (not offset laterally). `mount="workplane"` (default) places the sensor at `floor_top_z + workplane_h`, up-facing `[0,0,1]`; `mount="ceiling"` places it at `ceiling_z − 0.001` (or `floor_top_z + 3.0` if no ceiling is detected), down-facing `[0,0,-1]`. Each candidate point is checked against the floor footprint (`footprint.floor_polygons`/`point_in_footprint`); if it falls outside, `_snap_into_footprint` walks the point back toward the facade in 0.05 m steps until it lands inside (or, failing that, snaps to one step off the facade) — so a sensor is never returned floating outside the room. Returns `(points, methodology)` where `methodology` carries the facade record (`group`, `point`, `inward`, `H_win` [head height above floor], `sill_z`), the resolved `zones` (each with `position` and a `snapped` flag), `zone_rule`, `sensor_fraction`, `mount`, and `count`.

> **⚠️ `methodology` also carries `weights` / `uncontrolled_fraction` / `weights_note`** (`_zone_area_weights`, `:144`) — the floor-area fraction of each sensed zone, ready to pass straight to `daylight_savings(weights=…)`. They are emitted **so a caller feeding `daylight_savings` uses the zoning that matches THESE sensors by construction.** Without them the natural next step is `area_weights_from_geometry` (§8.2), which encodes a *different* zone rule and can cover the whole floor where these zones do not — **a difference worth tens of percent in the resulting savings figure**. `weights` generally sums to **less than 1**: the remainder is floor not sensed by any of these photosensors and is billed at full power, which `weights_note` states in prose and `uncontrolled_fraction` quantifies. Check `Σweights` is physically true before believing a savings number.

### 4.6c matplotlib PNG scene previews — `hcl_radiance/scene_preview.py`

Renders PNG images via matplotlib (Agg backend), **diagnostic only, explicitly not a photometric render** (contrast with `image.py`'s `rpict`-based fisheye renders, §4.4). Backs the `preview_scene` MCP tool. Draws the true floor polygon, window geometry, and luminaire footprints; overlays point layers (grid, photosensors, observers) from the scene geometry. Works in the **post-north final frame** (`floor_polygons(..., north_angle_deg=...)`) so it aligns with `.pts` files, which are already north-rotated by the time they're written. Produces an orthographic plan (top-down) PNG and a real matplotlib **mplot3d** 3D-view PNG (`fig.add_subplot(111, projection="3d")` — not a hand-rolled isometric projection). Four public functions:

- **`object_xy_bbox(parsed, name, scale, up_axis, north_angle_deg=None)`** — XY bounding box of all faces belonging to a named object or group (matches on OBJ `o` object name first, `g` group name second); returns `None` if nothing matches. Used to place luminaire/desk footprint rectangles.
- **`build_scene(parsed, material_map, scale, up_axis, north_angle_deg, luminaire_groups=None)`** — assembles a scene dict: `footprint` (floor polygon rings, post-north), `windows` (a `(x0, y0, x1, y1, z0, z1)` 6-tuple per glass face — the XY bounding box **plus** its Z extent, so the window can be drawn both as a plan-view line and, at its true height, as a 3D quad), `luminaires` (XY bbox rectangles for each named group in `luminaire_groups`), `z_floor` (`floor_top_z`) and `z_ceiling` (`_ceiling_z`, falling back to the tallest vertex in the model if no ceiling group is found).
- **`render_plan(scene, layers, out_path, *, size_in=6.0, dpi=150)`** — orthographic top-down PNG built on `plt.subplots`: draws the true floor polygon outline (never a hardcoded rectangle — non-rectangular rooms render their real footprint), the window as a cyan line (`w[:4]` of the 6-tuple), luminaire rectangles (filled yellow/`#f4c430`, edge `#d4a017`), and a point layer per entry in `layers` (a `{"grid"|"photosensors"|"observers": [[x,y,z,dx,dy,dz],...]}` dict) styled by `_STYLE`: grid = orange dots, photosensors = green diamonds, observers = red dots with a direction arrowhead (via `ax.annotate`, drawn from `dx,dy` when present). Axes are equal-aspect with X/Y labelled in metres, a dotted grid, and a legend; matplotlib's default +Y-up orientation is used as-is (no manual flip needed). Writes PNG to `out_path` and returns `None`.
- **`render_3d(scene, layers, out_path, *, size_in=6.0, dpi=150)`** — a genuine matplotlib **mplot3d** 3D view (`ax = fig.add_subplot(111, projection="3d")`): floor and ceiling polygon rings drawn as wireframes at `z_floor`/`z_ceiling` plus vertical edges at each ring vertex; luminaires as filled yellow `Poly3DCollection` quads at ceiling height; the window as a translucent `Poly3DCollection` quad plus an outline drawn at its true `(z0, z1)` extent from the `build_scene` 6-tuple (falling back to floor/ceiling height if no z-extent was recorded); point layers as a 3D `ax.scatter` at each point's real Z (or `z_floor` if no Z is given); and a 3D direction **quiver** (`ax.quiver`) for any point row that carries a non-zero `(dx, dy, dz)` — so observers do get direction arrows in 3D, not just in plan. The view sets `ax.set_box_aspect(_box_aspect(scene))`, where the private `_box_aspect` helper derives the (x, y, z) proportions from the room's **real** footprint bounds (XY span) and floor→ceiling height — so any room shape renders true rather than at a hardcoded office proportion; every component is clamped >0 so a degenerate/empty footprint falls back to a unit cube. It labels the X/Y/Z axes in metres and adds a legend. Writes PNG to `out_path` and returns `None`.

Legend/styling is shared between both views via the module-level `_STYLE` dict (`{"grid": ("#e8820c", "o", "grid @0.8 m"), "photosensors": ("#1a9850", "D", "daylight sensor"), "observers": ("#d73027", "o", "observer")}` — colour, matplotlib marker, legend label); any layer name not in `_STYLE` falls back to a grey dot labelled with its own name.

## 5. Annual 2-phase DDS — `hcl_radiance/{annual,annual_commands,annual_results}.py`

> **Source:** Subramaniam 2017, *Daylighting Simulations with Radiance using Matrix-based Methods*, LBNL, §2-phase decomposition (H-30).
> **Source:** Perez et al. 1990/1993 all-weather sky (embedded in Radiance `gendaymtx`) — model lives inside Radiance.
> **Source:** Reinhart 2001 / Tregenza 1987 sky-vault patch discretization (145 patches MF:1 / 5185 solar discs MF:6, embedded in `gendaymtx`) — model lives inside Radiance.

**Method:** the 2-phase Daylight-Coefficient method with Direct Sun (DDS), per **Subramaniam 2017** (H-30), with sky-diffuse and sun-direct computed as **two independent transports** (no black-room subtraction).

**Per channel-set command chain** (per Subramaniam 2017 §2-phase DDS), built by `_build_annual_steps` in `annual.py` and the command builders in `annual_commands.py`:

```
Phase 1 (sky-diffuse):  oconv {mat}{geo}            → sky{i}.oct                 (plain, NO -f)
                        rfluxmtx -I+ -y N … skyglow.rad -i sky{i}.oct < pts  → illum_sky.mtx   (Reinhart MF:1, 145 patches)
                        gendaymtx -m 1 -s -c R G B {wea}                     → sky.mtx  (COLORED sky)
                        dctimestep illum_sky.mtx sky.mtx                     → annual_sky{i}.ill
Phase 2 (sun-direct):   oconv -f {mat}{geo} suns.rad → sun{i}.oct           (FROZEN octree, -f)
                        rcontrib -I+ -y N … -e MF:6 -f reinhart.cal -b rbin -bn Nrbins -m solar  → illum_sun.mtx  (5185 solar discs)
                        gendaymtx -5 0.533 -d -m 6 {wea}                     → sun.mtx   (NEUTRAL sun, 0.533° disc)
                        dctimestep illum_sun.mtx sun.mtx                     → annual_sun{i}.ill
```

(`-bn Nrbins` is verbatim from source — `Nrbins` is a `reinhart.cal` variable that expands to the bin count at MF:6, not the sensor-point count `N` in `-y N`.)

Color enters **only** through `gendaymtx -c` on the sky (`build_gendaymtx_sky`, `annual_commands.py:112`); the **sun is neutral** (`build_gendaymtx_sun`, `annual_commands.py:133`, no `-c` — `gendaymtx -c` cannot color the direct beam; confirmed in source comments, spec §9.5). The three Reinhart `.cal` files (`reinhartb.cal`/`reinsrc.cal`/`reinhart.cal`, `REINHART_CAL_FILES`) are front-loaded into `work_dir` by `stage_cal_files` before any `rfluxmtx`/`rcontrib` step. If a required `.cal` is absent from the Radiance lib, `_emit_if_cal_missing` degrades to an honest emit envelope (`ran:False` + full command plan + reason) rather than failing mid-run at the `cp` step; the predicate behind it is `missing_cal_files(lib_dir=None)` (`annual_commands.py:37-48`), which counts **every** file as missing when no lib dir can be located at all. `materials_files` (`annual_commands.py:29-34`) normalizes the `{mat}` term from either a space-joined string **or** a list (DEF-3 — a list is what `import_geometry`'s `material_sets` returns). The 5185 solar-disc sources are written by `suns_rad_steps` (`echo` head + `cnt 5185 | rcalc … reinsrc.cal … solar source sun … 0.533`).

`run_annual` combines sky+sun by **element-wise addition** (`combine_sky_sun`, `annual_results.py:109`, physically correct; they are emitted separately upstream — combining them here is a deliberate extension). `run_annual_separated` keeps them apart for the annual→nvRD bridge (spec §5.1), which needs the direct beam re-colorable; it always processes the **full** `.wea` and supports neither `period` nor `dosimetry_threshold` (`annual.py:184-185`). Both share `_build_annual_steps`; only `run_annual` supports the optional `period` window (via `weather.decompose`/`subset_wea` → `period.wea`, subset in-process when the `.wea` is readable, else an emitted `subset_wea` command) and the optional `dosimetry_threshold` (`dose_summary` over the real period HOY series). Default `rad_params="-ab 2 -ad 512 -aa 0.1 -ar 64"`, `timestep_min=60`.

**The `.ill` parse** (`parse_ill`, `annual_results.py:47`): a real `dctimestep` matrix is `NROWS=points × NCOLS=timesteps × NCOMP=3`; **each data row is one sensor point** holding interleaved RGB triplets. The original code treated each *line* as a timestep and kept 3 columns → on a single-sensor study returned `n_timesteps==1`, silently destroying the year. Now `_parse_ill_header` scans for the `NROWS=`/`NCOLS=`/`NCOMP=`/`FORMAT=` lines wherever they appear (rather than brittle fixed `lines[4/5/6]` offsets, which also read only the first digit of each count), rejects a non-`ascii` `FORMAT` (a hard `ValueError` carrying a re-run instruction, not a silent skip — `annual_results.py:62-65`, `:90-93`), and each sensor row is chunked into `NCOMP`-sized groups (default `sensor=0` = eye point). A companion `parse_ill_matrix` (`annual_results.py:81`) returns **all** points × timesteps for the climate-metrics path (§5ter), leaving `parse_ill` untouched for the single-eye melanopic path. **9-bin concatenation** order in `recombine_annual` (`annual_results.py:122`) is a documented (unpinned) ==caller== contract: the 3 channel-sets are concatenated per timestep in the order given, and the ==caller== must pass `channel_scenes` in the matching `W_*_9` band order.

**Documented divergence:** the sun `rcontrib` (`build_rcontrib_sun`, `annual_commands.py:117`) drops the `-faf` (binary float) so the `.ill` stays ASCII and parses with the same `parse_ill` — numbers identical, encoding differs. Restoring `-faf` for speed/size would require a binary-float branch in the parser.

## 5ter. Annual climate-based daylight metrics — `hcl_radiance/{annual_daylight,daylight_factor,sensor_sets}.py`, `hcl_core/daylight_metrics.py`

Three MCP tools (`annual_daylight`, `daylight_factor`, `sensors`) added on top of the §5 annual/grid infrastructure — no changes to `run_annual`'s command chain or byte output.

**`hcl_core/daylight_metrics.py`** (pure Python, no Radiance dependency) reduces a `[points][timesteps]` photopic-lux matrix (`rgb_to_photopic_lux`, `daylight_metrics.py:9` — applies `LUMINOUS_EFFICACY` over the same verified `W_PHOTOPIC_3`/`W_PHOTOPIC_9` weights as the rest of the spectral core) to:

- **DA** (`daylight_autonomy`) — fraction of *occupied* timesteps with illuminance ≥ `threshold` (default **300 lx**).
- **cDA** (`continuous_da`) — continuous DA: partial credit `min(1, E/threshold)` averaged over occupied timesteps (never binary pass/fail; returns 1.0 if `threshold ≤ 0`).
- **UDI** (`udi_bins`) — four occupied-hour fractions: `short` (`E < lower`, default **100 lx**), `supplementary` (`lower ≤ E < upper_sup`, default **300 lx**), `autonomous` (`upper_sup ≤ E < upper_aut`, default **3000 lx**), `exceed` (`E ≥ upper_aut`).
- **sDA** (`spatial_da`) — fraction of points whose DA ≥ `da_fraction` (default **0.5**, i.e. the LEED-style "sDA300/50%" convention).
- **ASE** (`annual_sunlight_exposure`) — fraction of points where a **separate direct-only lux series** exceeds `threshold` (default **1000 lx**) for **more than** `hour_limit` (default **250 h**, strict `>`) of occupied time. Takes `sun_lux_matrix` (the direct-only, NOT the total matrix) and `step_hours` for correct hour accounting at non-hourly timesteps; also returns `per_point_hours`.
- `daylight_metrics(...)` (`daylight_metrics.py:95`) composes all of the above into `{per_point: [...], spatial: {...}}` (`spatial` holds `sDA`, `DA_avg`, `UDI_autonomous_avg`, and — when `sun_lux_matrix` is given — `ASE`/`ASE_per_point_hours`) and accepts a `partial_year` flag that, when `True`, adds a **top-level** `partial_year = True` key to the returned dict (alongside `per_point`/`spatial`, NOT nested under `spatial`) to flag a non-full-year series to the ==caller==, **plus a `partial_year_note`** (`daylight_metrics.py:125-128`) carrying the substantive caveat: sDA/DA/UDI are fractions of the *supplied* occupied hours, but **ASE's 250 h threshold is a FULL-YEAR criterion and cannot be reached by a shorter window** — so a low partial-year ASE means "not enough hours", **not** "no direct-sun problem".

**Occupancy** (`hcl_core.lighting_controls.default_schedule`, `lighting_controls.py:134`, reused — not reimplemented): 1.0 on weekday hours in `[occupied_start, occupied_end)` (defaults **08:00–18:00**), else 0.0, over `year_hours` (default 8760). Convention: **HOY 0 = Monday 00:00** (`dow = (h // 24) % 7`, 0–4 = Mon–Fri). ==Caller==s may override with an explicit per-timestep `occupancy` mask (the `annual_daylight` tool validates its length against the simulated timestep count).

**`hcl_radiance/annual_daylight.py`** (`run_annual_daylight`) reuses `annual._build_annual_steps` (the same DDS chain as `run_annual`) for the total (sky+sun, ambient-bounced) lux matrix, and — when `ase=True` (the default, and the `annual_daylight` tool never overrides it) — runs a **second, independent pass** with `_force_direct_only` rewriting `rad_params` to `-ab 0` for the ASE-only direct-sun lux matrix, via an additive `ase_rad_params` kwarg on `_build_annual_steps` (so `set_outputs` entries become 3-tuples; `run_annual` never passes it, keeping its command chain byte-identical). Inline `[[x,y,z,dx,dy,dz],…]` points are accepted and written to `points.pts` (via `pts_to_text`) so `_count_points`/stdin see a path. Sensor rows are parsed with `annual_results.parse_ill_matrix` (all points × timesteps, vs. the single-sensor `parse_ill`), sky+sun combined per point via `combine_sky_sun`, channel-sets concatenated by `_concat_sets` (which **raises when the sets disagree on point count or timestep count**, since it pairs them positionally at `[p][t]` — a short set otherwise supplies a later entry's values, i.e. a wrong annual figure reported with confidence), and converted to lux by `rgb_to_photopic_lux`. The two matrices are never combined; `annual_daylight` passes the total (`lux_matrix`) to the DA/cDA/UDI path and the direct-only (`sun_lux_matrix`) to ASE, with `step_hours = timestep_min/60.0`. **The `annual_daylight` MCP tool does not yet expose a `period` subsetting argument** (unlike `run_annual`) — every call simulates the full 8760-hour year; `partial_year` is wired in `daylight_metrics()` but not yet surfaced through this tool.

`run_annual_daylight` also stamps `rad_params` on its result and, via `commands.ambient_convergence_note`, a **`convergence_warning`** when the ambient settings are preview-grade — DA/sDA/UDI are threshold crossings, so under-converged indirect sampling moves them far more than it moves means, and nothing else in the return would reveal that a number is sampling-limited. The ASE pass is exempt by construction: `_force_direct_only` rewrites it to `-ab 0`, which ambient settings cannot affect (`direct_only_ok=True`).

Found by the first live `annual_daylight(quality="medium")` call after a client restart: `ran:true`, full metrics, no warning — while the same parameters flagged correctly in-process. Every existing test called `ambient_convergence_note` directly, so the file stayed green throughout. Same shape as the unregistered `quality_presets` one layer up. `server.py` now forwards both fields; `test_the_warning_survives_the_server_envelope` goes through `server.annual_daylight` with the core stubbed (an 8760-h solve is not a unit test) and fails on the pre-fix tree. Scope checked, not assumed: `annual_daylight` is the only core that emits the field, `daylight_factor` returns its core result whole, and `daylight_savings`' core never produces it. **Assert that a field arrives in the caller's hands, not merely that some function can produce it.**

**`hcl_radiance/daylight_factor.py`** (`run_daylight_factor`) builds a **CIE Standard Overcast Sky** via `gensky <month> <day> <hour> -c -g <gnd_refl>` (`sky_overcast.build_gensky_overcast`/`write_overcast_sky`; the date/time only fix solar geometry for the sun-free overcast dome — `-c` selects the distribution, `-g` sets ground reflectance) plus its ground/sky glow tail (appended by `printf`). On the live path the sky-build steps run in-process before `run_grid`'s oconv reads `overcast_sky.rad`; on the emit path they render to strings so the plan stays honest. It runs `run_grid` once on the indoor scene + overcast sky and once on a sky-only exterior scene with a single unobstructed upward-facing reference point (`[0,0,0, 0,0,1]`), and returns `DF = 100 × E_indoor / E_outdoor` per point (`df_per_point`, `df_avg`, `df_min`, `uniformity = df_min/df_avg`, `e_outdoor`). The **exterior reference run is guarded exactly as the indoor one is**: DF is `E_indoor/E_outdoor`, so that reference *is* the denominator, and an unguarded failure died on `KeyError: 'daylight'` instead of naming which run failed — a failed exterior pass now returns `{ran:True, error, failed_step, stage:"exterior_reference"}`. `E_outdoor` is *traced*, not a fixed constant (e.g. not literally 100000 lx) — the CIE overcast luminance distribution and ground reflectance both affect it. Defaults `month=6, day=21, hour=12.0, gnd_refl=0.2`.

**`hcl_radiance/sensor_sets.py`** (`create_sensor_set`/`list_sensor_sets`/`get_sensor_set`/`delete_sensor_set`) is a small persistence layer independent of both: a named set is either an explicit points list or an EN 12464-1 `grid={interior, floor_z, workplane_h?, max_spacing?}` (default `workplane_h=0.8`; delegates to the same `en12464_grid` helper as `sensor_methodology.py` §4.6), written to `<work_dir>/sensors/<name>.pts` (via `pts_to_text`) plus a JSON registry entry (`<work_dir>/sensors/sensors.json`) with keys `path`, `count`, `source`, `methodology`. The `sensors` MCP tool exposes this as `action=create|list|get|delete`. `annual_daylight`, `daylight_factor`, and `daylight_savings` (mode=`annual`) all resolve `points` via a shared `_resolve_points(points, sensor_set, work_dir)` helper in `server.py:1062`: a named `sensor_set` wins over inline `points` when both are given.

**`daylight_savings`** (§8.2, unchanged command chain) was extended to accept the same multi-point `points`/`sensor_set` resolution for `mode="annual"`, so one call can now cost out daylight-responsive savings across a full sensor grid (one `weights` entry per point) rather than a single reference point.

## 5quater. LM-83 three-phase engine — `hcl_radiance/{threephase,threephase_commands,aperture,lm83_run,lm83_sun}.py`, `hcl_core/{lm83,klems}.py` (2026-08-12)

> **Source:** IES LM-83-12 (sDA/ASE method, §§2.2.5–2.2.7, 3.2.6, 3.3); three-phase matrix method (V·T·D·s) per Subramaniam 2017 / LBNL; Klems basis for the transmission matrix.

The `lm83_daylight` tool (server def `:1204`, 20 params) runs LM-83's **method**, not just its arithmetic: a three-phase engine (`rfluxmtx` view matrix V and daylight matrix D per window group; a Klems-basis transmission matrix T from `hcl_core/klems.py`) with an hourly **blind-state policy** in `hcl_core/lm83.py` — blinds close whenever §2.2.6's trigger fires (>2 % of an analysis area's points see direct sun, floored at 1 point, evaluated **per area**; areas must be split by facade orientation and each under 10 000 sf, refused otherwise), and ASE runs a zero-bounce direct-sun pass with blinds retracted and no sky/ground (`lm83_sun.py`, §§3.2.6/3.3). ## 6. The nvRD alerting model — `hcl_core/nvrd.py`

> **Source:** Amundadottir 2016, *Light-driven model for identifying indicators of non-visual health potential in the built environment* (EPFL PhD thesis); H-13…H-19 — thesis not obtained as a primary source.

The non-visual direct response model implements **Amundadottir 2016** (EPFL) — constants digit-for-digit verified against the thesis constants. Pure-Python: the source's custom convolution + `lfilter` truncation are reproduced exactly; it consumes a user-provided sub-hourly spectral irradiance series (no Daysim; spec §9.4).

The model constants live in one place — `data.py:36` `NVRD = {"EI50": 106.0, "slope": 3.55, "filters_h": (0.3, 1.7, 2.3), "zeff": 0.0024545715023813522, "timestep_h": 0.1}` — and are read by `direct_response` (`:66-69`), never re-literalized.

**Effective ipRGC irradiance** (`effective_irradiance:85-90`): from a 311-point spectral vector over **390–700 nm @1 nm**:

```
I_eff = trapz( E(λ)·s_ipRGC(λ) ) × 311        (the ×311 is the source's literal multiplier, not a normalized mean)
```

`IPRGC_SENS_WEIGHTING` is a 311-element table (`data.py`), and `effective_irradiance` hard-rejects any row that is not exactly 311 points. The 401→311 window is `_slice_311` (`:92-97`) using `row[10:-80]` (index 10 = 390 nm, last kept = 700 nm, count 311). This implementation builds a new weighted list rather than mutating the input in place (safe; numerically identical).

**The filter cascade** (`direct_response:63-83`):


| Stage | Filter   | Window | Length @ δ=0.1h | Role                                  |
| ------- | ---------- | -------- | ------------------ | --------------------------------------- |
| L1    | SMA      | 0.3 h  | 3                | smooth I_eff → drives history H      |
| LH    | adaptive | 1.7 h  | 17               | light-adaptation history → shifts σ |
| L2    | EMA      | 2.3 h  | 23               | temporal smoothing → R_D             |

The three windows are `NVRD["filters_h"] = (0.3, 1.7, 2.3)` h; per-run lengths are `round(window/δ)` (`:70`).

**History transform** (`adaptive_response:55-61`): `H = SMA( log10(I · 118.5 · 2.2) )`, clamped ≥0 (the 118.5·2.2 = 260.7 factor maps effective irradiance back toward a luminance-like scale before the log; `log10` of a zero sample is coerced to 0.0). An optional `FLOOR==1` branch quantizes H to integers; the production ==caller== passes `FLOOR=0` (`:81`), so it is inactive.

**Adaptive sigmoid:** `σ_t = σ₀ · 2^(H−1)` with `σ₀ = EI50·zeff = 106 · 0.0024545715 = 0.26018458`, then the Hill response (`relative_response:51-53`):

```
r_t = 1 / (1 + (σ_t / I_eff,t)^n)        n = 3.55 (slope),  0 when I_eff = 0 (daylight gate)
```

`zeff = 310/683/118.5/1.42·0.91 = 0.0024545715023813522` is the lux→melanopic-effective-irradiance conversion (F11 source). **Output** (`nvrd:126-161`): relative `R_D(t)` ∈ [0,1] (`relative_response`) and cumulative `RD_cum = cumtrapz(R_D, hours)` (trapezoidal; `cumulative_response`), alongside the raw `effective_irradiance` series.

**Step guard:** `δ ≤ 0.3 h` required (checked both in `nvrd:143` and `direct_response:64`); default 0.1 h (6 min) from `NVRD["timestep_h"]`. **The one material fix:** a naive implementation hardcodes `direct_response(…, 0.1)` (ignoring its own `time_step` input), so all filter lengths are odd and the truncation in `lfilter_base` (`:33-36`) is benign — for an odd filter length the naive-convolution output is trimmed back to exactly `len(input)`; for an **even** length it is `len(input)+1`, which misaligns the final `eff_irradiance[i]` gate and raises an opaque `IndexError`. This implementation honours `timestep_h`, so it adds an explicit even-filter-length guard (`:76-79`) that returns a clear error string (surfaced by `nvrd` as a `ValueError`), confining the model to the validated δ=0.1 regime. Two further documented divergences, both in `nvrd`: uniform-grid synthesis when `hours` is omitted (`:150-154`, `hours=[i·δ]`, versus integrating the CSV's actual `hour` column) and no automatic per-orientation grouping (==caller== must pre-group + pass a single-orientation, chronologically-ordered row set). A monotonic-`hours` guard (`:158-159`) rejects out-of-order timestamps so the cumulative integral stays meaningful.

**Wire-transport accommodation** (`_coerce_series:99-123`): `nvrd` accepts the spectral series either inline (list of 311- or 401-point rows) **or as a path** to a whitespace/comma-separated text/CSV file (one timestep per non-comment line; `#`-comment lines are skipped and the comma-vs-whitespace separator is sniffed per line, `nvrd.py:116-119`). A full-resolution inline series can be truncated over the MCP stdio wire (401-pt rows observed arriving as 367); the file-path form sidesteps the transport, consistent with the file-path-input contract used elsewhere on the tool surface.

### 6.1 Circadian dosimetry — `hcl_core/dosimetry.py`

Pure-Python dose accumulation over a melanopic-EDI time series. This is a **separate** module from `nvrd.py` (nvRD does its own trapezoidal integration); dosimetry is consumed by the **annual daylight transport** (§5): `run_annual` calls `dose_summary` (`hcl_radiance/annual.py:160-165`) only when `dosimetry_threshold is not None`, and the MCP `run_annual` tool defaults `dosimetry_threshold=250.0` lx (`server.py:1088-1089`).

- **`hours_above_threshold(medi_series, hoy, threshold=250.0, *, step_hours=None)`** — total hours where mel-EDI ≥ threshold. Each qualifying sample contributes **its own timestep**, clamped by the actual forward gap so a short final interval stays exact. `step_hours` wins when given (`run_annual` threads `timestep_min/60`); otherwise the step is the **modal** positive HOY gap (`_nominal_step_hours`, `:3-26`) — chosen over the median so the returned duration is always an interval the series actually contained: on an even-length gap list the median averages the two middle values, so gaps `[1,1,2,2]` yield 1.5 h, an interval no sample had, where the mode yields 1 h. Ties break to the smaller gap. A bare forward difference `hoy[i+1]-hoy[i]` is exact only on a contiguous series — on the gapped windows `weather.decompose` produces it charged the last sample of every block the whole non-occupied gap (a 3-day 08:00–18:00 window read 59 h instead of 33 h; a Jun–Aug window read 1475 h instead of 33 h), and the error does not shrink with a finer timestep. Every sample is treated alike, first and last; a single-element series contributes `step_hours` if given, else 1.0 h. Requires `len(medi_series)==len(hoy)`; returns `round(total, 4)`. See ADR-0003.
  **Quantity:** pass CIE S 026 **mel-EDI**, never `melanopic_lux` (larger by ≈1.0997 on the 9-bin route; the `≥` comparison would manufacture compliance). See ADR-0001.
- **`daily_profile(medi_series, days)`** (`:59`) — groups mel-EDI values by day number → `{day: [values…]}`.
- **`dose_summary(medi_series, hoy, threshold=250.0, *, step_hours=None)`** — compact rollup `{n, threshold, hours_above, mean, max}` (mean/max are 0.0/absent-safe for an empty series). This is the dict surfaced as `out["dosimetry"]` on an annual run. `mean`/`max` are in the same quantity as `medi_series`, i.e. mel-EDI.

## 7. Spectral reconstruction & the annual→nvRD bridge — `spectral_reconstruct.py`, `_recon_data.py`, `annual_nvrd.py`

> **Source:** CIE 15 / Judd–MacAdam–Wyszecki D-series (S₀/S₁/S₂ eigenvectors for sky SPD reconstruction, H-21/H-22).

The bridge wires existing pieces: **EPW → Daysim sub-hourly `.wea` → run_annual_separated (sky & sun separate) → reconstruct per-nm spectrum two ways → assemble nvRD rows → nvrd() twice → {faithful, enhanced} R_D + divergence.** Default 6-min timestep (0.1 h) satisfies nvRD's δ≤0.3h guard. Location is **always EPW-derived** (the "location footgun" was removed — wrong coordinates are unrepresentable: `annual_nvrd` passes NO coordinates to `generate_subhourly_wea`, which reads the EPW LOCATION line itself).

### 7.1 The two reconstruction methods (`reconstruct_spectrum`)

- **faithful** (`:99-101`): `irradiance_per_nm(sky+sun)` — the flat §9.3a step-expansion `I=(179/683)·(1/107)·channel` held constant across each bin + neutral sun.
  > **Grounding gap:** The `(179/683)·(1/107)` scalar (H-10) has no published derivation; appears only in `melanopic_calcs.bas:40`; treat as implementation lineage. Cancels in ELR and in same-path EDI **ratios**; does **NOT** cancel in absolute E_α, in absolute EDI/mel-EDI, or in the nvRD sigmoid (§1.5).
  >
- **reference (a.k.a. enhanced)** (`:102-121`): within each bin, redistribute the flat energy across a reference shape **preserving the bin total**: `E(λ) = E_bin · R(λ)/Σ_bin R(λ)` (`_shape_within_bins:37-57`). The shape is clamped non-negative first (D-18); if a bin's clamped shape sums to ≤0 it falls back to the flat/uniform distribution for that bin.
  - **Sky** (`_sky_reference_spd:59-78`) shaped by an explicit SPD, else a per-timestep CIE D-series sky from the timestep CCT (`dseries_sky=True`, requires `sky_cct`), else a default D65 (6504 K) shape. Precedence is `sky_spd` → D-series → D65, so a physics-covered timestep uses its real EPW-derived sky and only uncovered timesteps fall back.
  - **Sun** (`_sun_reference_spd:80-87`) re-colored by an **air-mass-dependent direct-normal solar SPD** keyed to solar zenith (`sun_spectral="colored"`), or left neutral/flat (`sun_spectral="neutral"`).

> **Note on names:** the code method value is `"reference"` (the default of `reconstruct_spectrum`); the bridge/tool surface exposes it as `"enhanced"`. `method` must be `"faithful"` or `"reference"` or it raises.

**The re-integration invariant** (verified numerically <1e-9 and structurally; the central test in `test_spectral_reconstruct.py`): re-summing the enhanced 401-vector over each bin returns the flat bin total — the reconstruction **can never contradict the Radiance transport**. `_bin_spans` (`:21-35`) folds the appended 780-nm point into the last bin (`hi_i = 401`) so spans tile indices 0..400 exactly once. Bins are `BINS_9` for 9-channel (`channel_type==1`) else the ascending 3-channel `_BINS_3_ASC`.

### 7.2 Embedded standards (`_recon_data.py`) — honestly labelled as NOT measurements

- **Air-mass solar templates** (`_SOLAR_ANCHORS:53-63` → `SOLAR_AM_SPD:64`): coarse 20-nm anchors for AM 1.0/1.5/2.0/3.0, linearly interpolated to 401 pts (`_interp_anchors`). **Representative slopes inspired by ASTM G173/SMARTS — NOT literal G173 values; the 760 nm O₂ dip is omitted.** Used shape-only (renormalized per bin), so absolute calibration is irrelevant. `solar_spd_for_zenith` (`:72-86`) maps zenith → air mass via `AM = 1/cos(z)` plane-parallel (`_air_mass:66-70`, z clamped to [0,89]°), then interpolates between the two bracketing air-mass anchor sets. (Docstring points production users to NREL's `ASTMG173.xls`.)
- **CIE D-series S0/S1/S2** eigenvectors (CIE 15 / Judd-MacAdam-Wyszecki), 41 anchors @10 nm (`_S0/_S1/_S2:94-102`) interpolated to 401; the 560-nm anchor locked at S0=100/S1=0/S2=0 (the CIE normalization point; `test_dseries_table_structural_anchor` locks it against re-fabrication). `dseries_xy_from_cct` (`:107-119`) is the standard daylight-locus chromaticity (cubic-in-1/T, split at 7000 K, valid 4000–25000 K) and `dseries_spd` (`:121-127`) applies the M1/M2 mixing → the canonical daylight SPD. `dseries_xy_from_cct` **raises** outside 4000–25000 K rather than extrapolating off the locus (`:110-113`).

### 7.3 The 413-column nvRD row (`assemble_nvrd_rows:168-197`)

`[x,y,z, vx,vy,vz, m,d,h, E_alpha, ELR, EDI, <401 per-nm>]` — length **413** (12 + 401). Cols 9–11 are the **melanopic** (alpha=5) E/ELR/EDI of the *summed* sky+sun channels (`alpha_opic_from_channels`, `:188`). `nvrd()` consumes `rows[12:]` (`annual_nvrd.py:123`) and windows `[10:-80]`=311 pts. Note: a source docstring says "400 columns" but the executable code requires 401 — this implementation matches the code (401). Per-row overrides: `solar_zenith` may be a scalar or a per-timestep list (`:189`); `sky_spd_series`/`sun_spd_series`, when supplied, override the scalar `sky_spd`/`sun_spd` row-by-row (`:190-191`).

### 7.4 Divergence reporting (`reconstruction_divergence:139-165`)

- **Single-timestep spectral divergence:** `{flat_vs_reference, neutral_vs_colored_sun}` each as `{mel_edi_pct, i_eff_pct}` (proxies `_mel_edi_proxy:124-126` over the melanopic action and `_i_eff_proxy:128-131` over the 390–700 nm ipRGC window), computed in `annual_nvrd` at the timestep chosen by **`_representative_timestep`** (`annual_nvrd.py:93-113`, called at `:241`).
  > **The selection rule is PEAK SUN, not first-non-zero-sky.** The comparison this feeds contrasts a colored against a neutral sun, so a step with no sun makes it degenerate: the percent-difference guard divides zero by zero and reports exactly **0.0**, which reads as "the sun's spectral treatment is immaterial" rather than "this step has no sun". Selecting on non-zero *sky* instead lands on a **pre-sunrise** step on any real year and does exactly that — the documented `divergence.neutral_vs_colored_sun = 0` artefact. The rule therefore picks the step whose **direct-sun channels sum highest** (`sun_tot`), falling back to the **brightest sky** step when the sun never rises (a fully overcast series), and to index 0 only when the series is empty or wholly dark. Quote `RD_series_divergence` (below) in preference to the single-timestep figure.
- **R_D-series divergence** (`annual_nvrd.py:259-263`): `{mean_abs, max_abs, final_cum_pct}` over the whole faithful-vs-enhanced R_D series — the honest "how much does the reconstruction choice move the *alertness result*?" signal.
- Baseline direction (`_pct:133-137`): percentages are **enhanced relative to the simpler baseline** (positive = enhanced yields the larger metric).

### 7.5 The enhanced colored-sun is time-resolved on a live Daysim run; constant-zenith (30°) is only a fallback

`generate_subhourly_wea` parses the produced sub-hourly `.wea` and returns per-row `timestamps` + `solar_zeniths`, which `annual_nvrd` feeds into both reconstruction methods; the 30° zenith is strictly a *degraded-mode fallback* (no Daysim / empty `.wea`). The evidence chain:

1. `generate_subhourly_wea` (`subhourly.py:109-110`), on a successful Daysim run, returns `{wea, ran, commands, timestamps, solar_zeniths}` — `_parse_wea_timestamps_and_zeniths` (`:21-37`) computes a **per-row** `solar_zenith(month, day, hour, …)` for every sub-hourly timestep. (On `run=False` / Daysim-absent / empty `.wea`, it returns `([], [])` so the ==caller== degrades cleanly.)
2. In `annual_nvrd` (`hcl_radiance/annual_nvrd.py:214`), `solar_zeniths = wea_zen if wea_zen else None` (`:214`) — a **real per-timestep list** on a live run; `None` only when the list is empty/missing. Those zeniths flow into both the faithful (`:228`) and enhanced (`:234`) reconstruction calls.
3. With a real list, `reconstruct_spectrum` colors each timestep's sun with its **own** air-mass SPD (`AM = 1/cos z`), so the reddening **is time-resolved**. The constant-30° branch (`zen = 30.0 if solar_zenith is None else solar_zenith`, `spectral_reconstruct.py:86`) fires only when `solar_zeniths is None` (degraded mode).
4. **Surfaced honestly** via `out["enhanced_solar_note"]` — but it is now **only emitted when `"enhanced" in out and solar_zeniths is None and not full_physics`** (`annual_nvrd.py:274-283`), i.e. exactly the fallback case. Under partial `physical_sky` coverage the note correctly scopes to "the template-fallback timesteps" vs "ALL timesteps".
5. The per-timestep zeniths derive from `weather.solar_zenith` (§7.8) — a simplified constant-declination solar-position model (Cooper-1969 lineage). It is physically reasonable (e.g. Athens summer-solstice noon → ~15.5° zenith), but absolute air-mass-reddening accuracy is bounded by that model's fidelity, not by a fixed 30°.

**Net:** the colored-sun machinery is built, energy-preserving, tested, **and time-resolved on any live Daysim run**. The constant-30° path remains only as a labelled fallback for the no-Daysim / empty-`.wea` case (or, under `physical_sky`, for the steps not covered by physical spectra).

### 7.5a Post-review seams added by the spectral-sky feature (§7bis)

The spectral-sky-from-EPW work (Phases 1–7, see §7bis) wired four additive seams into this module without disturbing the faithful/enhanced contract above:

- **`sun_spd` injection (`reconstruct_spectrum:114`, `_sun_reference_spd:80-87`).** Alongside the air-mass-template sun, the reference path now accepts an explicit 401-value `sun_spd` (a physical direct-normal SPD). When supplied it overrides the air-mass template; when `None` the **30° fallback still applies** (`:86` — `zen = 30.0 if solar_zenith is None else solar_zenith` — verified unchanged) — but note (per §7.5) that the production `annual_nvrd` path now passes a real per-timestep `solar_zeniths` list on a live Daysim run, so `None` (and thus the 30° fallback) is reached only in degraded mode or for steps without physical SPDs.
- **`sky_spd_series`/`sun_spd_series` (`assemble_nvrd_rows:168-197`).** Per-timestep lists of 401-SPDs (or `None`) that override the scalar `sky_spd`/`sun_spd` row-by-row (`:190-191`) — the hook through which physical EPW-derived shapes reach the enhanced reconstruction.
- **`reconstruct_from_record` (`spectral_emit.py:30-38`).** Convenience wrapper: pulls `(sky_spd, sun_spd)` from a `SpectralSkyRecord` via `to_reference` (`spectral_emit.py:25-27`, `sky=diffuse`/`sun=direct`) and calls `reconstruct_spectrum(..., sun_spectral="colored")` — replacing the D-series/air-mass templates with physics for that timestep.
- **Opt-in `physical_sky` on `annual_nvrd` (the Live-DDS flip).** `annual_nvrd(..., physical_sky=False)` (`annual_nvrd.py:129`) defaults **off**. When `True` it builds a per-(m,d,hour-ending) record index from the EPW (`_build_record_index`, one `record_from_epw` call per unique hour-ending, `annual_nvrd.py:72-91`; `except ValueError` narrowed so a real integration break surfaces instead of hiding as 0% coverage), derives `sky_series`/`sun_series` (`_physical_spd_series:43-70`, invoked `:225-226`; a miss / synthetic-timestamp run / night-zero record all yield `None` → template; `_is_zero_record`, `:38-41`, treats a record whose spectra are all ≤1e-12 as night and excludes it from physical coverage), and feeds them into the *enhanced* path only (`:233-239`); the faithful path stays neutral. A coverage report `out["physical_sky"]` (`:264-272`) records `n_physical`/`n_template`/`coverage_pct` and carries the honest note: *"Shape-only — per-bin transport totals are unchanged. Not live-validated (no Daysim/Radiance here)."* Under partial coverage the 30° template applies only to the fallback steps; under full coverage (`full_physics`, `:273`) the `enhanced_solar_note` is suppressed because every step then carries a time-resolved physical sun. When `physical_sky` supplies a physical sky shape, the single-timestep `divergence` uses that physical sky but the **template** sun (`reconstruction_divergence` has no `sun_spd` param), flagged via `out["divergence_note"]` (`:248-252`). **Default behaviour is still the §7.5 template path; `physical_sky` is opt-in and not live-validated.**

### 7.6 ⚠️ The §9.3a constant scales R_D and does NOT cancel

The flat `(179/683)·(1/107)` constant flows **linearly** into `effective_irradiance`, then into the **nonlinear** sigmoid `1/(1+(σ/I_eff)^n)` with adaptation `2^(H−1)` where `H=log10(I·260.7)`. Unlike ELR/EDI (ratios), it does **not** cancel — so the physically-suspect `1/107` factor **biases absolute R_D**. Both methods share this (enhanced redistributes *within* bins but bin totals still come from the same channel→irradiance conversion). Hence the headline rule: **R_D is RELATIVE only** (the nvRD intensity-response was fit from nighttime electric-light studies; daytime adaptation is unvalidated). The `_RELATIVE_NOTE` (`annual_nvrd.py:15-19`) is on every return path (`relative_RD_note`, including the run=False/degraded emit return).

### 7.7 Accuracy envelope (Pierson 2023, Inanici 2023, Pierson 2021)

- Daylight mel-EDI within **±20%** of the reference; ~**9% of 6-h daylight exposures** yield significant cumulative-R_D error, concentrated in the 150–1500 lx band. Validated for neutral-colored interiors; chromatic/inter-reflecting scenes degrade. (This envelope is quoted verbatim in `_RELATIVE_NOTE`.)
- Neutral sun biases melanopic/R_D **upward** at high direct-sun fractions (direct beam ~4736 K vs ~5455 K white assumed). The colored sun targets this, and per §7.5 it is now time-resolved on a live Daysim run (constant-30° only in the degraded fallback).
- Flat reconstruction is coarse across the steep 459–558 nm melanopic bins (Pierson 2021: flat ≈ +7% vs reference). The enhanced within-bin shaping reduces it; the per-run `RD_series_divergence` quantifies it.

### 7.8 Weather & analysis-period utilities — `hcl_core/weather.py`

This module underpins two things in this cluster: the **solar-position** model that feeds the §7.5 colored sun, and the **period-subsetting** primitives that `run_annual` (§5) uses to trim a `.wea` to an analysis window.

- **`solar_zenith(*, month, day, hour, latitude, longitude, time_zone)`** (`:84-103`) — the Cooper-1969 model consumed by `_parse_wea_timestamps_and_zeniths` (§7.5): `decl = 23.45·sin(360·(284+doy)/365)`, equation-of-time `eot = 9.87·sin2b − 7.53·cos b − 1.5·sin b` with `b = 360·(doy−81)/364`, solar time `= hour + (4·(time_zone − longitude) + eot)/60`, then `cos z = sin(lat)sin(decl) + cos(lat)cos(decl)cos(hour_angle)` (clamped to [−1,1]). Returns a zenith in [0,180]° (>90 → sun below horizon). **Convention (DAYSIM):** latitude north-positive; longitude **WEST-positive**; `time_zone` = standard meridian, WEST-positive (= −15 × UTC offset). This is the exact position model `solpos.SolarGeometry` extends (`solpos.py:11,46`, zenith identical) and that §7bis's spectral pipeline mirrors — so the reconstruction path and the spectral-sky path never disagree on sun position.
- **`decompose(period, timestep_min=60)`** (`:24-58`) — verbatim `analysisPeriod` expansion: a Cartesian `month×day×hour×substep` product, so a fixed day/hour window is **repeated across each month** in the range (NOT a continuous calendar span). Reference year is the **non-leap 2010** (so month/day map 1:1); invalid days are skipped (Feb 29/30/31 and the 31st of 30-day months), and hour-24 rolls over to hour-0 of the next day via `timedelta` (datetime rejects hour 24). Returns `{months, days, hours, HOY, HOYround, wea_lines}`; the `wea_lines` key is the spec §5.11 snake_case rename of `weaLines` and holds 1-based `.wea` data-line numbers.
- **`analysis_period(from_mdh, to_mdh)`** (`:17-19`) — trivial `[[m,d,h],[m,d,h]]` constructor matching the `analysisPeriod` shape; paired with `decompose` by the annual ==caller==s.
- **`subset_wea(path, line_numbers)`** (`:60-75`) — returns a `.wea` string of the 6 header lines + only the requested 1-based data lines. It raises loudly if any line number falls outside the file's data rows (the guard is `6 < n <= len(all_lines)`, so a number landing in the 6 header lines is rejected too) — a guard that catches a `timestep_min` mismatch (wrong-resolution `wea_lines`) rather than silently emitting a wrong-timestamp subset. Consumer: `annual.run_annual` (`annual.py:119-132`).
- **`import_wea(path)`** (`:5-15`) — parses a `.wea` (skips 6 header lines) into string lists `{months, days, hours, DNI, DHI}`. Used by `_parse_wea_timestamps_and_zeniths` (`subhourly.py:14,28`) to recover per-row timestamps for the zenith computation.
- **`_day_of_year(month, day)`** (`:80-82`) with `_MONTH_CUM` (`:78`) — 1-based day-of-year in the same non-leap 2010 reference year; reused by both `solar_zenith` and `solpos` (`solpos.py:11`) so the two agree on DOY.

> Where §7 *reshapes* per-channel Radiance totals using template SPDs (D-series sky, air-mass sun), this section builds a **physical** per-nm sky from the EPW itself — a clear-sky spectral model (SPECTRL2) energy-bridged to the EPW's measured broadband DNI/DHI (SEDES1), resolved to a canonical 1nm 380–780 nm `SpectralSkyRecord`. The record feeds the same §7 consumers (reconstruct/colored-sky) and a set of artifact emitters. Two parallel engines exist: a **SMARTS** subprocess oracle and a **native Radiance `gensdaymtx`** driver — and as of 2026-06-19 the SPECTRL2-vs-SMARTS choice is **user-selectable** at the tool boundary (`engine="spectrl2"` default | `"smarts"`, §7bis.4). Everything here is pure-Python/offline except the two binary-gated engines. **The whole stack is unit-tested; of the live binary paths, both the native `gensdaymtx` driver (first live validation under Radiance 6.1a, 2026-06-20) AND the SMARTS oracle (first live run 2026-06-21 — compiled from the NREL SMARTS 2.9.5 source, gated cross-check passes, ~2–7 % agreement with SPECTRL2 at r≈0.99; see `docs/spectral-engine-comparison.md`) have now been live-validated (validations, not calibrated baselines); only the `physical_sky` DDS flip has never run live (see §7bis.11, §13).**

### 7bis.1 EPW hourly parse (`epw_hourly.py`)

`parse_epw_hourly_diagnostics` (`:63-96`) skips the **8 header lines** (`_HEADER_LINES = 8`, `:15`) and returns `(rows, {kept, dropped, reasons})` — one dict per data row plus a drop report; `parse_epw_hourly` (`:99-105`) is the backward-compatible thin wrapper returning just the row list. **Malformed rows (< 16 comma fields) or a non-integer date triple are dropped — each logged with its 1-based line number + reason, with a one-line drop-count summary when any are dropped — never silently skipped.** `_FIELDS` (`:18-31`) maps each field to its **0-based comma index + missing-sentinel**: dry-bulb 6, dew-point 7, RH 8, pressure 9 (Pa), GHI 13, DNI 14, DHI 15, total-sky-cover **22 (N22)**, opaque-sky-cover **23 (N23)**, precip-water 28, AOD 29, albedo 32. The docstring flags the classic off-by-one trap (the A1 data-source-flags **string** sits at index 5). `_num` (`:50-60`) returns `None` for absent/unparseable/sentinel values within a kept row (sentinel-equality maps to `None`), **plus a third rejection path: a physical-validity predicate** applied after the sentinel test via the `_VALID` table (`:45-47`). Today it carries one entry — **albedo must be ≥ `_ALBEDO_MIN_PHYSICAL` = 0.01** (`:41`). This exists because **IWEC/TMY2 files write a literal `0.000` in the albedo column for every hour** instead of the data dictionary's 999.0 sentinel — **4 of the 11 EPWs bundled with this repo do exactly that, Athens among them.** Nothing outdoors is a perfect absorber (fresh asphalt ≈0.04, calm deep water at high sun ≈0.03), so a value at or below the floor cannot be real. Accepting 0.0 as data silently zeroed the whole ground-reflected term **and** stamped it `source: "epw"`, claiming an instrument had measured it. A `False` verdict means "missing", so `atmosphere.derive` falls back to its documented 0.20 default and honestly reports `source="default"` (ADR-0004; the same guard is mirrored in `derive` via `resolve(..., valid=)`, §7bis.3). `row_for` (`:108-113`) linear-scans for `(month, day, hour)`. **`hour` is kept as the raw EPW hour-ENDING value (1–24)** — converting it to a mid-interval clock hour is the Phase 5 orchestrator's job (`:8-9`), not done here.

### 7bis.2 Solar geometry — the single source (`solpos.py`)

`SolarGeometry` (`:14-20`, frozen): `zenith_deg`, `azimuth_deg`, `air_mass`, `earth_radius_vector`, `day_of_year`. DAYSIM site convention throughout (latitude north-+, longitude **west-+**, `time_zone = −15·UTC`).

- **Zenith** (`compute:43-60`) is computed **identically to `weather.solar_zenith`** — Cooper-1969 declination `decl = 23.45·sin(360·(284+doy)/365)`, equation-of-time `eot = 9.87·sin2b − 7.53·cos b − 1.5·sin b`, hour-angle from solar time — so the spectral pipeline and the existing weather path never disagree on sun position.
- **Azimuth** (`:62-67`) measured clockwise from North (N=0, E=90, S=180, W=270 — the SPECTRL2 aspect convention), via `atan2` from-South then rotated +180°.
- **Air mass** (`air_mass:23-28`) — **Kasten-Young 1989** `1/(cos z + 0.50572·(96.07995 − z)^−1.6364)`, returns `inf` at/below the horizon (z ≥ 90°).
- **Earth-radius-vector** (`earth_radius_vector:31-40`) — **NREL/Spencer 1971** `(r0/r)²` correction, ~0.966–1.034; multiply ETR by this. Max near perihelion (early Jan).

### 7bis.3 Atmosphere (`atmosphere.py`)

`AtmosphericState` (`:72-81`, frozen): `aod500`, `angstrom_alpha`, `pw_cm`, `ozone_atm_cm`, `pressure_mbar`, `albedo`, a **per-field `provenance` dict** `{field: {source, method, uncertainty}}`, and `aerosol_g: float = 0.65` (aerosol asymmetry, appended last, resolved opt-in, D-7). `derive(row, *, overrides=None, ozone_mode="constant", aod_anchor_nm=None, lat_deg=None, lon_deg=None, day_of_year=None)` (`:94`) assembles it with documented defaults via the inner `resolve` helper (override > EPW value > default), tagging each field's source. `resolve` also takes a **`valid=` predicate** so a present-but-non-physical EPW value is treated as missing and falls back to the default with an honest `source="default"` — the albedo `≥ 0.01` gate of §7bis.1, mirrored here (ADR-0004). All four new keyword-only args default to values that reproduce byte-identical output.

- **Precipitable water** (`_pw_and_provenance:83-91`): **Gueymard 1994** (`gueymard94_pw:11-21`, the pvlib formulation, from temp + RH) is primary; **Reitan 1963** (`reitan63_pw:24-30`, `ln(W)=−0.0392+0.0681·Td`, dew-point only) is the fallback; a fixed 1.5 cm mid-latitude default when no humidity field is present. **The EPW precip-water column is deliberately ignored** (officially unreliable; `:97-98`).
- **Documented defaults** (`:61-68`): ozone 0.30 atm-cm (300 DU), Ångström α 1.14, AOD500 0.10 (clean-continental, pvlib default), pressure 1013.25 mbar, albedo 0.20, aerosol_g 0.65 (`_G_DEFAULT`, `:68`). EPW pressure is Pa→mbar (`÷100`); EPW AOD (usually missing) is treated as a 500 nm broadband proxy and noted in provenance (`:151-153`).
- **Ozone climatology — resolved, opt-in (D-2/ozone).** `van_heuklon_ozone(lat_deg, lon_deg, day_of_year)` (`:33-57`) implements van Heuklon (1979), Sol. Energy 22:63, Table 1, with the **hemisphere-specific** coefficients (NH F=−30 → spring-max; SH F=152.625), independently confirmed vs Karavana-Papadimou 2013 eq. 2 (bibliography §6). `ozone_mode="constant"` (default) always uses the 0.30 atm-cm literal (byte-identical); `ozone_mode="climatology"` computes it from `lat_deg`/`lon_deg`/`day_of_year` (falls back to the constant if any is `None`); an explicit `ozone_atm_cm` override always wins. `annual_records` forwards `ozone_mode` per-row using each row's own `day_of_year`, so ozone varies by season across a year.
- **Ångström AOD anchor — resolved, opt-in (D-3).** `aod_anchor_nm` Ångström-converts a declared-wavelength AOD to `tau500` (`aod500 *= (aod_anchor_nm/500.0) ** angstrom_alpha`, `:165-168`), retagging provenance `method="angstrom_from_<nm>nm"`. `None` or `500.0` is a strict no-op (`abs(aod_anchor_nm − 500.0) > 1e-9` guard) — the pre-refinement identity behavior.
- **Aerosol asymmetry — resolved, opt-in (D-7).** `aerosol_g` is now a first-class `AtmosphericState` field (default 0.65, `_G_DEFAULT`, `:68`) instead of a hardcoded engine literal; settable via `derive(overrides={"aerosol_g": …})`. `Spectrl2Engine` and the single-scatter façade colour in `receiver.py` both consume `atm.aerosol_g`.

### 7bis.4 The engine swap point (`spectral_engine/base.py`)

`ClearSkySpectra` (`:11-16`, frozen): `wavelength_nm`, `direct_normal`, `sky_diffuse_horizontal`, `units="W/m^2/um"` — engine output is **always native-grid W/m²/µm**; the µm→nm conversion is the resampler's job, never the engine's (`:4-6`). `SpectralEngine` (`:19-22`, runtime-checkable Protocol): `name` + `compute(atm, geo, *, tilt_deg=0.0, cos_incidence=None) -> ClearSkySpectra`. This is the backend swap point — `spectrl2`, `smarts`, … all satisfy it.

**User-selectable engine (added 2026-06-19).** `spectral_engine/__init__.py` exposes a one-line registry `resolve_engine(name="spectrl2", *, smarts_aerosol=None) -> SpectralEngine` (`:11-27`): `"spectrl2"` → `Spectrl2Engine()` (default, always available, ignores `smarts_aerosol`); `"smarts"` → it first calls `smarts_available()` and raises a clear `RuntimeError` *early* if `$SMARTSPATH` is unset (the SMARTS gate is in `compute()`, not its ctor, §7bis.6 — so the registry checks availability itself), else `SmartsEngine(aerosol=(smarts_aerosol or "rural"))`; an unknown name → `ValueError` listing the valid choices `_ENGINES = ("spectrl2", "smarts")` (`:8`). `native` is deliberately **not** in the registry (different output contract; own tool, §7bis.7). The MCP tools `spectral_sky_from_epw` (`server.py:1638`), `spectral_epw` (`:1684`), and `annual_nvrd` (`:1507`) take `engine="spectrl2"` and pass `resolve_engine(engine, …)` into the pipeline's existing `engine=` kwarg; `annual_nvrd` resolves **lazily** (`_resolve_engine(engine) if physical_sky else None`, `:1544` — so `engine="smarts"` never raises on a call that never uses the engine). `atmosphere_from_epw` (`:1624`) takes no `engine`/`smarts_aerosol` — its derived-atmosphere output is computed before and independently of the engine, so it is engine-invariant. Defaults are unchanged everywhere (every new parameter defaults to `"spectrl2"`). `spectral_sky_from_epw`/`spectral_epw` additionally expose `smarts_aerosol: str | None = None` — **resolved, opt-in (D-20)** — threaded into `resolve_engine`/`SmartsEngine(aerosol=…)`; default `None` resolves to `"rural"`, byte-identical to before.

### 7bis.5 SPECTRL2 — Bird & Riordan 1986 clear-sky implementation (`spectral_engine/spectrl2.py`, `_spectrl2_data.py`)

> **Source:** Bird & Riordan 1986, *Simple Solar Spectral Model for Direct and Diffuse Irradiance on Horizontal and Tilted Planes at the Earth's Surface for Cloudless Atmospheres*, J. Climate Appl. Meteorol. **25**:87; M-14…M-24.

`Spectrl2Engine.compute` (`spectrl2.py:20-99`) implements the SPECTRL2 model — per-wavelength Beer-Lambert transmittances + the single-pass diffuse decomposition (Bird & Riordan 1986 / SERI/TR-215-2436). Solar geometry is **passed in** (no native solpos). Constants from the Bird & Riordan 1986 / NREL `spectrl2_2.c` reference tables: Rayleigh `115.6406 − 1.3366/λ²` (`:59`), uniform-gas `118.3` (`:62`), single-scattering albedo `ω=0.945`/`ωP=0.095` (`:13-14`); the aerosol asymmetry (a rural-default `0.65`) is **no longer a `:36` literal — it is now read from `atm.aerosol_g`** (`:36`, D-7, §7bis.3). Direct normal `H0·To·Tw·Tu·Tr·Ta` (Eq 2-1, M-19, `:74-76`); diffuse-on-horizontal = Rayleigh `dray` (Eq 3-5, M-22) + aerosol `daer` (Eq 3-6) + ground multi-reflection `drgd` (Eq 3-7) × the `Cs` forward-scatter factor (Eq 3-17), `:80-85`. A tilt branch (`:87-93`) exists only to reproduce the tilted Fortran golden (ground + beam-correlated + isotropic). **Night guard** (`:24-28`): z ≥ 90° / cz ≤ 0 / non-finite air mass → all-zero spectra.

`_spectrl2_data.py` is the **122-wavelength coefficient table** (generated from the bundled `SPCTRAL2_TAPE2.txt`, identical to `spectrl2_2.c`'s `A[5][122]`): `WL_UM` (0.3–4.0 µm, `:5-27`), `ET_H0` extraterrestrial irradiance (`:29-51`), and water-vapor / ozone / uniform-mixed-gas absorption columns `ABS_H2O`/`ABS_O3`/`ABS_UMG` (`:53-75`/`:77-99`/`:101-123`). Each column is length 122 (verified). *(Note: the table actually spans 0.3–4.0 µm = 300–4000 nm; `base.py`'s comment "300–4000nm" is right, but `spectral_sky.py`'s provenance string `"spectrl2_122pt"` describes the point count, not a 380–780 span — the resampler narrows to 380–780.)*

### 7bis.6 SMARTS — the validation oracle / selectable engine (`spectral_engine/smarts.py`)

`SmartsEngine` (`:134-170`) is the high-accuracy oracle slot — and, since 2026-06-19, a **user-selectable engine** (`engine="smarts"`, resolved via §7bis.4's `resolve_engine`). **Capability-gated:** `smarts_available()` (`:17-20`) returns `True` only when `SMARTSPATH` names a runnable executable; `compute` (`:140-170`) raises `RuntimeError` otherwise — *so green pytest does NOT imply a live SMARTS run* (`:6-7`). SMARTS emits **W/m²/nm**, so `compute` `×1000` to the engine-uniform W/m²/µm (`:167-170`). `compare_engines` (§7bis.10) is the cross-engine harness.

### 7bis.7 The SEDES1 cloud bridge (`cloud_modifier.py`, `_sedes1_data.py`, `sedes1_fit.py`)

> **Source:** Nann & Riordan 1991, *Solar Spectral Irradiance under Clear and Cloudy Skies*, J. Appl. Meteorol. **30**:447 (CCM Eq. 11; M-25…M-29).

`Sedes1Modifier.apply` (`cloud_modifier.py:129-155`) — Nann & Riordan 1991 — has **two halves**:

1. **Energy-rescale (always on — the "bridge invariant").** `energy_normalize` (`:46-64`), over the shared trapezoid `broadband_integral` (`:37-43`) that `build_record`'s bridge residuals and `clearsky_bias` also use, grey-scales the clear-sky direct/diffuse so their **full-native-range** trapezoidal broadband integrals equal the EPW's measured DNI/DHI: `k_dir = DNI/∫direct`, `k_dif = DHI/∫diffuse`. Done on the native W/m²/µm grid **before** any narrowing to 380–780. This is the exact, validated half — it forces ∫direct = DNI and ∫diffuse = DHI.
2. **CCM diffuse reshape (shape-only).** Multiply diffuse by `CCM(λ,Kt) = A(λ) + B(λ)·Kt + C(λ)·Kt²` (`_ccm`, `:115-127`) — under the default `reanchored` variant this is divided by `CCM(λ,0.70)` so it is unity at the clear `KT_CLEAR` (a pure cloud modifier) — then **renormalize diffuse back to DHI** (`apply`, `:129-155`) so the bridge invariant survives the reshape. `clearness_index` (`:29-34`) is `Kt = GHI/(I0_normal·cos z)`, clamped [0, 1.2]. When `kt is None` the CCM is skipped entirely (grey fallback, `ccm_applied=False`, `ccm_basis="grey-fallback"`, `:114-122`) — the always-on energy-rescale still guarantees broadband correctness.

`_sedes1_data.py` loads a **faithful Fig. 11 digitization** (`_sedes1_fig11.csv`, A/B/C/σ on a 10 nm grid **330–1100 nm**, produced by a human-in-the-loop WebPlotDigitizer pass — see `docs/Coefficient provenance/`), exposed via `ccm_coeffs(wl_nm)` (`:52-58`, verbatim with `(1,0,0)` pass-through outside 330–1100 nm) and `ccm_sigma(wl_nm)` (`:61-65`, the per-λ regression standard error, `0.0` outside range). The legacy eyeballed **9-anchor seed** (`SEED_WL_NM = [350,400,450,500,600,700,800,950,1050]` nm, `:13`) is **retained only for the `seed` variant** (`seed_coeffs`, `:68-72`), not the production default. A separate module, **`sedes1_fit.py`**, lets a ==caller== locally re-fit A/B/C/σ from measured spectra and write drop-in coefficients: `fit_ccm(spectra, kt_values, reference_shapes, wavelength_nm)` (`:48-70`) does a per-wavelength quadratic least-squares (pure-Python normal equations, `_quad_fit`/`_solve3`, `:10-45`) of the **normalized diffuse shape-ratio** `r = (s/∫s)/(c/∫c)` (measured diffuse `s` vs a clear-sky reference `c`) against Kt, returning `{"wavelength_nm","A","B","C","sigma"}` (σ is the regression std error, `0.0` when <4 points); `write_ccm_csv`/`load_ccm_csv` (`:73-117`) round-trip the same CSV schema (`wavelength_nm,A,B,C,sigma`), `load_ccm_csv` returning `(coeffs_fn, sigma_fn)` interpolators with `(1,0,0)`/`0` pass-through outside range — consumed by the `local` variant below.

> **Source:** Nann & Riordan 1991, Fig. 11 (A/B/C coefficients — figure-digitized via WebPlotDigitizer; **no table in that paper**). approximate — the faithful digitization gives B(400 nm) = **−2.037** (`_sedes1_fig11.csv`), not the old seed's B(400) = −3.55, which was materially too steep; the paper's published B ≈ −3.5 cross-check is actually near the ~340–345 nm value (B(340) = −3.877 in the digitization). ⚠️ **"No published table *anywhere*" is retired** — Whitaker & Newmiller 1998 (NREL/SR-520-23942 Table 2-1) tabulates the same regression, and ships here as the opt-in `Sedes2Modifier`; see the SEDES2 treatment in §7bis.7a below.

`Sedes1Modifier` (`cloud_modifier.py:73-155`) ships **four variants** (validated at construction, `:102-103`): `reanchored` (**default**) — `CCM'(λ,Kt) = CCM(λ,Kt) / CCM(λ,0.70)`, a pure cloud modifier (unity at the clear `KT_CLEAR = 0.70`; the clear-sky-engine bias is handled separately by the clear-sky-bias layer); `verbatim` (the faithful Fig. 11 CCM as published, un-reanchored); `seed` (the legacy 9-anchor approximation, over-blues ~2×, kept for comparison); and **`local`** — ==caller==-injected `coeffs`/`sigma` (typically from `sedes1_fit.load_ccm_csv`), reanchored the same way as `reanchored` (unity at clear Kt), requiring `coeffs` at construction (`ValueError` otherwise, `:104-105`). The module's own caveats: the paper *fits* CCM to **global** spectra but this implementation *applies* it to the **diffuse** (an approximation the paper does not validate; over-weights blueing slightly), and PWV is not a shape driver here (Kt is the sole driver; the ~940 nm PWV signature is outside 380–780). **Only the energy-rescale is exact; the CCM shape is figure-digitized** (or, for `local`, locally re-fitted — still shape-only, now σ-quantified). Provenance is **variant-aware** (`_BASIS` table `:94-99`, applied in `apply`'s `info.update`, `:134-137`): `reanchored`/`verbatim` carry `ccm_basis="fig11-faithful"`/`coeff_method="webplotdigitizer_fig11"`; `seed` carries `"seed-9anchor"`/`"eyeballed_seed"`; `local` carries `"local-fit"`/`"local_recalibration"` plus `ccm_source` (the CSV path/fit metadata passed as `source=`, `None` for the other variants). All variants additionally carry `ccm_sigma` (dict at 400/500/600/700 nm via `_sigma_summary`, `:111-113`) and `ccm_sigma_mean` — the Fig. 11 (or local-fit) regression σ, exposed but not yet propagated into downstream uncertainty bars — alongside `ccm_variant=<variant>`. At the MCP boundary, `spectral_sky_from_epw`/`spectral_epw` expose this as `cloud_variant`/`ccm_coeffs` (a fitted CSV path, required for `cloud_variant='local'`), threaded through the existing `modifier=` pipeline param with no signature change (`server.py:_build_modifier`, `:1603-1621`); `atmosphere_from_epw` is unaffected. *(Full sourcing investigation and the variant comparison: [`spectral-sky-methodology.md` §8.6](spectral-sky-methodology.md); recalibration how-to: [`docs/recalibrating-cloud-ccm.md`](recalibrating-cloud-ccm.md).)*

### 7bis.7a SEDES2 — the tabulated cloud modifier (`Sedes2Modifier`, opt-in, NOT the default)

> **Source:** Whitaker, C.M. & Newmiller, J.D. (1998), *Photovoltaic Module Energy Rating Procedure — Final Subcontract Report*, **NREL/SR-520-23942, Table 2-1, pp. 19–20** — 74 rows, 320–1050 nm at 10 nm, a US Government contractor report distributed without copyright restriction. Its p. 20 states the coefficients "were derived from measured data using statistical analyses as described by Nann and Riordan, 1991", so this **is** a tabulation of the regression §7bis.7's coefficients approximate from a figure. Retrieved and read from the primary PDF; four rows spot-checked against a visual read of the rendered page (320, 640, 760, 1050 — 640 and 760 being the two the text-layer OCR damaged). The retrieval-and-transcription provenance record is held in an internal validation tree that is not part of this repository; the shipped values live in `src/hcl_core/_sedes2_data.py` and are pinned against the primary source by `tests/test_sedes2.py`.

`Sedes2Modifier` (`cloud_modifier.py:158-229`) is a **separate class, not a `Sedes1Modifier` variant**, because the model form differs in two structural ways:

$$\mathrm{CCM}(\lambda, \mathrm{NGH}, z) = \Big(A_1 + \tfrac{A_2}{\cos z}\Big) + \Big(B_1 + \tfrac{B_2}{\cos z}\Big)\mathrm{NGH} + \Big(C_1 + \tfrac{C_2}{\cos z}\Big)\mathrm{NGH}^2$$

1. **Six coefficients with a 1/cos z zenith term** (`_ccm`, `:187-195`). SEDES1's three-term $A+BK_t+CK_t^2$ cannot express this, so there the zenith dependence is absorbed into A/B/C.
2. **The independent variable is NGH, not $K_t$.** `normalized_global_horizontal` (`:13-27`) computes NGH = measured GHI ÷ **estimated clear-sky** GHI, clamped to `[0, 1.5]`, versus `clearness_index` (`:29-35`) dividing by the **extraterrestrial** horizontal. Under clear sky NGH → 1 while $K_t$ → ~0.7 — **not interchangeable even approximately**.

**It refuses rather than guesses.** `apply` (`:197-229`) takes an extra `clear_ghi=None` kwarg; when NGH is unavailable (no clear-sky reference, or `ghi is None`) **or** `cos_z ≤ 0.05` (where 1/cos z diverges), it returns the energy-normalised spectrum with a **grey unity CCM** and `ccm_applied=False`, rather than evaluating the polynomial on the wrong variable. `sedes2_coeffs` (`_sedes2_data.py:131`) linearly interpolates the 10 nm table and **clamps** outside 320–1050 nm instead of extrapolating.

**Provenance:** `cloud_model="sedes2"`, `ccm_basis="whitaker1998-table2-1"`, `coeff_method="tabulated"`, `ccm_source="NREL/SR-520-23942 Table 2-1"`, `ccm_variant="reanchored"|"verbatim"` (the `reanchor=True` default divides by the modifier's own NGH=1 clear value, matching how the SEDES1 default is made a pure cloud term). ⚠️ `ccm_sigma`/`ccm_sigma_mean` are **`None`** — the tabulated source publishes no per-coefficient regression σ, unlike the Fig. 11 digitization.

⚠️ **Opt-in by construction and NOT reachable over MCP.** Nothing in `src/` constructs it, so every figure computed with the SEDES1 default stays **byte-identical**; `server.py:_build_modifier` accepts only `reanchored`/`verbatim`/`seed`/`local`, all of which build a `Sedes1Modifier`. Using SEDES2 means constructing the class directly in Python **and** supplying the clear-sky GHI it needs. It is **not validated against the Athens dataset**; adopting it changes overcast colour and requires a re-run before any overcast number is re-quoted. ⚠️ The 1040 nm and 1050 nm rows are **byte-identical in Table 2-1** (verified in the source PDF, not a transcription artefact).

### 7bis.8 The canonical record + the µm→nm boundary (`spectral_sky.py`)

`SpectralSkyRecord` (`:19-28`, frozen): `timestamp`, `grid_nm` (`GRID_NM` = 380..780 @1nm, 401 pts, `:16`), `direct_normal`/`sky_diffuse_horizontal` (**W/m²/nm**), `broadband` (`{dni,dhi,ghi,clearness_kt}`), `atmosphere`, `geometry`, `provenance`.

- **`resample_to_1nm` (`:48-56`) is the ONE place the µm→nm conversion lives** — linear-interpolate the native grid onto `GRID_NM`, then **×0.001** to convert W·m⁻²·µm⁻¹ → W·m⁻²·nm⁻¹.
- **`build_record` (`:76-134`)** is the per-timestep orchestrator: `engine.compute` (tilt 0 → horizontal sky-truth) → optional `clearsky_correction.apply` (§7bis.12 K(λ), when a correction is passed, `:105-107`) → `modifier.apply` (energy + CCM, native grid) → `resample_to_1nm` → record. Bridge scale factors `k_dir`/`k_dif`, bridge/GHI residuals (`ghi_epw_residual` = `(dni·cos z + dhi) − ghi`), and the CCM provenance (`ccm_basis`/`coeff_method`/`ccm_source`/`ccm_applied`/`ccm_sigma`/`ccm_sigma_mean`) land in `provenance` (`:118-130`). The signature carries an optional `clearsky_correction=None` kwarg (`:76`).
- **Night/twilight handling (`:83-103`).** `night = zenith ≥ 90° or cos z ≤ 0` (`:83`). A night record is all-zero, but the provenance flags `night_but_epw_nonzero` when the **mid-interval geometry reads below-horizon while the hour-ending EPW row still carries radiation** (the twilight edge) — the dropped energy is auditable, not silent (`:88-92`).
- **`ground_for_receiver` (`:59-73`)** = `spectral_GHI(λ)·albedo(λ)·(1−cos tilt)/2`, where `spectral_GHI = direct·cos z + diffuse`. Both `surface_tilt_deg` and **`spectral_albedo` are keyword-only and REQUIRED** — the albedo is a per-λ 401-value array, not a scalar (tilt=0 → zeros; tilt=90 → half). This is the **spectral ground-glow input for the Radiance path**, not a standalone receiver irradiance (Radiance transport does the sky transposition); isotropic ground, so no orientation argument.

### 7bis.9 EPW→record orchestration (`spectral_pipeline.py`)

`record_from_epw(epw_path, month, day, hour, *, engine=None, modifier=None, overrides=None, ozone_mode=None, aerosol_g=None, aod_anchor_nm=None, return_diagnostics=False)` (`:18-58`) and `annual_records(epw_path, *, engine=None, modifier=None, hours=None, overrides=None, ozone_mode=None, aerosol_g=None, aod_anchor_nm=None, return_diagnostics=False)` (`:61-99`) chain Phases 1–3: parse the hourly row + LOCATION header → `atmosphere.derive` → `solpos.compute` **at the mid-interval hour** (`hour − 0.5`, because EPW is hour-ending, `:43`/`:86`) → `build_record`. The atmosphere-refinement kwargs (`ozone_mode`/`aerosol_g`/`aod_anchor_nm`, plus `overrides`) pass straight through to `atmosphere.derive` per row (`aerosol_g` merges into `overrides` with precedence, `:47-48`/`:90-91`); `return_diagnostics=True` additionally returns the EPW parse drop report `{"kept","dropped","reasons"}`. `i0_normal = 1361·ERV` (`:55`/`:95`) — the modern WMO solar constant `_SOLAR_CONSTANT = 1361.0` (`:12`), used **only** to normalize Kt; deliberately decoupled from each engine's internal ETR (SMARTS keeps its native 1367, SPECTRL2 has its `ET_H0` table — different roles, not a bug, `:13-15`).

### 7bis.10 Consumers, artifacts, validation (`spectral_emit.py`, `spectral_validate.py`)

`spectral_emit.py` feeds both the legacy reconstruction and a set of archival artifacts:

- **`to_channels(record, channel_type)` (`:18-22`)** — bin the record's diffuse/direct into 3/9-channel vectors for `colored_sky`.
- **`to_reference(record)` (`:25-27`)** — return `(sky_spd, sun_spd)` 401-value reference SPDs (sky=diffuse, sun=direct) for `reconstruct_spectrum`, **replacing the D-series/air-mass templates with physical spectra**. (`reconstruct_from_record`, `:30-38`, is the wrapper — see §7.5a.)

### 7bis.11 Native Radiance gensdaymtx driver (`hcl_radiance/spectral_native.py`)

The parallel **native Radiance 6.x** spectral engine — `gensdaymtx` EPW → 20-band spectral sky matrix — capability-gated to emit-or-run.

- **`build_gensdaymtx_cmd` (`:16-31`)** uses **only implemented flags** (the binary's usage string advertises non-existent `-c/-O/-A/-D/-M` that abort the run, `:5-6`): `-m mf`, mode `all`/`sun(-d)`/`sky(-s)`, `-g <scalar>`, `-o<fmt>`. **`ground_refl` is a single scalar gray reflectance, NOT an r/g/b tuple** (`:18-20` cites `gensdaymtx.c:647-648 case 'g': grefl = atof(...)`, default .2) — a defect caught against the bundled Radiance source (an earlier spec had specified r/g/b). A `TypeError` guard enforces scalar (`:27-28`).
- **`parse_smx_header` (`:61-102`)** reads NCOMP/NROWS/NCOLS + the `WAVELENGTH_SPLITS` record, stored under `rgb_partition`. **`WAVELENGTH_SPLITS` is the legacy 4-value RGB+UV/IR partition `WLPART[4]={780,588,480,380}` (common/color.c:94, printed via gensdaymtx.c:917), NOT a band-edge list** — the second such source-vs-spec defect (the 20 spectral bins are a *separate* uniform grid). The `#?RADIANCE` magic / blank lines and matrix body rows (no `=`) are skipped (`:82-85`).
- **The native spectral grid is `NSSAMP=20` uniform bins over 380–780 nm** (`:150-156`, citing `gen/atmos.h:17`, `gen/atmos.c:164,169` in the bundled source; START_WVL=390 / END_WVL=770 are bin *centers*). `reconcile_to_native_bands` (`:195-220`) re-bins a 401-pt 1nm spectrum onto `ncomp` equal-width bins **derived from NCOMP, not the RGB partition**. For the default ncomp=20 this uniform grid **IS** `spectral_emit.band_average`'s `BAND_EDGES_20` — so reconciliation *reproduces* the nominal grid exactly (`:202-206`): the spec §8 "byte-compat gap" feared between the native grid and the nominal 20-band grid **does not exist** for matching ncomp/span.
- **`run_gensdaymtx` (`:113-147`)** is run-or-emit: on absent Radiance 6.x it returns `{ran:False, commands:[gensdaymtx…, rcomb -c <S 026 coefficients>…], reason}` (the second command comes from `build_rcomb_melanopic_cmd`, below — **not** `-c M`; the reason notes `mie_ca.dat` must be on `RAYPATH`); on run it writes `sky_spectral.smx` and parses the header. **`timeout` param (default `None` = no cap; added 2026-06-21):** `gensdaymtx` processes every EPW hour, but a full 8760-hour year at mf=1 (NROWS=146, NCOMP=20) is **fast — ~12 s wall / ~10 s CPU on Radiance 6.1a (measured 2026-06-29)**; cost grows steeply with the Reinhart subdivision mf (**minutes at mf≥4**), which is why the cap is ==caller==-supplied. The previous hard-coded 600 s cap raised `TimeoutExpired` and crashed the call on a high-mf run, so the cap is now ==caller==-supplied and expiry returns a discriminable `{ran:True, ok:False, timed_out:True, …}` dict rather than raising (as-built D-29). `radiance_spectral_status` (`:105-110`) probes `gensdaymtx`/`rcomb` on PATH.

> **`build_rcomb_melanopic_cmd` (`:34-58`) deliberately does NOT use `rcomb -c M`.** That flag returns equal-energy-normalised **"melanopic lux"** (the EML-style quantity), **not** CIE S 026 mel-EDI: `util/rcomb.c:269-271` applies `scolor2melanopic * WHTMELANOPIC`, and `common/color.h:276` defines `WHTMELANOPIC 179.` — identical to `WHTEFFICACY`, i.e. Radiance's photopic convention. This is Radiance behaving as documented (`rcomb.1:150` states the 179 lm/W factor and calls the output melanopic lux), **not** a Radiance defect; the defect was *ours*, consuming EML as if it were mel-EDI. Verified live 2026-07-17 on a D65 spectrum in **descending** band order: `-c M` reads **1.081× true mel-EDI** (8.1% high) and `-c M`/`-c Y` = 1.098. S 026 requires mel-DER(D65) = 1 exactly, so the command instead passes **explicit numeric S 026 coefficients** (`s026_melanopic_coefficients`, `:164-192`, using `K_MEL_D65 = 1.3262e-3` at `:161` over `NATIVE_LO_NM`/`NATIVE_HI_NM` = 380/780), which `rcomb` applies as a plain dot product over the components in file order. ⚠️ Band order is load-bearing: feeding *ascending* components reads 0.774 — Radiance's symbolic path indexes `scol[ncs-1-n]` (`spec_rgb.c:280`), i.e. it assumes descending. Getting that backwards fabricates a spurious ~23% error. **First live validation 2026-06-20 under Radiance 6.1a** (`/usr/local/radiance/bin`): `run_gensdaymtx(..., run=True)` → `ran=True, ok=True`; header `NCOMP=20` (NROWS=146 patches). The 20-band native spectrum agrees with the offline Python SPECTRL2 engine within a loose envelope — per-band normalized mean ~2.5%, Pearson correlation **0.987**, mel/phot native 0.987 vs Python 1.015, no inversion. Validation, not a baseline (native W/sr/m² vs Python W/m²/nm are incommensurable; absolute broadband not asserted). **Band-order note:** the `.smx` body stores its 20 components *descending* in wavelength (red→blue, per `WAVELENGTH_SPLITS = 780 588 480 380`); reverse (`[::-1]`) to ascending 380→780 before use (`parse_smx_header` docstring, `:69-76`). Only the test helper `_native_band_vector_for_hour` does this reversal today; no production code reads the `.smx` body yet.

### 7bis.12 Internal spectral-sky helper modules (non-tool)

These pure-Python `hcl_core` modules support the physical-sky pipeline and are **not exposed as MCP tools**. Two form the anisotropic "Layer A magnitude × Layer B colour" façade model (`perez_distribution.py` → `sky_radiance.py` → `receiver.py`); the rest are validation/deconfounding utilities. All are consumed by `receiver.py` and the test suite; none is on the default `spectral_sky_from_epw` path unless a non-`isotropic` mode is explicitly requested.

> **Source:** Perez, Seals & Michalsky 1993, *Sol. Energy* 50:235 (all-weather sky). Layer A is a pure-Python port cross-checked against the **bundled Radiance `gen/gendaylit.c`** (coefficient array, epsilon bins, and the `l(ζ,γ)` form). Layer B single-scatter colour is a first-order construction, not an external standard.

**`perez_distribution.py` — Layer A (achromatic angular magnitude).** Supplies the angular *brightness* envelope only; colour rides on top in `sky_radiance.py`, and no engine internals are touched.

- `PEREZ_COEFF` (`:30-33`) is the `coeff_perez[]` array reshaped `[bin][param][term]` (8 ε-bins × 5 params a…e × 4 terms), transcribed **verbatim** from `gendaylit.c:27` into the flat tuple `_FLAT` (`:12-29`). `SOLAR_CONSTANT_E = 1367.0 W/m²` (`:35`, the gendaylit value used for Δ).
- `air_mass(zenith_deg)` (`:38-41`) — Kasten 1965 relative optical air mass (cites `gendaylit.c:1506`), zenith clamped to ≤90°.
- `sky_clearness(dni, dhi, zenith_deg)` (`:44-50`) — Perez ε (cites `gendaylit.c:1236`); `dni` is direct **normal**, `dhi` diffuse horizontal; returns 1.0 when `dhi ≤ 0` (overcast/night guard).
- `sky_brightness(dhi, zenith_deg, eccentricity=1.0)` (`:53-55`) — Perez Δ (cites `gendaylit.c:1225`).
- `_numlin(epsilon)` (`:58-64`) maps ε to bin 0…7 via the seven published thresholds (1.065/1.230/1.500/1.950/2.800/4.500/6.200).
- `perez_params(zenith_rad, epsilon, delta)` (`:67-81`, cites `gendaylit.c:1359-1371`) returns the five luminance coefficients; the **bin-0 branch** (`:76-81`) applies gendaylit's special `exp`-of-`pow` forms for c and d, and the `1.065<ε<2.8 ∧ δ<0.2 → δ=0.2` floor (`:69-70`).
- `relative_luminance(zeta_rad, gamma_rad, zenith_rad, epsilon, delta)` (`:84-92`, cites `gendaylit.c:1374`) is the `l(ζ,γ)=(1+a·e^{b/cosζ})·(1+c·e^{dγ}+e·cos²γ)` form, with `cos ζ` floored at 0.01 to avoid the horizon singularity (`:89-90`).

**`sky_radiance.py` — Layer B (per-direction spectral colour).** A single-scattering colour ratio that *rides on* Layer A's magnitude; it does not carry the magnitude itself and, by construction, does not change the engine's baseline diffuse colour.

- Physics (module docstring): colour anisotropy arises **only** from the Rayleigh-vs-aerosol ratio varying with scattering angle Θ — Rayleigh is λ⁻⁴ blue-rich and peaks 90° from the sun; the aerosol Henyey–Greenstein lobe is warm and forward. `rayleigh_phase` (`:19-21`) = ¾(1+cos²Θ); `hg_phase` (`:24-26`) = (1−g²)/(1+g²−2g·cosΘ)^{1.5}.
- `_patch_spectrum(theta_deg, wavelengths_nm, aod_ratio, g)` (`:29-39`) — un-normalized single-scatter spectrum per patch = `(550/λ)⁴·rayleigh_phase + aod_ratio·(550/λ)¹·hg_phase`.
- `color_ratio_field(wavelengths_nm, sun_alt, sun_az, *, aod_ratio, g=DEFAULT_G, eta=None)` (`:42-59`) — the per-patch colour-only ratio, shape `145 × len(wl)`, cosine-weighted **dome-mean-normalized to 1** (`:52-54`, via `R.integrate_diffuse … /π`) and **damped toward isotropy** by η: `1 + η·(ratio−1)` (`:58`).
- **Constants / honesty flags:** `DEFAULT_G = 0.65` (`:12`, aerosol HG asymmetry, typical continental). `DEFAULT_ETA = 0.5` (`:13-16`) is **the one fitted, tunable knob** — it damps the first-order single-scatter ratio, which omits multiple-scattering graying and overshoots. ⚠️ η is **empirical**: it was fitted against an internal dataset that is not published with this toolkit, and the fit constrains it to an **interval, η ∈ [0.19, 0.69]**, not a point. Any claim that η is "fitted" must carry the interval rather than imply a point estimate. `eta=None` resolves to the **live** module-level `DEFAULT_ETA` at call time (`:46-47`), so ==caller==s that leave it unset track the fitted constant rather than a value frozen at import.

**`receiver.py` — anisotropic-diffuse façade projector.** Optional consumer of a `SpectralSkyRecord`; promotes the Reinhart/Tregenza **MF:1** sky dome + cosine-weighted integrator out of the engine-comparison scripts into `src/` so production and the validation analysis share one integrator. Engines and the record are untouched.

- Dome: `ROW_COUNTS = [30,30,24,24,18,12,6,1]` → `N_SKY = 145` (`:17-18`), with `BAND_CENTRE_ALT = [6,18,30,42,54,66,78,90]` and `_band_edges` (`:19-22`) giving the 12°-wide altitude bands (the last capped at 84–90°); `build_dome` (`:28-45`) builds the 145 patches (row/band/alt/az/theta/omega/**cw** cosine-weight) with the same geometry as `patch_geometry.build_dome`; module-level `DOME` (`:48`).
- `integrate_diffuse(values, dome=DOME)` (`:51-55`) — cosine-weighted dome integral Σ value·cw; **unit radiance integrates to π** (gate G1), and it raises on a patch-count mismatch.
- `facade_cos_inc(patch_alt, patch_az, surface_az, tilt=90.0)` (`:58-65`) signed incidence cosine; `scattering_angle_deg(...)` (`:68-73`) great-circle patch↔sun angle.
- `_isotropic_facade` (`:76-83`) — today's default behaviour: horizontal-diffuse **shape** scaled by the isotropic view factor `vf = Σ max(0,cos_inc)·omega` (= π/2 for a vertical façade), so an isotropic vertical façade gets DHI·(vf/π) and **colour is unchanged**.
- `_eps_delta(record)` (`:86-97`) derives Perez ε/δ from broadband DNI/DHI when present. **Honesty guard:** it tests `dni is not None and dhi is not None and dhi > 0` (`:95`) — `dni==0.0` with `dhi>0` is a *valid overcast* reading, not missing data, and a truthiness test would push overcast hours into the clear-sky fallback (exactly backwards). The documented fallback when broadband is absent is `(6.5, 0.12)` (`:97`, the highest/clearest bin).
- `_anchored_facade` (`:100-128`) builds per-patch spectra = base colour × Layer-A relative luminance × (Layer-B colour ratio if present), then **anchors** the cosine-weighted dome integral to reproduce the record's horizontal diffuse at each wavelength (`:120-124`) before projecting onto the façade normal.
- `oriented_diffuse_for_receiver(record, *, surface_az, tilt=90.0, mode="isotropic")` (`:131-143`) is the public entry, returning a 401-value oriented-façade diffuse SPD. Modes: **`isotropic`** (default, single colour), **`perez`** (Layer A magnitude, single colour), **`single_scatter`** (Layer A × Layer B colour). The `single_scatter` branch (`:137-142`) feeds Layer B `aod_ratio = max(0.05, record.atmosphere.aod500 · 2.0)` and `g = record.atmosphere.aerosol_g`. Unknown modes raise. **Scope:** exercised only by the test suite (`tests/test_receiver.py`, `tests/test_sky_radiance.py`); not wired to a live Radiance transport.

**`skyspectra.py` — SKYSPECTRA external cross-check reader.** Streaming reader for the SKYSPECTRA dataset (Zenodo 8147546, CC BY-NC-ND 4.0), used as an **external spectral cross-check**. Long-format CSVs (one row per timestamp×wavelength, or ×patch×wavelength); the patch file is 1.4 GB so everything streams (rows sharing `(location, timestamp[, patch])` are contiguous, buffering ≤1 group). **Raw data is git-ignored and not redistributed.**

- `GRID_NM = range(380, 781)` (401, `:9`).
- `to_grid(pairs)` (`:12-38`) sorts `(wl, value)` pairs and linear-interpolates/clips onto GRID_NM; blank/non-numeric values are dropped (the patch file carries blank-radiance rows), and an all-blank spectrum returns zeros rather than raising (`:16-18`).
- `iter_horizontal(path, location)` (`:48-66`) yields `(timestamp, spd(401), cct_horizontal_or_None)` per `(location, measurement_setup)` group.
- `iter_patch_sets(path, location)` (`:69-101`) yields `(timestamp, [patch dicts])` where each patch = `{patch, almucantar, azimuth, cct, spd(401)}`, preserving first-seen patch order.
- `load_meta(path)` (`:104-110`) loads the small metadata CSV into a dict keyed by `(location_code, timestamp, measurement_setup)`.

**`glazing.py` — representative glazing transmittances, for deconfounding an SPD that genuinely passed through glass.**

- **Honesty flag (module docstring):** the curves are **REPRESENTATIVE / parametric**; they are used as a *sensitivity band* (clear→single→double coated, increasing warm tilt), not a single ground truth. `KINDS = ("clear","lowE_single","lowE_double")` is retained — those remain valid kinds a *caller* may choose to model. `ASSUMED_UNCOATED_DOUBLE_VT = 0.80` (`:31`) is an **assumption a caller may override, not a measurement**: the transmittance was never measured and no product datasheet exists. Plain uncoated double runs nearer 0.78–0.82 τv. Any result sensitive to it must state the value used.
- `_raw_shape(kind, wl)` (`:16-22`): `clear`→1.0 (flat), `lowE_single`→0.85+0.15·t, `lowE_double`→0.70+0.30·t, where t = (wl−380)/400.
- `_visible_transmittance(trans)` (`:25-29`) — photopic VT = Σ T·D65·V / Σ D65·V, using `V_LAMBDA`/`D65_ELR` from `hcl_core.data`.
- `transmittance(kind, target_vt=ASSUMED_UNCOATED_DOUBLE_VT)` (`:51-65`) renormalizes each shape so its VT equals `target_vt`, then clamps ≤1. An **assert** fires if any scaled value exceeds 1 — guarding against a future warming of `_raw_shape` that would make the clamp silently distort the VT normalization (inert today; peak ~0.90).
- `deconfound(spd_pairs, kind, target_vt=ASSUMED_UNCOATED_DOUBLE_VT)` (`:68-`) divides a measured `(wl, value)` SPD by the glazing transmittance → the sky-side relative SPD; note the **detector/instrument response is NOT removed**. ⚠️ Valid only for an SPD that genuinely passed through glass.

**`clearsky_bias.py`** — the optional clear-sky engine-bias correction `K(λ)` (**default OFF / opt-in**): a per-engine spectral warming that renormalizes so broadband diffuse is unchanged (shape-only), applied only when explicitly constructed enabled and passed to `build_record` (inserted **before** the cloud modifier — architecture invariant). ⚠️ K(λ) is **empirical**: the shipped curve was derived from an internal measured dataset that is not published with this toolkit, against the engine's own clear prediction, both unit-area normalised. It is applied **shape-only**, so that dataset's absolute scale never enters the correction.

> **⚠️ It is keyed PER ENGINE and no-ops silently for any engine it has no artifact for.** `_ART` (`:21`) maps only `"spectrl2"` → `_clearsky_K_spectrl2.csv`. The constructor loads `([], [])` for any other engine name, and `apply` (`:52-55`) then returns the input unchanged with `{"clearsky_corrected": False, "engine": …}`. So **`engine="smarts"` plus an enabled correction yields no correction and no error** — the honest report is in the returned provenance, not an exception. Check `clearsky_corrected` before assuming a correction was applied.

## 8. Electric lighting — `hcl_core/{ies,lighting_controls}.py`, `hcl_radiance/ies_radiance.py`

### 8.1 IES photometry (`ies.py`) — IESNA LM-63

> **Source:** ANSI/IES LM-63, *Standard File Format for the Electronic Transfer of Photometric Data* (H-23…H-26).

Tolerant parser handling keyword block, `TILT=NONE/INCLUDE` (the embedded tilt block is **consumed** so data-line-1 indexing doesn't shift; carried un-applied in `tilt_block`), data lines 1 (10 fields) & 2 (3 fields — `pfactor` correctly captured, not "future_use"), and a flat number-stream for the angle/candela grid (tolerant of arbitrary line-wrapping).

**Effective candela** = `raw · candela_multiplier · ballast_factor · pfactor` (the LM-63 rule; the same product ies2rad applies). This is applied once up front (`replace(ies, candela=…)`) and surfaced via `candela_scale_applied`; an earlier version ignored the multiplier so every fixture used 1.0 and all unit tests missed it.

Derived photometry (hand-verified on the synthetic fixture): `rated_lumens = num_lamps·lumens_per_lamp`; `efficacy = rated/watts`; **zonal flux** `ΔΦ = Ī·2π·(cos v₁ − cos v₂)` (mid-point solid-angle integration over the file's *actual* vertical extent, with a **90° hemisphere split** so down/up flux is apportioned correctly; cos is additive across the split, so `total_flux` is preserved); **beam angle** = full vertical angle at 50% peak, **field angle** at 10% peak (symmetric one-sided interpolation, returns 2·half-angle, half capped at 90° so full ≤ 180°); **LOR** = total_flux/rated. Verified: zonal total 2765.81 lm, beam 105°, field 165°, efficacy 100 lm/W.

Guards: **Type-C only** (B/A return `flux_supported=False` + structured `flux_note`, all flux/beam/field fields `None`); **absolute photometry** (`lumens_per_lamp=-1` → rated = `abs(total_flux)`, LOR=None); **beam/field reliability** flag (`_beam_field_reliable` — False for off-nadir/batwing, i.e. peak not at nadir or non-monotonic outward, with a structured `beam_field_note`); **azimuth note** when >1 horizontal plane (flat plane-mean biases partial-azimuth flux — deferred).

### 8.2 EnergyPlus daylight-controls (`lighting_controls.py`) — §7.3.5

> **Source:** EnergyPlus Engineering Reference §7.3.5, *Daylighting Calculations* (H-27…H-29).

Implements the **EnergyPlus Engineering Reference §7.3.5** lighting-control model (H-27…H-29). Two semantics: the EnergyPlus-faithful **default** vs **`workbook_compat=True`** (reproduces `elec_lights.xlsx`).

```
fL = max(0, (Iset − Itot)/Iset)                          light-output fraction needed

Continuous:     fP = fP_min                                   if fL < fL_min
                   = (fL + (1−fL)·fP_min − fL_min)/(1−fL_min) if fL_min ≤ fL ≤ 1
ContinuousOff:  = Continuous, but fP = 0 when fL < fL_min     ← DEFAULT (lamp off)
Stepped:        fP = (floor(N·fL) + 1)/N                       (floor, NOT ceil; 0 if fL=0, 1 if fL=1)

FP = Σ_i fP_i·W_i + (1 − Σ_i W_i)        zone power fraction (remainder = uncontrolled lights at full power)
P_elec = P_rated·schedule·FP ;  P_saved = P_rated·schedule·(1−FP) ;  reduction = 1−FP
```

Defaults (module constants, all overridable): `control_type="ContinuousOff"`, `Iset=500` lx, `fP_min=0.15`, `fL_min=0.05`, `n_steps=3`. The Continuous blend is algebraically identical to `fP_min + (fL−fL_min)·(1−fP_min)/(1−fL_min)` (verified ≤1.1e-16). `area_weights_from_geometry(width, length, window_head, task_height)`: primary daylit depth = `2.5·(window_head − task_height)`, **clamped at 0** as well as capped at total floor area, verified `(4,7,2.5,0.8) → W=(0.6071, 0.3929)`. Default schedule = weekdays 08:00–18:00 → 2610 occupied h (HOY 0 = Monday). Annual `kwh/m² = Σ consumed_Wh/1000/area`; `controls_series` raises on a schedule/series length mismatch rather than letting `zip()` silently truncate.

**Two guards against a negative-power result** (both shipped fixes, both cheap to re-introduce):

- `zone_power_fraction` validates `Σ W ≤ 1` (within a 1e-6 epsilon, clamping the remainder to 0 if slightly over) **and checks EACH weight for negativity** (`:82-93`), not only the sum. Weights are floor-**area** fractions, so a negative one is unphysical — and it hides inside a valid-looking total: `(-0.075, 1.075)` sums to exactly 1.0, passes the sum check, and yields `FP = −0.075`, i.e. a 250 W installation reporting **−18.7 W consumed and 107.5% saved**.
- `area_weights_from_geometry` clamps `primary_depth` at 0 (`:128`): a window head **below** the working plane makes `(window_head − task_height)` negative, and an unclamped negative depth becomes a negative area fraction and thence negative power. There is no negative daylit area; the physical reading is simply "no primary zone".

**`controls_series` returns `sum_weights`, `uncontrolled_fraction` and a prose `coverage_note`** (`:190-199`). Savings can never exceed `Σweights`, and **two shipped zoning helpers disagree about what the weights should be for the same room** — `photosensors`' zones (§4.6b) vs `area_weights_from_geometry` here — so the assumption is made visible in the result that depends on it rather than being inferable only from the caller's choice of helper. When the weights sum to 1.0 the note says so and asks the caller to confirm that is physically true, since an uncontrolled core would lower the saving.

**Golden values from `elec_lights.xlsx` — all reproduce exactly:** Row 14 (FP=0.84968881, reduction=0.15031119), Row 19 (fL₁=0.021<fL_min → Continuous fP=0.15, ContinuousOff fP=0), Row 16, All-dark (default fL=1 full power; workbook_compat fL=0), Annual (≈13.962076 kWh/m²·yr — *illustrative; not pinned by a regression test*). `workbook_compat=True` reproduces the sheet's **two off-gates** (Itot==0→fL=0; within Continuous, fL==0→fP=0); the default does neither.

**Deliberate divergences from EnergyPlus (faithful by design):** Stepped probabilistic reset (pL) deferred (deterministic only); glare→shade→Itot feedback loop omitted (so savings diverge from EnergyPlus when glare control is active); annual reconciles with the workbook, not bit-for-bit with EnergyPlus; the N-reference-point Σ-aggregation extends EnergyPlus's 1–2-point limit (reduces exactly to it for N≤2).

### 8.3 The Radiance electric adapter (`ies_radiance.py`)

> **Source:** ANSI/IES LM-63 + Radiance `ies2rad` (Ward / LBNL) (H-26).
> **Source:** Wienold & Christoffersen 2006, *Evaluating glare in buildings*, Energy Build. **38**:743 (DGP/UGR, realized in Radiance `evalglare -d`) — model lives inside Radiance `evalglare`.

`build_ies2rad`: `-m = multiplier·maintenance_factor` (**user scaling only** — ies2rad applies `mult·bfactor·pfactor` internally; folding them in would square them); units `1→-df / 2→-dm` with optional `/divisor`; optional `-c R G B` colour, `-t lamp`, `-o out_prefix`; inline `!ies2rad` form. `place_luminaires` (accepts `positions` or `grid`): `!xform -rx -ry -rz -t x y z name` — **rotation before translation** (orient in place, then move), emitted with a leading `!` so oconv/rpict expand it (a bare `xform` line is invalid scene input). Returns `{UGR, DGP, glare_sources}`.

## 9. Daysim adapter — `hcl_daysim/`

> **Source:** Skartveit & Olseth 1992 / Walkenhorst et al. 2002 stochastic sub-hourly decomposition (implemented in Daysim `ds_shortterm`) — model lives inside Daysim.

The adapter is a thin, capability-gated driver for two Daysim binaries — `epw2wea` (EPW → hourly `.wea`) and `ds_shortterm` (hourly `.wea` + `.hea` header → sub-hourly `.wea`). Every command line and the `.hea` header text is authored in pure Python (no execution), so the full plan is emittable when Daysim is absent; only `runner.run_sequence` shells out. `hcl_daysim/__init__.py` is an **empty package marker** (0 bytes). The six working modules are: `discover.py` (binary resolution), `commands.py` (command + header builders), `epw.py` (EPW → DAYSIM-convention location), `subhourly.py` (the orchestrator), `runner.py` (run-or-emit executor), and `build.py` (build-from-source helper).

**Pipeline at a glance:** `epw2wea <epw> <wea>` (hourly `.wea`) → write `.hea` header → `ds_shortterm <hea>` (sub-hourly `.wea`). The MCP surface exposes three tools over these modules: `daysim_status` (`server.py:1412`), `build_daysim` (`server.py:1421`), and `generate_subhourly_wea` (`server.py:1461`, async).

### 9.1 Discovery & `HCL_DAYSIM_BIN` handling (`discover.py`)

`_REQUIRED = ["ds_shortterm", "epw2wea"]` (`discover.py:8`) — both must resolve for the adapter to be "available". `resolve_bin(name)` (`discover.py:10`) is the single resolution point and **checks `HCL_DAYSIM_BIN` first, then `PATH`**. It is a one-line delegation to **`hcl_platform.resolve_exe(name, os.environ.get("HCL_DAYSIM_BIN"))`** — the isfile/`X_OK`/`shutil.which` logic lives in the platform base, not here, and `resolve_exe` additionally appends **platform executable extensions** (`.exe` on Windows) so the same call works cross-platform. Returns an absolute path or `None`.

`daysim_status()` (`discover.py:34`) returns `{available, bin_dir, version, found, missing}`:

- `available` is `True` only when **both** `ds_shortterm` and `epw2wea` resolve (`all(resolve_bin(n) for n in _REQUIRED)`).
- `bin_dir` reports `$HCL_DAYSIM_BIN` if set, else falls back to `os.path.dirname(resolve_bin("ds_shortterm"))` (so PATH-found installs still report a directory).
- `version` comes from `_version(ds)` (`discover.py:15`) — a best-effort probe: `ds_shortterm` has **no `--version`**, so it is run with no args (5 s timeout, stdin `/dev/null`) and the output is scanned for a line containing `DAYSIM`/`version`. The scan **skips** any line containing `fatal/error/missing/usage/cannot/no such` — the guard here matters because with no args `ds_shortterm` prints a path-prefixed *"fatal error - header file missing"* line, and because the install path itself contains "daysim" that line would otherwise be returned as the version. Returns `None` on any failure.

`_available()` (`discover.py:52`) is a convenience wrapper (`daysim_status()["available"]`) used by `subhourly`/build code (mirrors `hcl_radiance.grid._available`).

### 9.2 Command builders + the `.hea` header (`commands.py`)

Pure builders, no execution:

- `build_epw2wea(epw, wea_out)` → `["epw2wea", epw, wea_out]` (hourly `.wea`; units 1 = direct-normal + diffuse-horizontal).
- `build_ds_shortterm(hea_path)` → `["ds_shortterm", hea_path]`.
- `write_hea(*, input_wea, output_wea, timestep_min, latitude, longitude, time_zone, site_elevation, solar_time=0, units=1, input_units=1)` returns the header text.

`DS_SHORTTERM_TIMESTEPS = frozenset({1,2,3,4,5,6,10,12,15,20,30})` (`commands.py:18`) — the minutes the `ds_shortterm` `genshortterm` guard accepts (each evenly divides the hour). `write_hea` **raises `ValueError`** up-front if `timestep_min` is outside this set, so the **default 6** (δ = 0.1 h) is valid; a textually-valid-but-out-of-set value such as 60 would only be rejected at Daysim runtime, so it is caught here instead.

The `.hea` uses the **literal keyword spellings** `read_in_header.c` matches: `latitude`/`longitude`/`time_zone`/`site_elevation`/`solar_time` (site block), `wea_data_file` (input hourly `.wea`), `wea_data_file_units` (the **recognized** input-units spelling), `first_weekday 1`, `time_step` (minutes), `wea_data_short_file` (output sub-hourly `.wea`), and `wea_data_short_file_units`. `units` (output) `1` keeps solar radiation / `2` converts to photopic; `input_units` `1` = direct-normal + diffuse-horizontal.

Documented, source-checked divergences from the reference `.hea` header:

- **drops** the `project_directory` / `bin_directory` lines — `ds_shortterm`'s shortterm path never reads `bin_directory` and only uses `project_directory` to rebase *output* paths (a no-op when absent; the runner already runs in `work_dir`);
- takes the site values as **explicit args** rather than injecting the `.wea`'s first six lines;
- adds the recognized `wea_data_file_units` keyword — **epw2wea's own `.wea` writes the UNRECOGNIZED `weather_data_file_units`** (a `weather_`-prefixed variant `read_in_header` silently skips), so the header sets it explicitly rather than relying on `ds_shortterm`'s internal default;
- adds a `solar_time` line (an unrecognized keyword the parser silently skips — harmless, documents intent).

All hard-required `ds_shortterm` fields (`wea_data_file`, `time_step`, `latitude`, `longitude`, `time_zone`) are present.

### 9.3 EPW-derived location (`hcl_core/epw_location.py`)

`parse_epw_location(epw_path)` lives in `hcl_core/epw_location.py` — the spectral pipeline needs the same parse with no engine installed, and `hcl_core`'s solar-geometry functions already speak this convention — and `hcl_daysim/epw.py` re-exports it unchanged, so `from hcl_daysim.epw import parse_epw_location` keeps working. It reads the EPW `LOCATION` line (fields `_LAT,_LON,_TZ,_ELEV = 6,7,8,9`) and reproduces the exact transform `epw2wea` applies (`src/cv/epw2wea.c:54-77`), so the sub-hourly run is weather-file-consistent without the ==caller== knowing DAYSIM's sign/units conventions:


| field            | transform                                                                                  |
| ------------------ | -------------------------------------------------------------------------------------------- |
| `latitude`       | EPW latitude verbatim (north-positive)                                                     |
| `longitude`      | `round(-1.0 × EPW longitude, 2)` (EPW east-positive → `.wea` west-positive, 2 dp)        |
| `time_zone`      | `int(-15 × trunc(tz))` degrees (`int()` truncates toward zero, matching epw2wea's `atoi`) |
| `site_elevation` | EPW elevation verbatim (metres)                                                            |

Returns `{latitude, longitude, time_zone, site_elevation, tz_truncated}`, or `None` when the file can't be read, the first line isn't a parseable `LOCATION` line, or a field fails `float()` — so ==caller==s fall back to explicit values. When the EPW time zone is not a whole hour it is truncated toward zero, `tz_truncated=True` is returned, and a `warnings.warn` fires advising an explicit `time_zone` override.

### 9.4 Sub-hourly WEA generation (`subhourly.py`)

`generate_subhourly_wea(epw, *, timestep_min=6, latitude=None, longitude=None, time_zone=None, site_elevation=None, solar_time=0, work_dir, run=True)` (`subhourly.py:39`, **NOT** `epw.py`) is the orchestrator: EPW → `epw2wea` (hourly `.wea`) → `write_hea` → `ds_shortterm` → sub-hourly broadband `.wea`. Default `timestep_min=6` (0.1 h) satisfies the nvRD δ ≤ 0.3 h guard (base §5.9).

Order of operations:

1. `os.makedirs(work_dir)`, then **validate `timestep_min` against `DS_SHORTTERM_TIMESTEPS` before any file I/O** (raises `ValueError`) so an out-of-set value never produces a `.hea`/plan that only fails at runtime.
2. Site defaults from `parse_epw_location(epw)` (DAYSIM convention); **explicit args win**; `site_elevation` defaults to `site.get("site_elevation", 0)`.
3. If `latitude`/`longitude`/`time_zone` are neither supplied nor EPW-derivable, **raise `ValueError`** rather than silently running at lat 0 / long 0.
4. Filenames from the EPW stem: hourly `<stem>.wea`, output `<stem>_<timestep>_short.wea`, header `daysim_header.hea`.
5. **Always write the `.hea`** (via `write_hea`) so the emitted commands are runnable by hand.
6. Build `steps = [epw2wea, ds_shortterm]`, set `available = run and _available()`, hand to `run_sequence`.

Return contract:

- Daysim absent or `run=False` → `{wea, ran: False, commands, reason}` (with the `.hea` and command plan already written; distinct messages for the dry-run vs. missing-binary cases).
- Ran but non-zero exit → `{wea, ran: True, commands, error, failed_step}`.
- Success → `{wea, ran: True, commands, timestamps, solar_zeniths}`, where `_parse_wea_timestamps_and_zeniths` (`subhourly.py:21`) reads the produced sub-hourly `.wea` via `hcl_core.weather.import_wea` and computes a per-timestamp `solar_zenith` (lat/lon/time_zone). That helper returns `([], [])` on `OSError` so ==caller==s degrade to the documented constant-zenith fallback.

### 9.5 Run-or-emit executor (`runner.py`)

`run_sequence(steps, work_dir, available, *, timeout=None)` (`runner.py:13`) is a thin wrapper over `hcl_core.proc.run_sequence`; `render` is re-exported as `_render`. Steps are `{cmd:[...], stdin?:path, stdout?:path}`; it returns `{ran, commands, reason?, outputs}`. When Daysim resolves, **`$HCL_DAYSIM_BIN` is prepended to `PATH` for execution** (`path_prepend=[bin_dir]`) so `ds_shortterm`/`epw2wea` resolve even when that directory isn't on `PATH`; the **emitted command plan stays bare-name and portable**. The unavailable reason is *"Daysim not available; build it (build_daysim) or set HCL_DAYSIM_BIN, or run the commands yourself."*

### 9.6 Build-from-source (`build.py`)

> No binaries are bundled — Daysim is **NRC/Fraunhofer-ISE source-available** (not OSI-open); `build.py` clones + builds on the user's machine per the EULA.

`build_daysim(src_dir=None, *, run=True, work_dir=None, build_timeout=1800)` (`build.py:38`) emits (or runs) an ordered three-step plan from `_plan()` (`build.py:30`):

1. `git clone --depth 1 --branch master https://github.com/MITSustainableDesignLab/Daysim.git <src_dir>` (`BRANCH = "master"` — the README's `combined` branch is gone);
2. `cmake -S <src_dir> -B <src_dir>/build <flags>` where `_configure_flags()` (`build.py:22`) yields `-DBUILD_HEADLESS=ON`, `-DCMAKE_BUILD_TYPE=Release`, then **on macOS only** `-DCMAKE_OSX_ARCHITECTURES=<platform.machine()>` (host arch, e.g. `arm64`; omitted off macOS so the plan is Linux-usable), then `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` (the two flags that avoid the known macOS frictions);
3. `cmake --build <src_dir>/build --target ds_shortterm epw2wea`.

`bin_dir` = `<src_dir>/build/bin`. Defaults: `work_dir` = `~/hcl_work`, `src_dir` = `<work>/Daysim`. `_BUILD_TIMEOUT = 1800` s caps **each** subprocess step. Behavior:

- `run=False` → returns `{commands, ran: False, bin_dir, reason}` (emit the plan; set `HCL_DAYSIM_BIN` to `build/bin` after building).
- missing `git`/`cmake` (`shutil.which`) → emit the plan with a reason.
- **already cloned** (`<src_dir>/.git` exists) → the clone step is replaced with `git -C <src_dir> fetch origin master` + `git ... checkout master` so it refreshes the existing tree to the intended branch rather than building whatever is checked out.
- per-step `subprocess.run` (cwd `work_dir`, output captured); on `TimeoutExpired` or non-zero return, emit `{ran: False, reason}` (the failure reason includes the tail of build output and, for the `time_step` extern error, the one-line-fix hint).
- success = both `ds_shortterm` and `epw2wea` exist in `bin_dir`. When the build completes but the binaries are absent, that is reported as **`ran: False` plus a distinct reason** ("Build finished but ds_shortterm/epw2wea not found in build/bin."), not as an error.

**Known source wart:** `src/daysim/ds_shortterm.c` declares a `time_step` extern some toolchains reject; on that build failure the plan is re-emitted so the user can apply the one-line fix and rerun the `cmake --build` step.

**As-built status (2026-07-04):** `cmake` **is** present on the dev machine (`/opt/homebrew/bin/cmake`), and Daysim binaries **are installed** at `/usr/local/daysim/bin` (`ds_shortterm` + `epw2wea`, built 2026-06-27, root-owned) — set as `HCL_DAYSIM_BIN`. The **`epw2wea` → `ds_shortterm` execution path is therefore live** (`generate_subhourly_wea`, and Daysim-backed `run_annual`/`annual_nvrd`, run end-to-end). `build_daysim`'s own clone+cmake path, however, is **emit/unit-tested only** — the installed binaries were built out-of-band, not via a recorded `build_daysim(run=True)` invocation — so that specific function remains **live-unverified**.

## 10. The MCP server — `hcl_mcp/{server,advisories,clientfeatures,prompts,resources,studio}.py`

### Advisories — result-side cautions attached at the registration seam

`hcl_mcp/advisories.py` holds nine pure rules over `(tool, args, result)`, collected by the `@rule`
decorator into `_RULES`; `advise()` returns a list of `{code, severity, message, field?}`. The nine are
**`MEL_DER_BINNED`**, **`SPECTRAL_TRANSPORT_SHIFT`**, **`ELECTRIC_EXCEEDS_LUMEN_BOUND`**,
**`ALBEDO_NOT_MEASURED`**, **`DOSE_THRESHOLD_IS_DEFAULT`**, **`ZONE_WEIGHT_REMAINDER`**,
**`GEOMETRY_HEALTH_UNCLEAN`**, **`NVRD_ZERO_DIVERGENCE`** and **`RADIANCE_DROPS_IES_CANDELA_SCALE`**
(§4.1a — keys off the `engine.source_cal` stamp, which is written only by runs that rendered IES
luminaires, so it covers both the grid and the image/glare path without flagging a daylight-only
run). Note `ELECTRIC_EXCEEDS_LUMEN_BOUND` and `RADIANCE_DROPS_IES_CANDELA_SCALE` bound the electric
block from **opposite** sides: the first catches surplus light (a leaked sky, a double-counted
fixture), the second a deficit, and neither can detect the other's failure. Two more are worth naming for what they
encode: `ALBEDO_NOT_MEASURED` fires because IWEC/TMY2 files write a literal `0.000` albedo for every
hour instead of the 999.0 sentinel, so `hcl_core` treats sub-physical values as missing and
substitutes (ADR-0004) — the substitution is correct practice, reporting it as measured is not; it
reads both the top-level `provenance.albedo` and the nested `atmosphere.provenance.albedo`.
`NVRD_ZERO_DIVERGENCE` flags an exactly-zero `divergence.neutral_vs_colored_sun` as the **timestep
artefact** it is (§7.4) rather than a physical finding. `server.py`'s `_with_advisories` wraps **both** registration
loops — the main tuple and the alias loop — and `_attach` merges a non-empty list into a **dict**
result, returning a new dict and omitting the key entirely when nothing fires. Non-dict results pass
through untouched, so multi-point `circadian_metrics` (the only union-annotated tool, `-> dict | list`)
carries none; exceptions propagate unwrapped so FastMCP still marks `is_error`.

Three properties are load-bearing and were established by probing FastMCP, not by reasoning:
`functools.wraps` is required — without it FastMCP rejects every tool with
`ValueError: Functions with *args are not supported as tools` at import, so the failure is loud
rather than a silent schema degradation; FastMCP fills unset parameters with their declared defaults
before the call, so a wrapper cannot tell a deliberate `250.0` from an absent argument (hence
`DOSE_THRESHOLD_IS_DEFAULT` is value-based); and `Σweights < 1` is documented intended behaviour, so
`ZONE_WEIGHT_REMAINDER` quantifies the uncontrolled remainder rather than asserting an error.

**Depth is part of a rule's contract.** `_iter_dicts` walks only the top level, which is right for
`circadian_metrics` (the metrics dict *is* the result) and wrong for `run_grid`, which nests every
per-point field under `daylight`/`electric`/`combined`.`metrics[]`. A rule reading a per-point field
through `_iter_dicts` alone therefore fires in its unit test and **never in production** —
`SPECTRAL_TRANSPORT_SHIFT` shipped that way for one commit, and `MEL_DER_BINNED` for far longer.
Both now use `_point_metrics`, which yields `(block, metrics)` over both shapes —
`ELECTRIC_EXCEEDS_LUMEN_BOUND` reads `electric.lumen_bound` explicitly for the same reason.
A test asserting a rule against a hand-picked nested dict does not prove the rule reaches the tool.

`_point_metrics` yields the **block name** because the right caution differs per block, and that is
what makes widening `MEL_DER_BINNED` an improvement rather than noise. The `daylight` block is
exempt: it is present on every run, its spectrum is a smooth sky where the binned route costs
~0.13% (methodology §"mel-DER accuracy"), and no single source spectrum exists to pass instead — so
a warning there is permanent, unactionable and ~60× overstated, which is how an advisory system
teaches people to stop reading it. `electric` and `combined` exist only when luminaires were driven,
which is exactly when a narrow-band source makes the ~8% real, and each gets its own message: pass a
shared `spd`/`preset` for `electric`; for `combined`, whose mixture has no single source spectrum,
exploit that **mel-EDI is additive** (melanopic irradiance is linear in the spectrum) and sum the
`daylight` and `electric` blocks. Measured across a daylight:electric sweep, the summed parts stay
within ~0.4% of the continuous truth while the `combined` block's own binned value degrades from
+0.17% to **+8.11%** as luminaires take over.

**A rule that fires on everything teaches people to stop reading it** — the mirror of the depth bug.
`GEOMETRY_HEALTH_UNCLEAN` fires only on a real defect (`ok` false, or a non-zero warning count) and
deliberately **not** on a non-empty `skipped`, which is structurally never empty:
`check_geometry_health` always appends the Tier-1 categories plus a `sensors` and a `luminaires`
entry on every branch, so triggering on it warned on every single import, spotless report included.
The skipped categories are still named once the rule has fired on other grounds, where they are
useful context rather than noise.

The rules read fields `hcl_core` already computed and phrase a caution about them — reporting, not
physics, which is why they sit in the protocol layer. Rationale and rejected alternatives:
[`adr/0005-advisories-attach-at-the-registration-seam.md`](adr/0005-advisories-attach-at-the-registration-seam.md).

### 10.1 Study-brief persistence + report rendering — `hcl_mcp/studio.py`

> **Source:** `hcl_studio` guided-journey spec, 2026-06-11. **Scope:** pure Python (json/os/re, no Radiance); the three MCP tools `save_brief`/`load_brief`/`build_report` (`server.py:1578`/`:1587`/`:1594`) are thin `ctx`-aware wrappers over these functions.

The `hcl_studio` journey (the `hcl_studio` prompt, §10 prompts) threads **one resumable study brief** across its phases. `studio.py` is the persistence + report layer.

- **Brief schema.** `_PHASE_KEYS = ("orient", "goal", "space", "daylight_baseline", "fixture_spec", "sim_results", "energy", "compliance")` — 8 phase slots. `_ALLOWED_BRIEF_KEYS = frozenset(_PHASE_KEYS) | {"study"}`. `empty_brief(study)` returns `{study}` + one `None` per phase.
- **Slug safety.** A `study` slug becomes a directory name and arrives from MCP arguments, so `_safe_study` enforces `_SAFE_STUDY = ^[A-Za-z0-9._-]+$` and rejects `"."`/`".."` (raises `ValueError`) — no path traversal out of the work dir. `_brief_path` = `<study_dir>/<study>/brief.json`.
- **`save_brief_to_dir(study_dir, study, brief)`** — shallow **per-top-level-key merge** into the stored brief (a phase passing only the keys it changed leaves the others intact). Unknown top-level keys **hard-fail** with `ValueError` rather than silently corrupting the schema; when a rejected key matches `_BRIEF_KEY_ALIASES` (e.g. `"fixtures"→"fixture_spec"`, `"savings"→"energy"`, `"room"/"geometry"→"space"`) the error carries a "did you mean" hint. The slug param is canonical — `current["study"] = _safe_study(study)` always overrides any `"study"` inside `brief`. Writes `json.dump(..., indent=2)`, returns the path.
- **`load_brief_from_dir`** — reads `brief.json`, returns `empty_brief(study)` if absent.
- **`_render_markdown(brief)`** — the report template (pure string building, no Radiance). Non-dict guard: any phase field given as a non-dict (e.g. `goal="office"`) degrades to `{}` → "*not evaluated*" instead of crashing on `.get`. Sections: **Goal**, **Space**, **Daylight Baseline**, **Fixture Spec**, **Target vs Achieved** (a `_row`-built table of Photopic Ēm / mel-EDI / UGR / Energy-saved with ✅/❌; UGR uses `lower_is_better=True`), **Renderings**, **Compliance**, **Notes & Caveats**. It is deliberately alias-tolerant so a natural `save_brief → build_report` round-trip populates rather than blanks: `_first()` accepts the natural key shapes upstream tools emit (space dims as `L/W/H`, `length/width/height`, or a `[L,W,H]` list under `dimensions`/`bbox_m`/`size`; fixture `required_flux_lm`/`fixture_count`/`target_cct_band`; the sim tools' `melanopic_lux` as a fallback for `mel_edi`). **That fallback is a quantity CONVERSION, not an alias** (`:199-218`): a legacy `melanopic_lux` brief is converted to mel-EDI — preferring the exact `photopic_lux × mel_der` relation, else dividing by the D65 mel/photopic ratio (~1.0997, derived from `hcl_core.metrics._d65_ratio`, never hardcoded) — and the affected row is flagged with a ⚠️ note. Passing `melanopic_lux` through unconverted would manufacture a false PASS against a mel-EDI threshold. `compliance` is accepted as either a list or a `{standard: verdict}` dict (`:244-247`). It also cross-checks circadian↔glare: if the mel-EDI target is met but `ugr > ugr_max`, it emits a **⚠️ Conflict** callout, and surfaces the circadian `verdict_source` and the fixture spec's own `assumptions`/`caveats`.
- **`build_report_to_dir(study_dir, study, brief)`** — renders to `<study_dir>/<study>/report.md` and `report.html` (the HTML is the same markdown escaped into a monospace `<pre>`). Pure templating — **always runs**, no Radiance needed. The slug param wins over `brief["study"]` so the header never shows "?". Returns `{md_path, html_path}`.

### 10.2 First-principles fixture-sizing engine — `hcl_core/fixtures.py`

> **Source:** `recommend_fixtures` spec 2026-06-11 §6 (constraints C1–C5). **Lineage:** first-principles lumen-method + CIE S 026 mel-DER solve; NOT a port. **Honesty:** every estimate is an engineering **ILLUSTRATIVE** approximation — the CU table is planning-grade (not a manufacturer photometric table) and the LED palette is illustrative (not measured product data). This engine is unit-tested only and has **never been live-validated**; the real chosen IES (phase 5, `ies_analyze`) and the phase-6 Radiance grid are what validate a design. Pure Python, zero external deps beyond the optional `colour` used by `mel_der`/`cct_duv`.

Drives the `recommend_fixtures` tool (`server.py:1558`, whose wrapper fixes `per_fixture_lumen_options=(2000,3000,4000)` — that arg is not exposed over MCP).

- **`_CU_TABLE`** — coefficient-of-utilization approximation indexed by integer Room Cavity Ratio (0..10) for a reference reflectance set (ceiling 0.70 / wall 0.50 / floor 0.20), for three distribution classes (`direct`, `direct_indirect`, `indirect`). Illustrative planning values; phase-5 `ies_analyze` recomputes UF from the real luminaire.
- **`room_cavity_ratio(L, W, h_cav)`** = `5·h_cav·(L+W)/(L·W)` (zonal-cavity RCR; `h_cav` = luminaire-plane→work-plane height).
- **`utilization_factor(rcr, distribution, ρ_ceiling, ρ_wall, ρ_floor)`** — linear interpolation of `_CU_TABLE` over RCR (clamped 0..10), scaled by a reflectance factor `= clamp(1 + δ, 0.6, 1.25)` where `δ = 0.5·(ρ_ceiling−0.70) + 0.4·(ρ_wall−0.50) + 0.1·(ρ_floor−0.20)`; returns `round(base·factor, 4)`.
- **`visual_flux_lm(...)`** — `Φ = Em·A / (UF·MF)`. Daylight is intentionally **NOT** subtracted (spec C1): the installation must meet Ēm with no daylight; daylight savings are realized operationally by phase-7 controls.
- **`led_palette()`** — the illustrative LED candidate list `[{name, cct_K, mel_der}]` sorted by CCT, built from `presets.ILLUSTRATIVE_LEDS` via the verified `cct_duv()`/`mel_der()` (NOT a Planckian idealization, spec C3 — LED spectral structure changes mel-DER). Cached in `_PALETTE_CACHE`; `ColourRuntimeWarning`/"Aligning…"/"CCT…" warnings are suppressed narrowly (stderr noise for stdio MCP clients).
- **`MEL_DER_PHYSICAL_MAX = 1.2`** — the practical mel-DER ceiling for a usable white source (D65 = 1.0 by definition; deliberately blue/cyan-enriched white reaches ~1.1–1.2). Reachability is gated on this **physical** ceiling, NOT on the illustrative palette's much lower max (~0.82), so the recommender does not over-advise supplementary fixtures for targets a real cool/blue-enriched product could meet (documented approximation, spec C2).
- **`solve_circadian_spectrum(required_mel_der, physical_max=1.2)`** — three bands (spec C2): `required ≤ palette max (~0.82)` → reachable `by_palette=True`, names the lowest-CCT preset that clears it; `palette max < required ≤ physical` → reachable `by_palette=False` (beyond the illustrative palette, no example preset); `required > physical` → not reachable (==caller== routes to extra vertical E_v). Returns `{reachable, by_palette, chosen_preset, chosen_cct_K, palette_max, physical_max}`.
- **`_SHR = {"direct": 1.5, "direct_indirect": 1.25, "indirect": 1.0}`** — spacing-to-height ratio (max), uniformity criterion `S ≤ SHR·h_cav`. `_grid_layout(L, W, count, s_max)` densifies a near-square grid until `nx·ny ≥ count` and returns cell-centre positions.
- **`recommend_fixtures(...)`** — the entry point. Defaults: `workplane_height_m=0.8, eye_height_m=1.2, ρ_ceiling=0.7, ρ_wall=0.5, ρ_floor=0.2, maintenance_factor=0.8, target_em_lux=500.0, target_mel_edi=None, mel_edi_daylight=0.0, vertical_horizontal_ratio=0.4, distribution="direct", target_efficacy_lm_w=120.0, per_fixture_lumen_options=(2000,3000,4000)`. Validates `distribution ∈ _CU_TABLE`, `h_cav = mount − workplane > 0`, `vhr > 0`, and — when a circadian target is given — `target_em_lux > 0` (`:184-185`, since it is the divisor forming `e_v_eye`).
  - **Visual sizing** via `visual_flux_lm` (C1, no daylight subtraction) → `phi_visual`; binding defaults to `"visual"`.
  - **Circadian sizing** (only when `target_mel_edi` is given): `e_v_eye = target_em_lux·vhr`; `net_mel_edi = max(0, target_mel_edi − mel_edi_daylight)` (daylight credited here only, C1); `required_der = net_mel_edi / e_v_eye`; `solve_circadian_spectrum`. If reachable, the spectrum handles the target with no extra flux (visual stays binding, CCT taken from the chosen preset or the coolest palette entry). If **not** reachable (above the physical ceiling), it adds vertical light: `e_v_needed = net_mel_edi / MEL_DER_PHYSICAL_MAX`, `extra_horizontal = e_v_needed / vhr`, `phi_circadian = extra_horizontal·A/(UF·MF)`; if that exceeds `phi_total`, `binding="circadian"`, and `supplementary_fixtures_advised`/`glare_warning` flip True.
  - **Layout/count** reconcile flux vs uniformity (C5): `uniformity_count = ⌈L/s_max⌉·⌈W/s_max⌉`; pick the smallest `per_fixture_lumen_options` entry that covers `phi_total/uniformity_count` (else the largest); `flux_count = ⌈phi_total/rec_lumens⌉`; realized `fixture_count = nx·ny ≥ max(flux_count, uniformity_count)`.
  - **CCT band:** no circadian target → `[3000, 4000]`; reachable within palette → `[chosen_cct, coolest]`; beyond palette / unreachable → `[5500, 6500]` (cool / blue-enriched white, verify on the real SPD).
  - Returns `required_flux_lm, fixture_count, layout{nx,ny,spacing_m,positions}, target_cct_band, min_mel_der, mel_der_achievable_max (=1.2), palette_mel_der_max, beyond_illustrative_palette, circadian_reachable_by_cct, binding_constraint, vertical_horizontal_ratio, flux_count, uniformity_count, est_total_watts, power_density_w_m2, per_fixture_options, supplementary_fixtures_advised, glare_warning`, plus inline `assumptions` and `caveats` (every result carries its own illustrative-palette / lumen-method / glare warnings).

## 12. Correctness findings — consolidated

### 12.1 Deliberate design choices

- **§9.3a** float division in the α-opic reconstruction (integer division would zero all outputs; `alpha_opic.py:50` uses float literals `(179.0/683.0)*(1.0/107.0)` to restore the intended CIE S 026:2018 computation).
- **§9.3b** 3-channel bin re-ordering (a descending-bin vector would misalign channels against the CIE S 026 action spectra). The 3-channel path reorders to `[b, g, r]` on the ascending bins (`_BINS_3_ASC`); 3-channel output intentionally differs from the naive descending-order result, and the 9-channel path is unaffected.
- **nvRD even-filter-length guard** + honoured `timestep_h` (a naive implementation hardcodes 0.1, ignoring its own input; this implementation honours the Amundadottir 2016 model's timestep parameter from `NVRD` in `data.py:36`).
- **§9.2** neuropic b3 standardized on the grid value `0.000069431` (`data.py:24`, `W_NEUROPIC_9[2]`), not the alternative image/pcomb rounding `0.00007`.

### 12.2 Surfaced (computed best-effort, flagged), not silently wrong

- IES beam/field angles for off-nadir/batwing → `beam_field_reliable=False`.
- Multi-plane IES flux azimuth bias → `flux_azimuth_note`.
- Y-up→Z-up Euler remap exact only for single-axis rotation.
- Synthesized FOV masks "not publication-grade."

### 12.3 Known approximations & deferred items (documented)

- α-opic channel path is a flat bin approximation; exact-from-SPD path (`alpha_opic_from_spd`, `alpha_opic.py:116`) provided for accuracy/validation.
- LED presets illustrative; CIE D/A/F-series authoritative.
- Annual sun left neutral in transport; enhanced colored-sun is the post-process (time-resolved per-timestep on a live Daysim run — constant-30° only as the degraded fallback, §7.5).
- Stepped probabilistic reset; glare→shade feedback loop; modified-Ēm tier in EN 12464-1; Brown-2022 `night` mis-attribution.
- 9-channel recombination ordering is an unpinned ==caller== contract.

## 13. The caveats that matter most before a live run

1. **Enhanced reconstruction is time-resolved on a live Daysim run; constant-30° is now a fallback (§7.5).** `generate_subhourly_wea` surfaces per-timestep `timestamps`/`solar_zeniths` and `annual_nvrd` feeds them into the reconstruction, so the air-mass colored-sun **does** vary by time of day on a real EPW→R_D run. A constant 30° zenith is used only in degraded mode (no Daysim / empty `.wea`), labelled in `enhanced_solar_note`. The residual caveat is the **fidelity of the `weather.solar_zenith` model** (a simplified constant-declination position), not a fixed-angle limitation.
2. **Most live end-to-end paths are now validated; the electric/luminaire and image/glare Radiance paths remain emit-/mock-tested.** This caveat has moved substantially since the original review (which said "no built Daysim (no `cmake`)"). As of the 2026-06/07 live re-validation the following run on real binaries — Radiance 6.1a at `/usr/local/radiance`, Daysim at `/usr/local/daysim/bin` (`HCL_DAYSIM_BIN`): the grid daylight pipeline (562.345 lux = 179π, live-verified), the 2-phase annual DDS (`run_annual`), the Daysim sub-hourly + `annual_nvrd` bridge, the SMARTS oracle, and the native `gensdaymtx` spectral sky. Since then the remaining gaps have closed: the electric-lighting/luminaire→Radiance transport and the image/glare (`rpict`/`evalglare`) paths went live on 2026-07-18 (the "undefined modifier" luminaire-group defect that blocked `office_room.obj` is fixed — `import_geometry` excludes luminaire groups from its material sets and builds the mapfile from the same scene map), and `annual_daylight` had a full production run on 2026-08-12: the complete 8760 h Athens year over 45 points, twice, at two ambient settings. `daylight_factor`'s wrapper remains toy-scene smoke-tested only. ⚠️ Two standing conditions on the now-live paths: electric numbers are valid only on an `A1`-honouring engine (§10.3), and an executed run is evidence the pipeline composes, not evidence it agrees with measured light.
3. **The spectral-sky-from-EPW pipeline runs end-to-end offline, and both native-binary paths have been live-validated (§7bis).** The pure-Python stack (EPW→atmosphere/geometry→SPECTRL2→SEDES1→1nm record→artifacts) is unit-tested and the SPECTRL2 port is golden-validated (<0.05% direct / <0.01% diffuse vs the SPCTRAL2 PC kit). Status by binary path: **the native `gensdaymtx` driver received its first live validation 2026-06-20** under Radiance 6.1a at `/usr/local/radiance/bin` (NCOMP=20, Pearson 0.987 vs Python engine — validation, not a baseline; band-order reversal noted in §7bis.11); the **SMARTS** engine received its **first live validation 2026-06-21** (compiled from the NREL SMARTS 2.9.5 source — that distribution's Mac binary is dead PowerPC; with `SMARTSPATH` set the gated cross-check `test_smarts_cross_check_clear_sky` passes and SMARTS agrees with the Python SPECTRL2 engine to ~2 % direct / ~7 % diffuse at r≈0.99 — validation, not a calibrated baseline; see `docs/spectral-engine-comparison.md`); only the opt-in **`physical_sky` Daysim/DDS flip** (default-off, shape-only) remains **never run live**. Two further honesty caveats: (a) **by default, the SEDES1 CCM coefficients are a faithful 10 nm Fig. 11 digitization** (`cloud_variant="reanchored"`; the 9-point eyeballed digitization is now only the opt-in `cloud_variant="seed"`) — *only the per-component energy-rescale (∫direct=DNI, ∫diffuse=DHI) is exact*; the digitization's regression σ is surfaced in provenance (`ccm_sigma`/`ccm_sigma_mean`), and the CCM shape can be locally re-fitted from measured spectra (`cloud_variant="local"`, `hcl_core/sedes1_fit.py`, `docs/recalibrating-cloud-ccm.md`); (b) **the physics is opt-in** — the §7.5 30° air-mass fallback is still the default reconstruction. The canonical as-built record + deviations ledger is `docs/spectral-sky-as-built.md` (its §9 carries this caveat wording); the physics/math derivation is `docs/spectral-sky-methodology.md`.

Plus the standing scientific caveat: **R_D is relative only** — the §9.3a `1/107` constant non-linearly scales it (it cancels only in ELR and in same-path EDI *ratios*, never in absolute EDI/mel-EDI — §1.5), and the nvRD model's daytime validity carries a ±20% / 9%-of-exposures envelope.
